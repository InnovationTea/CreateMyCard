# 2×4 单例闭环：Q058 InfoBlock 文字规格

## 本轮范围

先固定 Q057 的本地检查点，再处理 Q058。不修改原始输入、既有 Few-shot 或修复预算，
不按案例编号、会议名、具体电量或地点选择布局。暂不处理灵动布局、2×2 或 DataDisplay。

Q058 还有会议标题重复、查询具体值未进入预览等问题。本轮先只修复可确定的
InfoBlock 规格；后续问题单独观察、定位，不一次叠加所有策略。

## 设计

- 仅刷新 2×4 Recipe：主文本 body-M/14fp/700、行盒 19vp；次文本 body-S/12fp/500、
  行盒 16vp；主次间距 2vp。
- 保持固定槽 132×57vp、左右 padding 8vp，以及 icon/环的原尺寸和中心位置。
- 文案组承接槽内可用高度、顶端留 8vp，再从顶部连续排列；不把文字和 visual 一起顶推。
- 有 unit 的 primaryValue/primaryRow 同步主文本规格，单位仍底对齐；不追加或拆除业务单位。
- 参数由 Recipe 提供，不向模型开放字体、行高、padding 或固定槽几何。
- 不降低校验标准、不删字段，不改 2×2 的 InfoBlock Recipe。

## 验证

1. 合成组件：无 visual、icon、progressCircle，分别覆盖有/无 unit；保持真实动态绑定。
2. 用原 Q058 DSL 在同一渲染链路下分别渲染修改前后，区分确定性组件修复与模型变化。
3. 原 Q058 单例推理，检查字段和操作覆盖、校验、截断及真实 DOM 的文字位置。
4. 用 Q057 保存产物做本地回归；条件适合再用 Q059 验证复用效果，不先改 Q059 策略。
5. 保留每次失败和输出；不宣称这几个已知开发样本证明全量泛化。

## 单例发现与第二步

第一版原输入推理成功但修复 7 次：缺失动作的组件行虽被补出，却不可从 root 到达。
通用修复消息在没有容量错误时要求保留旧布局，容易使模型只新增孤立按钮，随后全树重组又
把完整会议降为短信息槽。新增一条仅针对 2×4 Action 覆盖失败的修复指引：核对可达引用和合法
动作位；有现成动作位时仅补引用，没有时允许最小必要的 Region/父布局变更。
不替用户选定父布局，不修改校验判定、事实、候选、Plan、重试上限或 Few-shot。

Q058 可见业务字段 4/4、操作 2/2；图库将两个动作条件字段也计入分母，显示为 4/6。
这不代表缺少两个用户要求展示的值。Q059 图库为 4/4 数据、2/2 操作。
Q058 预览时间仍为字段样例 14:00，而查询明确时间为下午三点；尚未修改首帧具体值处理，需独立闭环。

Q059 第二步见 [辅助文本同行预算](2026-10-14-2x4-casewise-q59.md)。其 r2 初稿与 r1 不同，
没有进入新宽度错误的修复，不能将首次通过或时延变化归因为这一检查。确定性证据是合成测试
可拒绝“标签＋完整值”超宽并接受合法两行。Q058 两次初始错误也不同，不能用 7→1 次证明策略收益。

真实 Chromium 六种 InfoBlock 组合均测得：主行顶/左偏移 8vp，主行高 19vp，次行高 16vp，
行间距 2vp，图标 24vp/环 44vp 继续居中。原 Q057 r4 保存输出在当前处理器中通过本地回归。
本轮未重新调用 Q057、未运行全量、未改 2×2 规格、未改变案例输入或 Few-shot、未按案例编号分支。
所有生成结果包含不理想的 r1，均保留在 `compact_dsl/output/1014-casewise-*` 中。
