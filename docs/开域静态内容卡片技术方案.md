# 开域静态内容卡片技术方案

## 1. 目标与设计状态

### 静态展示质量增量（2026-10-25）

本轮修复容量传递、分字段覆盖与对象身份保护：

- 静态内容组增加可选 `identity`（非空短名称或null），工具合同要求新计划显式表达；旧计划兼容省略。
  名称由模型结合来源声明，不从用户词、requirement或组ID提取。object的非空identity必须在本对象可见；
  shared只能为null。名称不占事实索引，候选可以将它放到标题或标签；整组可选省略规则保持原有口径。
- 来源语义仍交模型；覆盖只比较已接受的展示文字。原展示中明确的排版分隔片段可分别出现在同对象的
  带标签字段，允许字段前后增加说明；ASCII词元、数字与小数的边界必须完整，不能用130GB覆盖30GB，
  不能把散落的单字或数字重新拼成事实。原文模式不使用宽松覆盖。
- 容量反馈必须进入归一化返回及staticPresentationFeedback，在原两次Plan提交内使用；失败细化仍保留
  先前合法计划。不以有限试排未命中证明全局无解，不在接受后改写核心。
- 静态Layout.variant新增compact，根间距由共享合同给出；无标签属性使用attributeBody行盒，
  辅助说明使用note行盒。保持12字号及原安全区，所有行数和整卡高度仍实际校验，不扩大溢出容差。
- 对指定七个失败样本及Q013/Q047做历史源回放、真实模型抽样和显示核对；动态合同另做隔离回归。

复用当前两阶段模型调用，静态 Plan 可选增加 `presentationStyle`（auto/content/attributes/records/comparison）
和 `paletteFamily`（auto/blue/purple/warm）；静态 text 事实可选 `displayRole`，取值为
title/body/label/value/leading/trailing/detail。这些均为内部计划字段，不增加公开请求或端侧契约。
模型根据用途判断角色、主次和结构，程序不搜索业务词、修改动词或标点来推断语义。
同一对象内按角色分字段；名称、范围与决定含义的关联条件须在已接受展示事实中出现。
角色相同的多个事实保留顺序并合并承载，不因角色提示删除事实；动作不接受展示角色。

有限候选使用角色及已有组件候选，保留全部选入文字和组顺序。无角色时按原有事实顺序构造无标签正文，
不补造“信息”等占位标签；ContentBlock.attributes 的 value 必填、label 可选，显式标签仍须非空。
候选先按模型结构偏好和角色承载排序，再采用首个通过原公共校验的版本；未找到候选不拒绝 Plan。
staticPresentation 为已验证的备选，模型已有合格层级时无需强制复制，不用候选降低合格原稿的质量。
实际容量不足时仍沿用既有修复预算，不扩尺寸、不缩字、不由程序改写或删除核心。
首次合法 Plan 的有限候选均未通过时，可消耗原有第二次 Plan 提交额度反馈容量参考，
由模型在接受前调整摘要、字段和主次；反馈不宣称全局无解，第二次合法计划仍可交给 DSL。
候选可在全部保留版本失败后尝试省略模型已授权的无保护 should，计划本身保持原样并在交付记录实际缺失。
四至六行属性采用共享静态合同的 compactAttributeGap；不通过缩字或裁切提高容量。

静态后置主题复用现有蓝、紫、暖配色。模型可登记用户色系偏好；auto 或未登记时按有效请求内容稳定选择，
不根据业务关键词分类，不使用请求 ID、当前时间或每次随机数决定颜色。显式用户颜色继续优先。
静态面板使用主题已有浅色 panel 角色，属性表值列统一对齐；不改动态主题注册表默认值。
所有新增规则只在静态策略下生效，旧动态合同和 multi_step、单步创建与编辑不扩展。

支持用户把演唱会、旅行、备忘、节假日安排等开域信息制作成桌面卡片。卡片保存制作时采用的内容，
添加后不自动更新。内容可以筛选、合并、调整顺序和精简表达，不要求把全部来源事实逐字放到卡面。
用户明确要求保留的内容及影响用途的关键信息必须准确，不能通过精简改变对象、日期、地点、数量或条件。

采用普通 Compact 创建入口内的请求级生成策略，复用现有 Fusion 编排、模型客户端、转换器、主题和保存流程。
增加确定性的请求识别与策略选择，按策略组装提示词和校验规则，不新增场景识别模型调用或独立生成服务。

2026-10-24 已按本文完成普通 Fusion 创建链路适配，并同步
[云侧方案设计](云侧方案设计.md)。请求级策略、三类语义组件、来源与对象分组保护、共享文字度量、
静态布局、修复和保存前复核已接入；当前启用静态策略供本地手动批跑，真机验收仍须独立完成。
用户已授权复用现有文字与间距规范补齐首期参数，实际参数登记见第 15 节；不从截图像素反推。

依据：[产品需求 PRD](开域静态内容卡片产品需求PRD.md)、UX 设计图目录、
当前生成代码，以及本次讨论确认的静态识别和允许精简原则。UX 参考图仅在本地保留，不随本次提交提供。
闭域及混合动态请求继续采用原有事实传递和静态文本约束，不套用本专项的精简和删除政策。
本次不新增公开请求字段、动态能力或模型阶段；在线主 Agent 先选择静态展示范围，再完整传递选定事实，
不以自行改写的摘要替代来源。动态、混合动态及编辑保持原事实传递方式。

首期闭环同时接入 `ContentBlock`、`RecordList`、`ComparisonGroup` 和静态文档式布局，

不把旧组件扩展为万能内容容器；对比限定为 2x4 的 2–3 个等权静态对象，不扩大为任意网格。

## 2. 范围与兼容边界

| 项目 | 首期范围 |
| --- | --- |
| 创建入口 | 现有 `generateWidgetCardCompactDsl` |
| 内容类型 | 无动态数据绑定的静态内容，包括用户输入、已确认对话和已核实外部事实 |
| 来源获取 | 主 Agent 完成；生成服务不搜索、不推断个人事实 |
| 内容精简 | 在信息计划阶段选择展示范围、合并表达、形成展示文本 |
| 数据刷新 | 不新增刷新能力，不注册虚假的动态数据能力 |
| 点击动作 | 仅使用本轮已有且通过预检的事件；无动态数据不等于必须无动作 |
| 素材 | 可以为空；已有素材仍按原授权和适配规则使用 |
| 混合动态内容 | 保持现有动态创建路线，首期不套用本专项策略 |
| 模板专用入口 | 保持原语义，不变成静态 Fusion 入口 |
| 编辑、multi_step、单步创建 | 不在本专项设计和改造范围；仅保留路由隔离与相邻回归 |

| 后续 UX 扩展 | 2x2 多栏、混合多行网格及其它新变体另行设计，不提前开放 |

首期不增加公开生成工具、必填请求字段、TaskSpec 顶层字段、产物块或端侧解析协议。
不按演唱会、旅游、备忘逐项注册场景，不自动开放购票、预约、通知或随时间变化的倒计时。
静态来源不能作为实时数据能力的替代：用户要求实时余票而能力不可用时，仍应先处理需求边界。

## 3. 现有基础与适配缺口

| 现有实现 | 可以复用的部分 | 适配缺口 |
| --- | --- | --- |
| `CardSpecBuilder.build()` | 无绑定时构造静态运行配置 | 不需要为静态展示新增动态绑定 |
| `GenerationPreflight.run()` | 参数、事件、素材、能力和写入路径预检 | 预检成功后补请求级内容策略 |
| `submit_card_plan` | 静态事实、主次、组件和布局候选 | 静态 `text` 由模型提交摘要展示版本，引用与展示分离 |
| `PromptBuilder` | 同一消息历史中的 Plan、DSL 与 repair | 补静态内容模块，隔离动态专属说明 |
| `DesignCompactProcessor` | 确定性处理、语义布局、转换和容量检查 | 接收策略，并执行静态内容约束 |
| Compact 事实覆盖 | 已接受计划与可见内容对照 | 区分来源文字和精简后的展示文字 |
| `TextBlock`、`SummaryList` | 简单横向属性背板、同级单行摘要 | 不具备通用长正文、结构化记录和完整对比对象的承载能力 |
| S/W 布局合同 | 确定性几何、自适应编译与预算 | 增加静态专属文档式布局，不放宽原布局角色限制 |
| 文字预算 | 单行压力检查及声明行数的高度预留 | 增加静态长文本所需行数、条目分栏和完整可见性检查 |
| `CompactRepairStrategyTracker` | 有界修复、布局重组及可选删除 | 阻止静态核心事实进入通用 must 删除或缺失 warning 机制 |
| 模板 Search | 已登记业务的数据模板检索 | 依赖动态能力及字段，首期跳过而非改造 |
| 后置主题与保存 | 合格主题、最终产物、上传和响应 | 核对无业务素材的默认主题及精简结果反馈 |

设计原则是保留公共主流程，在少量调用点传入内容策略；不复制一套生成服务或完整校验流水线。

## 4. 模块与端到端流程

```text
主 Agent：确认需求、核实来源、明确展示范围与精简要求
  → 现有请求解析与创建／编辑分流
  → 现有 GenerationPreflight
  → GenerationContentPolicyResolver（新增，确定性识别）
      ├─ existing：原有路线
      └─ static_content：静态内容策略
          → 跳过业务模板、JSX 和未适配的单步兜底
          → 公共创建合同 + 静态内容模块 + Plan 阶段指令
          → 同一 Plan 调用完成内容选择、精简、对象分组和展示计划
          → 校验来源引用、受保护信息、分组及必要容量
          → 同一消息历史继续生成 Compact DSL
          → 公共转换与校验 + 静态展示内容检查
          → 同一策略下的有界 repair
          → 公共后置主题与最终内容复核
          → 公共保存、上传和响应
```

模块名为拟新增名称，不代表仓库已有实现。

### 4.1 主 Agent 与生成服务的职责

主 Agent 判断用户要静态快照还是动态刷新，获取并核实来源，处理场次、地区、年份、对象歧义，
说明实际采用的信息及卡片不自动更新。用户本次要求优先于历史记忆；偏好不能推断为已购票或已预约。

生成服务只基于已采用内容做展示规划，不补查来源。查询结果和用户正文按不可信内容处理，不能覆盖
提示词、事件或素材规则。无动态数据时跳过数据权限请求；已有事件和素材仍按原流程检查。
能力概述及工具调用顺序暂沿用在线 Skill，本专项不顺带优化为另一套调用 SOP。

主 Agent 仍按当前来源规则清洗并完整传入本轮实际采用的事实，不把生成模型当作查询工具，
也不先摘要后用摘要冒充完整来源。纯静态普通创建先按用途选择核心事实与必要上下文，查询也围绕该范围，
不默认采用所有相关详情；未要求的背景、宣传、重复解读及非必要附加详情不进入展示事实。
事实选择须保留完整对象名称、关联数值及单位、时地、适用范围和必要条件；用户明确的数量、字段、顺序、
对比、原文和全部展示约束不可擅改。不使用业务关键词、正则、固定条数或字符阈值截取。
改变明确要求且无法判断优先级时，生成前按在线 Skill 的 R05 确认一个展示重点；开放式速览可直接选取重点。
详细执行规则见在线 Skill 的“纯静态创建的展示范围选择”。选择完成后原顺序完整传递事实，
展示精简和实际容量判断仍由 Plan 与布局校验完成，不反写或裁剪已确定的有效需求，
不把整段来源默认升级为逐字必显正文，不新增容量失败反馈或保证复杂请求一定成功。
用户明确要求“原文”“全部列出”的部分另作保护。

静态正文直接写入合法显示属性，不伪造数据能力、动态 schema 或 `/data/static/...` 绑定。
首帧辅助状态沿用协议允许的 `/state` 等位置；不通过本专项增加端侧刷新任务。

### 4.2 识别模块

拟新增 `services/generation_content_policy.py`，包含内容模式、不可变策略对象和策略解析器。
解析器在预检成功后、构造提示词和调用任何源生成器之前执行；只读请求与预检结果，不再次查询能力。

识别按下表顺序执行，前一条命中后不继续转入其它模式。

| 条件 | 决策 |
| --- | --- |
| 提供来源产物 | 沿用编辑入口，不进入本专项识别 |
| 非普通 Compact 创建入口 | `existing` |
| 专项开关关闭 | `existing`，保持原有路由和默认行为 |
| 请求、能力或参数预检失败 | 按原错误处理，不生成静态卡片 |
| 原始请求包含数据能力候选 | `existing`；即使最后没有有效绑定，也不在此转换需求 |
| 最终仍有动态绑定 | `existing` |
| 普通创建、预检成功、原始数据候选及最终绑定均为空 | `static_content` |

缺失和空数组都表示未请求动态数据，但不得用能力失败后的空集合冒充原始空集合。
有批准的事件或素材不阻止静态模式。没有事件或素材也不是失败条件。
纯文字欢迎卡、静态动作入口等没有动态数据的请求也可归入这一数据模式；不存在额外的“演唱会识别”。
模式识别不强制选择正文或列表布局。纯动作请求继续使用现有动作合同，不补造正文、状态或装饰标题来填槽。

识别证明的是请求的数据形态，不能证明语义上不需要刷新，也不能证明事实充分。
后两项由主 Agent 的需求确认和 Plan 检查承担；不声称能从空绑定确定性识别出所有伪装成静态的动态需求。

## 5. 请求级生成策略

内容策略独立于现有 `GenerationRoutePolicy`。后者继续描述工具、协议、后端和处理器的固定差异，
前者只描述本次创建的内容规则，避免把“使用哪个入口”和“怎样处理内容”混成一个开关。

拟新增不可变 `GenerationContentPolicy`。首期以模式及固定行为约束为主，不实现可自由组合的策略框架。
下表是各模块必须遵守的行为矩阵，不要求每一行都成为可配置字段或独立 profile。

| 维度 | `existing` | `static_content` |
| --- | --- | --- |
| 模式 | 原有模式 | 静态内容 |
| 提示词 | 原提示词装配路径 | 公共基础加静态内容模块 |
| 源生成路线 | 沿用原配置 | 仅本专项适配的 Fusion，不进入业务模板或其它创建路线 |
| 校验 | 原有检查及严重程度政策 | 公共检查加静态来源、分组、展示与容量合同 |
| 内容精简 | 原行为 | 模型在Plan完成摘要与省略；DSL/repair落实已接受版本 |
| 核心覆盖 | 原有阶段性政策 | 已接受核心展示事实始终硬校验 |
| 省略 | 原有受控删减 | 无保护 should 可整项省略，核心省略号须已写入Plan |
| 组件与布局 | 原有候选和范围 | 三类新正文及必要标题、共享说明、动作；兼容布局按清单准入 |

策略应由解析器构造完整组合，不允许散落的布尔值形成“静态提示词加动态删除兜底”等非法组合。
处理器、计划校验、repair、主题后复核和结果规划消费同一策略。
旧调用未传策略时默认 `existing`，不得让本地脚本、标准 A2UI 或历史测试自动改变行为。

拟新增 `services/static_content_context.py` 保存本次已校验的来源引用、展示计划、对象分组、受保护片段、
允许省略项和实际省略项。该上下文仅在服务内部传递，不由模型修改开关，也不写入动态能力集合。
同时保存本请求使用的策略与合同版本；新增组件准入由服务上下文决定，不能由源 DSL 标记自行授权。
所有新增参数宜使用可选的仅关键字参数并保留旧默认值，避免改变现有位置参数和返回类型。

## 6. 内容精简与信息计划

### 6.1 来源内容与展示内容分离

| 层次 | 含义 | 完整性要求 |
| --- | --- | --- |
| 来源内容 | 用户提供或本轮核实、采用的输入材料 | 可追溯；不是全部必显清单 |
| 展示计划 | 本次选入卡面的内容及精简后的文字 | 核心用途和用户要求成立，精简有来源 |
| 最终卡面 | 对已接受展示计划的实现 | 核心内容准确可见；可选省略受策略控制 |

不要求保留所有来源事实。例如用户要演唱会速览，来源中的艺人履历、宣传文案和重复售票说明
可以不进入展示计划；名称、场次时间、地点等关键字段应按实际需求保留。
用户要“完整三天行程”时，不能按速览策略只选第一天；应先判断容量，必要时缩小范围。

### 6.2 允许与禁止的精简

允许删除无关背景、去重、合并同对象的相关描述、调整展示顺序，以及把完整句改为简短标签和值。
不得改变否定、条件、范围、时间先后、地点归属或确定程度；“预计”“待确认”等限定不能被改成确定事实。
不得补造数据、从不同场次各取一个字段拼成新场次，或把“可选活动”表述为“已安排活动”。

用户明确要求原样展示的正文采用逐字保护，不能自动摘要。一般正文允许精简，不默认逐字保护。
字符等价和换行规范应使用统一规则；不能以删除标点、单位或否定词的宽松归一化掩盖语义变化。

### 6.3 在现有 Plan 调用中完成精简

不新增“摘要模型”阶段。静态 Plan 在现有模型调用内同时选择展示范围、组织内容和形成展示文本，
继续提交 `submit_card_plan`。动态路线仍使用现有工具合同和静态文本解析规则。

闭域 `text` 继续使用原有原文规则；开域仅在独立静态策略内允许模型精简、总结和改写。
程序不比较摘要与引用的数字词元或原文拼接，不全局删除闭域原文检查。

| 静态事实字段 | 设计含义 |
| --- | --- |
| `requirement`、`priority`、`text` | 沿用现有字段；`text` 在静态模式下是精简后最终要展示的文字 |
| `sourceTexts` | 支撑展示事实的原文连续引用；可含未选上下文，引用全部内容不等于卡面必显内容 |
| `protectedTexts` | 仅用户明确要求逐字保留的来源片段；普通摘要填空数组，不以此代替语义核验 |
| `selectionNotes` | 静态 Plan 内部规划说明，最多8条、每条200字符；不单独触发降级 |
| `omittedContents` | 模型登记实际遗漏信息，最多24条、每条200字符；等义总结、措辞精简及去重复不算信息损失 |
| `preserveVerbatim` | 静态模式新增；用户明确要求原样展示时为 true |

新增字段仅用于静态 `text` 事实，不开放给动态路径或动作事实；不增加 TaskSpec 顶层字段。
`sourceTexts` 必须能在本次有效输入中定位；程序保存引用位置并限制引用数量、长度和总输入预算。
同一来源可以拆成多项展示，多个来源可以支持一项展示，但不得因此证明跨对象合并合法。

以下仅为虚构输入的机制示例，不是现实演出信息：

```text
来源：示例乐队的演出安排在六月十八日晚上七点半，场馆是示例剧场。
展示：6月18日 19:30 · 示例剧场
```

该例的等义日期时间表达由模型判断并复核，不要求逐个登记转换规则。程序不凭字符串不同拒绝摘要，
也不把引用存在当作语义正确的证明；具体数值和关系准确性由模型负责。

`must` 用于用户明确要求及用途成立必需的内容，`should` 用于可选补充。模型不能为了容量把明确要求降为 should。
展示内容数量仍受当前 Plan 和布局合同限制，不通过把长文塞进一个事实或提高数量上限绕过容量。
当前 `info_required` 总数上限为 24；2x2/2x4 的 6/10 条 must 是现有提示词引导，不是仅凭条数拒绝的程序门禁。
静态适配不改变这些旧规则，但按实际文字和布局预算检查内容。不得用“列表最多三项”省略用户明确要求的完整清单。

### 6.4 精简正确性的可验证边界

确定性检查可以证明引用存在、受保护片段保留、原文模式未变、已接受展示文字可见以及事件未变。
它不能仅靠字符串证明任意摘要语义正确，也不能证明模型已经列出用户要求的全部核心事实。

`sourceTexts` 和 `protectedTexts` 都由同一 Plan 模型提交，不构成独立真实性判官。
保护片段不完整、对象分组错误或用户核心要求未被提取，仍可能通过局部字符串检查。
Plan模型负责按用途摘要、选择主次并自查事实与关系；现有DSL模型阶段对照原始输入和Plan再次检查。
不增加独立语义评审调用，不增加输出审查字段，也不声称同一模型自查等同于独立核验。
模型抽样验收包含错误合并、条件遗漏和重要信息遗漏；这些是语义质量检查，不伪装成程序可判定的负例。
程序负例验证明确原文要求、已接受核心遗漏、对象错位、非法结构和容量溢出。
后续需要更强的多对象校验、内容更新或追溯时，可评估一个兼容旧请求的可选结构化静态输入，
表达对象与来源关系；这属于后续契约设计，不在首期增加每个场景专用字段。

### 6.5 对象分组及从 Plan 到条目的映射

静态 Plan 增加 `contentGroups`，冻结对象与条目关系，不开启或扩展现有全量 `composition` 工作表。
该字段仅属于静态 Plan 参数，不进入公开请求或 TaskSpec 顶层。动态 Plan 的字段白名单保持原样。

| 分组字段 | 约束 |
| --- | --- |
| `id` | 本计划内唯一的非空组 ID，仅用于内部映射，不作为用户业务标识或端侧绑定 |
| `kind` | `object` 表示一个对象／记录；`shared` 表示适用于全卡或集合的标题、说明或共同条件，不决定 must／should |
| `factIndexes` | 本次提交的 `info_required` 中从 0 开始的事实索引，不重复、不越界 |

每条入选静态 text 事实必须归属一个组；没有 text 事实的纯动作计划允许 contentGroups 为空数组。
同一场演出、同一行程成员或同一对比对象的事实进入同组；
日期、地点、金额与条件不能只按字段类型全局归并。Action 沿用原归属合同，不因没有正文组而被删除。
装饰标题不新增为硬事实；用户明确要求的标题文字仍须进入事实与对应组。

Plan 可根据用途调整组的顺序；接受后，RecordList 的 items 顺序与 object 组顺序对应，
ContentBlock 承载对应单对象，ComparisonGroup 的各栏对应各对象组。
shared 组仅进入已登记的全卡标题或说明位置，不拆到其它对象的日期、金额或属性槽。
没有相关标题／说明时不创建空组，不把对象独有条件提升为全卡共同条件。

归一化必须保留“原事实索引 → 接受后索引”的映射，并同步分组引用。现有按 `(来源类别, 文本值)`
去重的规则不能原样用于跨对象静态事实：两场演出均为“19:30”时，仍须保留两个对象各自的时间。
仅同组、同来源身份的等价重复可合并，不能因文字相同把两个条目合成一个。

DSL 不必新增 `groupId` 等业务 Prop；程序通过接受后的组顺序及各组件、items 的局部可见内容检查映射，
并在 Trace 保存定位结果。同一条目内标题、描述和属性可以共同覆盖本组事实，不跨条目、栏或全卡拼接覆盖。
该检查保护已接受的对象关系，不能证明 Plan 最初划分的对象关系必然正确。

### 6.6 计划接受后的内容边界

接受 Plan 时冻结核心事实、关键片段、组归属和顺序。DSL 允许把同一事实拆为同条目的标签和值，
或按已登记的规则折行；不能重新摘要、改写限定条件、交换对象，或为套用组件新增结论。
引用定位保留原始来源与位置；查找所需的换行规范化和展示等价比较分开维护，不复用删除标点与空白的宽松比较。
重复来源片段存在多个位置时保留可追溯的位置集合，不猜测唯一来源。

首期不登记任意同义改写比较器。格式变换只有在规则明确、双向信息不丢失并有负例验证后才准入；
否则按已接受展示文字复原。来源的范围、条件及关系由模型在Plan摘要中准确表达，不由关键词识别器推断保护清单。

## 7. 提示词组装

### 7.1 结构与加载

```text
公共基础：输出格式、协议、树结构、来源安全、事件与素材边界
  + 请求内容模块：existing 或 static_content
  + 当前尺寸已经实现的组件、组合和布局合同
  + 当前阶段增量：Plan／DSL／repair
  + DSL 阶段按原开关加载的同尺寸、同策略参考案例
```

静态规则在构造提示词时选择，不把一大段规则无条件追加到现有提示词尾部。
与静态精简冲突的动态专属规则和旧原文照搬说明，在静态路径下不加载；公共授权规则不被替换。
不修改全局创建提示词常量来同时改变其它请求。

继续使用 `compact_prompt_loader.py` 和 `prompt_source/manifest.yaml` 的模块化源机制。
旧 `existing` 加载路径应保持组装结果等价；静态新增独立的组合入口或内容模块引用，
由 `PromptBuilder` 按策略选择。禁止顺带重排旧模块、删除旧案例或修改全部尺寸规则。

### 7.2 各阶段要求

| 阶段 | 静态增量 |
| --- | --- |
| Plan | 根据用户用途筛选和精简；区分核心与补充；提交来源、保护片段和对象组；按可用组件预算规划 |
| DSL | 实现已接受文字、分组及顺序；仅从本期静态准入集合选组件和布局；无素材正常成卡 |
| repair | 使用同一计划、来源及保护信息；保留对象归属；优先修结构和容量，仅按 Plan should 授权省略补充 |
| 主题 | 使用公共候选选择规则；没有合格图片时使用通用背景；不能改文字迎合主题 |

Plan、DSL 和 repair 复用现有递增消息历史。Plan 不加载 Few-shot，DSL 案例仍遵守总开关和筛选开关。
静态案例不得意外回退到全量动态业务案例；开启静态策略前必须具备其声明需要的案例资源。
如果暂时只做框架联调，可使用已实现组件的静态机制样例，不能将其称为最终 UX 验收案例。
总开关开启且筛选关闭时加载同尺寸、同静态策略的全量案例；筛选开启时仍只在该集合内选择。
不得因静态案例库尚小而复用包含未授权业务字段、强制图标或未落地扩展组件的案例。

首期案例覆盖长标题、正文加属性、两条带副文记录、三条紧凑记录、两栏／三栏对比、
各栏长短文案、共同条件说明、无素材和可选补充省略。Plan 阶段仍不加载案例，所需组件容量合同由运行时生成。
本专项只补静态内容容量摘要，不打开动态路径默认关闭的全量运行时容量提示开关。

来源与展示文字作为数据传入，正文内的“忽略规则”“调用某动作”等内容不能改变 system 或策略。
策略相关内容须覆盖 repair 路径；只改首次创建提示词会使修复恢复原文规则或错误删除政策。

## 8. 校验设计与归属

继续运行现有公共校验流程，按请求补静态检查；不设置静态来源豁免，也不关闭整体 Compact 校验。
公共规则缺乏静态组件支持时，应补齐正式合同后接入，不以静态场景名绕过检查。

| 检查项 | 分类与实际落点 | 复用及归属理由 |
| --- | --- | --- |
| Plan JSON、字段类型和可选字段范围 | Plan 解析及工具合同，`compact_plan.py` | 扩展静态模式 schema；动态字段白名单不变 |
| 来源引用是否在本次输入中、保护片段是否有来源 | 语义／跨输入一致性，`compact_validation/semantic/cross_file.py` | 检查来源与计划的关系，不写入业务入口 |
| 分组索引、原索引到接受索引的映射 | Plan 解析与归一化，`compact_plan.py` | 属于静态计划结构，不以改全局去重规则影响动态 Plan |
| must／should 与动作完整性合同 | 语义／跨文件一致性，`semantic/plan_contracts.py`；Plan 覆盖保留原编排入口 | 不复制一套动作规则；静态核心硬保护 |
| 展示文字、保护片段、对象组及原文模式的可见性 | 语义／展示，拟新增 `semantic/static_content.py` | 复用公共可见文本提取，增加同对象和同条目局部覆盖，不重复维护全局 Plan 覆盖 |
| 新组件 Props、枚举及静态类型 | 语法／组件，复用共享组件合同及 `syntax/components.py` | 组件展开与检查使用相同合同，不按场景名豁免 |
| 表达式及树结构 | 既有语法检查和转换器 | 原流程直接复用；静态内容不新增动态表达式权限 |
| 事件、素材与动态路径边界 | 既有有效能力、绑定和跨文件检查 | 静态模式不授予额外路径或动作 |
| 静态组件与布局的请求级准入 | 共享组件／布局入口及其调用上下文 | 新组件和布局只向静态请求开放；不凭 DSL 标记授权，不扩大动态集合 |
| 多行文字、分栏及总高度容量 | `semantic/layout/`；必要时新增 `text_capacity.py`，依赖共享度量合同 | 属于布局与视觉约束，不在展示文本检查中复制几何算法 |
| 最终协议、运行配置和主题 | 既有 ArtifactValidator、主题检查 | 继续公共校验，主题之后补静态合同复核 |

实施前应再次核对 Compact 专项方案和规则分类清单。若共享可见文本辅助逻辑需提取，应做等价抽取，
保持旧规则顺序和诊断行为，不借本适配扩大为校验器整体重构。

### 8.1 三次检查位置

1. Plan 接受前检查静态引用、组与索引、优先级及保护合同；对已能确定的组件容量反馈错误，沿用现有 Plan 次数。
2. 每次 DSL 处理、确定性重组及模型 repair 后，检查已接受文字、条目映射、容量和省略授权。
3. 主题和其它后处理结束、保存之前，在最终标准 A2UI 上复核核心内容的可达性、可见性和承载容量。

静态专项合同属于该策略的必要检查，不受通用完整产物校验开关关闭而跳过；通用开关本身的行为不变。
静态上下文缺失或不一致时返回明确失败，不降回 existing 或从 DSL 标记推测授权。

### 8.2 诊断与规则登记

计划解析错误继续使用 `CompactPlanValidationError`。DSL 与最终产物问题沿用结构化诊断，
记录规则、来源事实位置、展示项、实际值、期望约束和可选修复建议。

拟新增静态专项诊断为来源不被允许、核心展示缺失、保护文字改变及原文模式改变；
正式标识需同步 `rule_catalog.py`、规则分类清单、诊断测试及必要的修复建议配置。
能够复用现有事实覆盖错误的，不再新增同义诊断。建议不能放宽核心保护或授权新的事实。
分组错误须定位到组和条目；容量反馈须包含完整文字、实际参考可用宽度、估算行数、预留行数和高度差。
新组件展开时保留源组件及 item/属性到基础节点的来源映射；无可靠映射时标记展开位置，不编造源行号。

不新增外部业务状态和错误码：模型阶段失败沿用 `A2UI_GENERATION_FAILED`，最终校验失败沿用
`VALIDATION_FAILED`；参数、能力、存储及网络错误保持现有语义。

### 8.3 文本存在与完整可见分开检查

源 DSL 中包含完整字符串，不等于文字已经完整显示。静态检查分别确认：

1. 展示文字与保护片段位于已接受的对象／条目中，而非其它条目、数据行、样式或未使用属性中。
2. 对应组件从 root 可达，且未被静态隐藏、透明承载、裁切或不足的行数吞掉。
3. 展开后文字有符合 Recipe 的可用宽度与行高；父容器容量同时成立，不以 maxLines 声明代替内容测量。

现有多行 Text 宽度检查会跳过 `maxLines != 1` 的节点，高度检查主要按声明行数预留；
首期必须补新组件的多行需求检查，不能只把正文 maxLines 改大就视为支持长文本。
现有 TextBlock 等组件的省略 warning 不自动成为新组件或静态核心事实的豁免。

## 9. 修复与容量策略

### 9.1 精简主要在 Plan 阶段完成

来源材料可以大量筛选，已接受计划冻结本轮实际展示版本。DSL 和 repair 不任意改写核心，可受控省略可选补充及非原文尾部。
这保护的是精简后的展示合同，不要求恢复已在 Plan 阶段合理省略的原始背景信息。

Plan 发现过长时，可在其原有次数内重新精简；UX 预算齐备后可提供容量反馈。
修复阶段如需要重新定义核心展示范围，应回到用户需求或新一轮计划，不暗中修改已接受 must。
首期不增加额外的内部 Plan 重规划循环，沿用现有接口整轮重试边界。
接口重试从原始有效请求重新规划，但“必须原文”“完整清单”等用户要求不因上一轮失败而丢失。

### 9.2 静态模式的修复顺序

```text
修正局部属性、引用和格式
  → 无损调整组件合组与合法父布局
  → 复用有界确定性重组并复检
  → 在剩余预算内模型修复
  → 容量仍不足时，省略无保护的 should 补充，或对非原文补充显式尾部省略
  → 核心仍无法容纳：失败，说明需要缩小范围
```

静态 must、用户要求的原文和所有已接受 Action 始终不可通过通用删除兜底移除。
原来的修复后非 Action 缺失 warning 政策不适用于静态核心；Plan 的无保护 should 本身即为可选授权。
不能直接套用 `validation_omitted_fact_indexes()` 在特定配置下扩展到全部非 Action 的行为。

省略候选必须是仅承载可省略内容的组件；同时含核心信息、动作或受保护文字时不能整体删除。
沿用实际覆盖复检和交付反馈；常规 should 省略无需等待修复预算耗尽，修复额外授权仍累计记录。
新组件内部允许在授权后删除纯补充属性或条目；授权应精确到事实索引与源 item/属性位置，
不能因为一个 should 位于 RecordList 内就删除整份列表。删除后同步合法引用、序号和组到条目的映射。
已接受组的相对顺序保持不变；补充组整体删除后，其余组按原顺序重新映射，不用压缩后的下标指向另一对象。

既有确定性重组函数只对明确支持的新结构调用。首期不顺带重写其旧候选搜索器；
如果候选生成器不理解新组件，应保留原稿和诊断交给模型修复。任何被采用的候选必须带同一静态上下文复检，
不能在候选验收时漏掉核心保护、分组和多行文字容量。

### 9.3 尺寸与过长内容

沿用生成前尺寸裁决。用户明确规格优先；主 Agent 按有效展示范围和已登记预算建议最小可用规格。
本专项首期不在 repair 中自动从 2x2 扩到 2x4，不增加重复开始通知或中途重建运行配置。
请求固定规格放不下核心信息时失败；来源过长也不能通过无限缩字、裁切、隐藏或机械截断满足校验。
不默认增加滚动、翻页或多卡交付，这些都需独立 UX 和协议支持。

Plan 事实数和模型上下文沿用既有边界；当前公开请求对 userQuery 只有非空约束，不能假定已有长来源上限。
首期为静态模式登记来源总长度、引用数量与长度、分组数量和模型输出预算，具体阈值作为实施配置确定，
不改动态请求的默认限制。模型调用前检查可确定的输入预算；超预算时按现有失败语义返回可执行说明，
由主 Agent 处理展示范围，不机械截断末尾文本或丢弃行程后半段。
最终卡面容量按文字和组件合同判断，不用统一总字数阈值替代不同尺寸与信息结构的预算。

### 9.4 重试和其它路线

模型异常、Plan 修复、DSL 修复与接口整轮重试沿用各自预算，不因静态模式叠加额外次数。
静态请求每一轮重新执行预检与策略选择，使用原始有效需求；上一轮删减不得污染下一轮输入。
容量恢复仍只针对已识别的结构或容量错误，恢复模式也不能删除静态核心。

静态模式跳过业务模板、JSX 和未适配静态合同的单步新建兜底，避免修复失败后绕开内容保护。
动态请求的模板回退、JSX 开关及单步兜底保持原行为。最外层上传等接口重试政策也保持原行为，
不能把本专项的路线限制描述成“所有存储错误都不会重跑整轮”。

## 10. UX、组件与布局适配

### 10.1 设计图依据与可确认范围

设计图用于确定信息结构与视觉方向，不作为真实业务事实，也不直接提供端侧尺寸或素材授权。

| 设计资料 | 可确认的信息结构 | 本方案承接 |
| --- | --- | --- |
| 单信息示例 | 单对象标题、可折行正文、1–3 行辅助属性，部分属性靠下 | 首期 ContentBlock；具体可容纳属性数按 Recipe 和正文剩余空间判断 |
| 列表信息示例 | 单条强调或最多三条记录，标题、副文、可选侧边信息；支持两种尺寸 | 首期 ContentBlock / RecordList，不要求所有条目具有日期或数值 |
| 信息对比示例 | 最多三个等权对象，主信息、描述和辅助内容；可有共享说明 | 首期 ComparisonGroup，仅 2x4 的 2–3 对象；不把它等同于旧 TextBlock |
| 典型示例 1 | 演出记录、场馆说明、属性表、带前后侧信息的行程、套餐对比 | 覆盖单对象、记录和对比的组合；场馆排期等多行容量单独验算 |
| 典型示例 2 | 指标说明、长短属性混排、多对象辅助条件及共享备注 | 首期覆盖正文／属性及受控等权对比；复杂多行网格不提前承诺 |
| 配色示例 | 相同前景可采用蓝、紫、橙等配色 | 复用后置主题，不把业务名称绑定为专属色或图片 |

设计图中的省略号不作为核心内容裁切授权。条目数、字体、行高、间距、背板和对齐必须形成正式合同，
参考几何只用于预算；开发预览显式提供视口，不能用截图像素证明真机避让或任意小宿主完整可见。

### 10.2 开域正文与兼容组件的边界

开域正文只允许 ContentBlock、RecordList、ComparisonGroup。TextBlock、SummaryList、TableText、
EmphasisText、EventCard、InfoBlock、DataDisplay 等旧正文组件退出开域 Plan 候选和模型源准入，
容量不足及 repair 也不能恢复这些组件；它们在闭域策略中的合同、Props、字号及校验保持不变。

旧组件只保留 SingleLineTitle 短标题、SecondaryBody 必要共享说明，以及 PillButton/CardButton 批准动作。
标题和说明不承载 object 核心；SecondaryBody 在静态策略下限定单列、12 字号、1–2 条说明，
每条共享说明最多三行，复用静态文字度量及固定行展开，实际总高仍须通过。
模型不直接提交基础 Text、Row、Column、Stack 或 Group；基础节点由程序展开。

无动作只使用 S-static-content/W-static-content。2x2 必要单动作兼容 S-title-content-action，
双动作兼容 S-content-dual-action；2x4 必要动作兼容 W-split-panels，正文仍只允许三类新组件。
2x4 的 W-four-slots 仅兼容四个批准 CardButton 的纯动作请求，禁止承载正文或说明。
这项动作兼容保留闭域系统操作入口，不把旧四槽重新开放为开域内容布局。
Plan 工具枚举、运行时布局范围、语法准入、模型修复说明及正式案例使用同一集合。

### 10.3 首期 ContentBlock：单对象正文与属性

ContentBlock 是拟新增的 Compact 语义组件，支持 2x2/2x4；内部全部文字属于同一 object 组。
它承载标题、段落和同对象属性，不是任意嵌套组件、富文本 HTML 或完整页面容器。

| Prop | 拟定合同 |
| --- | --- |
| `title` | 可选非空静态字符串；对象主标题，允许的行数由尺寸和变体 Recipe 决定 |
| `body` | 可选非空静态字符串；已接受的精简正文，可含显式换行，不解析 Markdown 或 HTML |
| `attributes` | 可选非空数组；每项仅为非空静态字符串 `label` 和 `value`，顺序与展示计划一致 |
| `variant` | `flow` 或 `bottom-attributes`，默认 flow；仅从本尺寸已登记的变体选择 |

title、body、attributes 至少存在一个，不用空字符串或空数组占位。属性不是必需时不补造；
只给属性也应能成立，不强制增加强调主值。标签和值保留对象、单位和限定语，不用位置代替必要说明。

flow 按实际内容顺序排布；bottom-attributes 仅在存在属性且上方完整内容与下方属性均放得下时准入，
程序使用剩余区域分配，不能用分布对齐掩盖溢出。不提供模型任意字号、宽高、权重或间距参数。
各属性可单行或按已登记模式折行，实际行数参与总高度；不把设计图的某个行数作为所有内容的通用上限。

### 10.4 首期 RecordList：结构化记录

RecordList 是拟新增的 Compact 语义组件，支持 2x2/2x4，适用于同一列表中结构相近的对象。
首期登记 1–3 项，单项优先选择 ContentBlock；多项按 object 组顺序逐项对应，不能随机取前三条。

| Prop | 拟定合同 |
| --- | --- |
| `items` | 1–3 个非空记录对象，不支持动态数组模板或任意嵌套组件 |
| `items[].title` | 必填非空静态字符串，表示该条目的对象名称或核心内容 |
| `items[].description` | 可选非空静态字符串，承载同对象的副文、地点或简短说明 |
| `items[].leading` | 可选非空静态字符串，承载确有来源的日期、Day 标记等前置信息 |
| `items[].trailing` | 可选非空静态字符串，承载确有来源的日期、价格或状态等侧边信息 |
| `variant` | `plain` 或 `panel`；分隔线或条目背板由对应 Recipe 生成，模型不自画装饰 |

每条至少有 title，不要求日期、价格或图标。description 与两侧字段不借用其它条目事实，
不为凑齐结构新增“推荐”“已预约”等结论。两侧可同时出现，但必须先扣除其宽度再计算标题和副文容量；
主文过窄时改选本期其它合法结构，不压窄到只能显示省略号。
一条、两条、三条分别有容量合同；三条是 UX 条目上限，不代表长记录一定能放下，也不授权删除完整清单成员。

首期三个新组件的业务内容均仅接受静态文字，不增加 PathBinding、Expression、条目／栏内 onClick 或任意素材字段。
Action 仍由已有合法动作组件承载，按第 10.6 节处理。动态绑定仍只通过原合同支持的旧组件使用。

### 10.5 首期 ComparisonGroup：多对象对比

ComparisonGroup 与正文、列表组件一起纳入首期，限定 2x4 的 2–3 个等权静态对象。
它复用相同的来源、Plan 分组、文字容量、主题及交付流程，只补对比语义与横向展开，
不新增独立生成阶段、模型调用或对比专用服务，也不以 TextBlock 的两层字段冒充完整实现。

| Prop | 首期拟定合同 |
| --- | --- |
| `items` | 必填，恰好 2 或 3 个非空对象；各栏按接受后的 object 组顺序对应 |
| `items[].primaryText` | 必填非空静态字符串，承载该对象的主信息，可为数值加单位或简短文字 |
| `items[].secondaryText` | 可选非空静态字符串，承载对象名称或紧密相关的描述；是否必显由 Plan 决定 |
| `items[].details` | 可选非空静态短文字数组，首期最多 2 条；各条只描述本栏对象 |

shared 说明由外层 note 承载，不增加组件内任意 footer、嵌套组件或模型自定义几何。
2x2 对比、四栏、跨行网格、不等宽栏、栏内点击和动态绑定不在首期范围。
两栏与三栏分别登记 Recipe；每层行数、字号、间距和高度在首期实现前确认，不从截图反推。

同级对象保留必要名称、单位、口径及条件；不能把所有运营商、日期或限定语只写一次后造成归属歧义。
primaryText、secondaryText 的层级在同卡各栏保持一致，不能让某栏展示价格、另一栏却以日期作为主比较内容。
需要强调价格或短状态时按语义选择主信息，不按字符串中是否含数字决定大字号。
模型不能补造本栏缺少的属性来凑齐结构；各栏可有不同数量的真实辅助内容，缺省位置不产生占位文字。

栏宽等权分配扣除内边距与固定间距后的参考剩余空间，再按各栏内边距计算文字区；
最长一栏决定整组所需高度，且必须扣除整卡 header、note 等承载空间。
不能用整卡宽度估算单栏文字，也不能让短栏的空白抵消长栏溢出。
三栏放不下时，修复可合法折行、调整组件／布局或按授权省略 should；不能直接删一个对象改成两栏。
减少栏数仅允许移除无保护的纯 should 对象组，且剩余至少两组；核心对象或用户明确要求的对象不可删除，
容量不足本身不是省略授权。整组省略的实际结果仍记录为 degraded，并重新核对剩余栏映射及比较口径。
用户未限定横向布局且对照目的仍成立时，可以改用完整保留同级对象与比较口径的列表等合法形态；
明确要求横向对比而核心内容无法容纳时失败，不用普通列表假装完成。

### 10.6 静态文档式布局

首期拟登记 `S-static-content`、`W-static-content`，分别适用于 2x2/2x4。
这是同一文档式布局族的两个尺寸合同，不复用或改写 S-title-content 的贴底语义、S-center 的 DataDisplay 限制，
也不放宽 W-top-bottom 对主区／明细及组件类型的要求。

| 角色 | 结构与边界 |
| --- | --- |
| `header` | 可选 SingleLineTitle，作为整卡短标题；用户要求的全卡标题归 shared 组，装饰标题不新增事实 |
| `body` | 必选；首期为 ContentBlock、RecordList，或仅 2x4 可用的 ComparisonGroup |
| `note` | 可选 SecondaryBody，承载 shared 组的说明或共同条件；按原辅助文字合同，不能独自承担整卡核心 |

由登记的角色组合生成 children，顺序为 header（若有）、body、note（若有）；不需要独立标题时省略 header，
模型不写空容器或占位组件。
`variant=flow` 按顺序排列；`variant=bottom-content` 仅在没有 note、正文确有剩余空间时允许将完整 body 靠下，
用于设计图的标题与单条记录分离场景。ContentBlock 内部属性靠下由自身变体负责，不与根布局重复分配空白。
长对象标题放入 ContentBlock.title 或记录 title；不能为保留装饰 header 而截断用户要求的长标题。

新布局族首期不提供点击角色，也不派生 root 点击。已接受 Action 时应选择兼容的既有动作布局，
将新组件放入其合法正文槽，容量、正文组件准入和动作槽全部复检；没有合格布局则失败，不删除动作。
这种兼容组合在首期必须有登记案例与测试，不能凭“普通内容组件”跳过父布局限制。
纯动作请求沿用原动作布局，不强制进入本布局族。

静态布局范围单独登记，包含本期文档式布局及已验证的兼容旧布局；不把新 ID 无条件加入动态
`S-plan-guided/W-plan-guided`。模型提示、Plan 候选、展开、修复与校验消费同一请求级范围。
当前部分覆盖与主题辅助调用写有固定旧 scope，实施时须传入有效 scope，不能只在首次提示词中换范围。

根尺寸沿用 matchParent、自适应区域和公共安全区规则，内部固定设计量来自 Recipe。
不按截图固定整卡像素宽高，不为长内容自动扩宽，也不将所有文字或间距整体缩放。

### 10.7 文字容量合同与展开

首期新增共享的静态文字容量辅助模块，例如 `static_text_capacity.py`；名称可等价调整。
它接收完整展示文字、已知参考可用宽度及 Recipe 文字规格，输出估算所需行数、占用高度和不能确定的原因。
Plan 中可确定的容量提示、新组件展开及 `semantic/layout/` 校验共用此模块，不各维护一套字符阈值。

计算必须覆盖显式换行、中文与拉丁文本、数字单位、长英文／URL 连续段，以及记录前后侧字段的占宽。
不得把字符数简单除以常数当作精确排版；首期可采用保守参考估算，并保留字体和实际宿主折行的不确定性。
未知值不能当作已通过，也不能退回“maxLines 已声明所以放得下”。

程序按正式 Recipe 选择有限行数与变体；模型不填写自由 maxLines 或几何。
总预算先扣除 header、note、内边距与间距，再验算 body；纵向累加实际所需行盒，横向按分栏实际宽度检查。
属性多行时计入完整高度，列表按各项高度累加，对比按各栏最大高度计算。
反馈包含可用空间与所需空间，修复仍优先合法折行、分组及布局，不通过降低核心字号或只减行数过关。

新增语义组件先展开为现有 Text、Row、Column、Divider 等基础节点，复用主题角色和资源映射。
在所用基础组件及属性均已由目标协议支持的前提下，不增加端侧原生组件和最终 A2UI 消息格式；
仍须同步源位置映射、组件准入、基础属性校验、预算及开发渲染测试，再开放模型输出。
调试平台的 Compact 预览沿用正式后端转换；如有仍被使用的独立转换源，按仓库同步机制处理，不直接修改生成副本。

### 10.8 无素材与主题

没有图标、图片是正常输入。卡片依靠文字层级、分组和留白成立；不补无关素材、不用 emoji 或
未授权海报代替缺失图标。搜索得到图片地址不代表获得生成资源授权。

复用后置主题的候选准入、选择和兜底；陌生业务没有专属图片或融球主题时使用已登记通用渐变。
设计图中的三套配色作为可用视觉方向，是否使用仍由当前主题配置和用户偏好决定，不新增按场景名的主题路由。
新增部件使用主文字、辅助文字和内容背板等既有角色，布局阶段不输出实际色值。
无法确认新结构的图片准入时使用合格通用背景，不改布局或正文迎合图片；主题完成后继续静态内容复核。

### 10.9 对比并入首期的风险与准入条件

对比与正文／列表共享同一条生成链，提前接入不增加新的服务边界；额外风险主要在栏内可读性、
对象关系及组合验收。首期通过有限结构和共同验收控制，不以共用流程代替视觉验证。

| 风险 | 首期约束与验收 |
| --- | --- |
| 三栏长标题、长数值及单位无法完整显示 | 只支持 2x4 的 2–3 栏；按单栏实际参考文字区和最宽完整文案验算，不缩字或默认省略核心 |
| 名称、价格、单位或条件被分到错误对象 | 各栏与 contentGroups 一一对应，局部覆盖；共享条件与对象独有条件分别保护 |
| 比较口径不一致或模型补齐空缺 | 同卡强调层级与指标语义一致；缺字段保持缺省，不补造数据、排名或比较结论 |
| header、共享 note 与对比组争夺高度 | 组合核算总预算，以最高栏为组高；必要共同条件不能为保住三栏而省略 |
| 修复把三栏变两栏或把本栏事实挪到其它栏 | 核心对象及组归属持续硬检查，只删除明确批准的 should，不按列数直接删对象 |
| 新类型或 Recipe 改动影响旧业务 | 静态请求级准入、独立增量合同及旧路径回归；不修改旧 TextBlock、SummaryList 默认行为 |

三类组件可以分批开发、分别做单元回归，但首期完整交付必须同时包含它们的合同、案例、容量检查和最终验收。
ComparisonGroup 的视觉参数或资源不齐时保持受控联调，不以正文／列表已经通过声称首期全部完成。
参考预算与真机渲染分别验收；实际宿主几何未知时仍不能承诺任意尺寸无折行或裁切。

## 11. 结果、产物和编辑

| 情况 | 结果语义 |
| --- | --- |
| 去重、标签分层和标点调整，展示内容未减少 | `success` |
| omittedContents 记录的实际范围选择或内容精简，核心用途成立 | `degraded`，说明空间限制和取舍 |
| 可选补充实际省略、或 Plan/DSL 使用显式省略号，核心仍成立 | `degraded`，记录具体省略并说明 |
| 核心或必须原文的内容最终缺失、改错、无法容纳 | `failed`，不保存成功产物 |
| 用户事实不足或有关键歧义 | 主 Agent 生成前澄清，不伪造微服务状态 |
| 动态需求不可支持 | 沿原不支持流程，不自动制作静态替代 |

`ResponsePlanner` 的取舍反馈来自 omittedContents、最终确实缺失的可选事实及真实尾部截短，
不能把所有未选入 Plan 的来源材料列为 omitted_requirements，导致每张摘要卡都返回 degraded。
不为创建流程新增仅编辑使用的 `needs_clarification` 语义。

产物继续保存无动态绑定的运行配置、最终 genui 和实际 Compact 源。来源引用与精简计划通过现有
Trace 和已有诊断承载位置记录，不新增端侧必读块；不伪造数据能力、数据绑定或刷新计划。
现有 artifact 的 generationplan 保存候选继承信息，不等于 submit_card_plan 的展示计划；
不把该块改作静态 Plan。Trace 记录接受计划、分组映射和最终复核结果，保持已有块的解析含义。
来源与正文的记录沿用现有脱敏、访问和保留策略，不增加长期保存个人记忆原文的要求。

静态卡片可继续接受现有支持的视觉编辑。更换场次、修改行程、追加备忘等是内容更新，
首期不放宽原编辑保护；用户可以按新内容重新创建。正文更新另行设计来源继承、重新摘要和内容校验。

## 12. 开关、观测与回滚

`enable_static_content_generation_policy` 当前默认 true；关闭可退出专项策略。所有进程读取配置快照，
同一次请求各阶段使用已解析策略，不因运行中开关变化切换路线。

关闭开关时保持已有请求行为；这表示退出本专项策略，不表示历史静态卡片被禁止。
启用前检查静态提示词、工具合同、校验器、案例和已开放 UX 资源是否齐备，缺失则明确配置失败，
不静默退成无静态保护的生成。本期视觉参数或实现资源尚未齐备时仅做受控联调，不作为正式启用依据。

Trace 追加策略版本、模式和选择原因、输入与展示长度、来源引用数、受保护项数、
分组及条目映射、Plan 次数、质量修复次数、实际省略、采用的组件与布局版本、
多行容量不确定原因、模板跳过原因和失败阶段；不在普通指标标签中写正文、城市或个人信息。
精简率只能说明长度变化，不能作为事实正确或卡片美观的替代指标。

回滚关闭专项开关；已经安装的标准产物继续由端侧显示，不需要迁移或重新生成。
旧路径的提示词、规则严重程度和既有开关应有回归对照，不能依赖关闭新开关后再修改全局配置恢复。

- 静态比较保留ASCII词元边界；排版标点允许变化，独立数字不能跨字段拼接，原文约束不变。
- guided运行匹配与静态编译共用flow/compact间距，试排必须覆盖guided合同。
- 静态SingleLineTitle使用共享header文字行盒（12/16/单行），图标使用登记尺寸；宽度不足报容量错误，
  不接受隐藏裁切。只在静态分支接入，原动态标题和素材准入保持不变。
- omittedContents新模型工具只声明对象项{description,factIndexes}，索引为原info_required中的text引用，
  归一化后保存为内部omissionCandidates。引用项不直接生成降级说明，最终可见覆盖决定实际should遗漏。
  factIndexes为空时声明未入计划的实际输入损失，description保留于omittedContents；历史字符串兼容。
  不对自由文字说明做语义字符串推断，不将可能遗漏误报为实际遗漏。
- ContentBlock.attributes增加可选valueRole:body|value，默认body左对齐，value在合法单行组合时右对齐；
  该元数据不计入可见文字。候选根据Plan显式展示角色填入，长说明不使用右对齐，完整文字不被删改。
- 静态换行共用排版禁则字符集，防止闭标点孤立到行首、开标点留在行尾；数值和单位仍整体换行。
- 验证分别报告误判修复、真实超容量拒绝、显示质量和语义限制；不以全部样本成卡为目标。
