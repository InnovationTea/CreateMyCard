# Compact DSL 校验器重构方案 v1

- 版本：v1
- 日期：2026-09-29
- 状态：评审草案，尚未实施
- 适用范围：微服务侧 Compact DSL 转换前校验及模型修复反馈

本方案采用“先等价拆分校验器，再引入结构化诊断和可配置修复建议，最后优化模型修复反馈”的路线。
目标是让校验规则更容易维护，并让模型清楚知道：哪里出错、违反什么约束、在本次输入和环境下应该如何修改。

本文为重构提案，不替代 `docs/云侧方案设计.md`。实施前先将确认后的设计同步到方案总文档；
如果发现现有代码与方案总文档冲突，单独列出差异并确认依据，不借重构顺带改变规则。

## 1. 重构目标与范围

本次重构覆盖：

- Compact DSL 转换前校验器及其辅助规则。
- 校验结果向生成流水线的传递。
- 根据输入和环境选择修复建议的策略。
- 模型修复提示词和相关测试。
- 方案总文档中的校验与修复约定。

基本原则：

1. 保持现有公开校验入口、通过与失败判定、异常行为、警告级别和模板跳过逻辑。
2. 保持现有生成及重试策略，不在重构中增加重试次数或改变失败处理。
3. 转换器继续负责原有解析和转换职责，本次不重新划分转换器与校验器的边界。
4. 第一阶段保持错误文案、顺序和去重语义，结构化诊断作为后续独立增强。
5. 修复建议不能放宽校验规则，也不能改变用户需求和数据语义。
6. 先更新 `docs/云侧方案设计.md`，再同步代码、配置、提示词和测试，不向 `AGENTS.md` 复制方案细节。

## 2. 校验规则分类与模块结构

保留 `compact_dsl_validator.py` 作为兼容入口，在同级新增 `compact_validation/`：

```text
card_validation/
├── compact_dsl_validator.py       # 保留公开接口
└── compact_validation/
    ├── api.py                    # 校验流程编排
    ├── context.py                # 公共校验上下文
    ├── diagnostics.py            # 诊断类型、汇总及兼容输出
    ├── structure.py              # 组件契约、父子结构、空容器
    ├── bindings.py               # 表达式与路径绑定
    ├── data.py                   # 数据范围、首帧类型、未使用数据告警
    ├── assets.py                 # 素材来源与染色策略
    ├── actions.py                # 事件及动作组件约束
    ├── semantics.py              # 单位、布尔展示、指标与文案语义
    ├── typography.py             # 主数值字号与文字压力
    ├── geometry.py               # 高度预算及尺寸计算
    ├── layouts/
    │   ├── routing.py            # 布局适用条件与规则调度
    │   ├── two_by_two.py         # 2×2 布局规则
    │   ├── two_by_four.py        # 2×4 布局规则
    │   └── fusion.py             # 融球组合规则
    └── repair_guidance/
        ├── context.py            # 修复策略使用的上下文
        ├── resolver.py           # 策略匹配与选择
        ├── renderer.py           # 修复建议模板渲染
        └── config.py             # 配置加载与合法性检查
```

配置放入现有校验规则目录：

```text
cloud/data/validator_rules/
└── compact/
    └── repair_hints/
        ├── schema.json
        ├── structure.yaml
        ├── bindings.yaml
        ├── semantics.yaml
        ├── typography.yaml
        └── layout.yaml
```

分类依据是规则职责，不以文件行数机械切分。某个布局文件仍包含多个独立规则簇时，再按具体布局拆分。

现有双动作校验器先保留实现，由编排层接入。公共函数放入对应职责模块，避免建立不断膨胀的通用工具文件。

## 3. 公共上下文与执行流程

公共上下文统一保存：

| 内容 | 用途 |
|---|---|
| 原始 DSL、解析后的组件行和数据行 | 提供校验对象和源码定位基础 |
| 组件索引、父子关系 | 避免各规则重复构建和遍历 |
| 全部绑定路径、可见内容绑定路径 | 区分事件参数与展示内容 |
| 首帧数据及字段约束 | 校验路径、类型和展示语义 |
| 尺寸、布局和本次生成约束 | 判断规则适用范围 |
| 可可靠获得的源行号、组件及属性位置 | 定位模型需要修改的位置 |

上下文只服务于校验，不修改输入 DSL。构建索引前保留原始记录，避免重复组件 ID 被字典覆盖而丢失错误。

模块依赖保持单向：

```text
兼容入口
    → 校验流程编排
        → 分类规则
            → 公共上下文与诊断类型
        → 修复建议策略解析
            → 配置与模板
```

分类规则不调用入口，也不互相串联。跨类别的执行依赖由编排层管理。

首次拆分保留原有执行顺序。后续再根据明确依赖，减少非法结构、绑定或类型引发的无效下游诊断；
不因某一类别失败就跳过全部其他检查。

## 4. 结构化诊断设计

每条诊断应回答：哪里出错、为什么出错、应满足什么约束、当前情况下怎么改。

建议采用具名诊断对象，包含以下信息：

| 字段 | 用途 |
|---|---|
| `code` | 稳定的规则错误码 |
| `category` | 结构、绑定、语义、布局等类别 |
| `severity` | 保持原有 error 或 warning 语义 |
| `message` | 描述违规事实 |
| `componentId` | 原始 DSL 中的组件 |
| `propertyPath` | 组件内部的属性位置 |
| `sourceLine` | 可可靠取得时提供源行号 |
| `actual` | 本次校验得到的实际值 |
| `expected` | 规则要求的合法范围或约束 |
| `fixHint` | 根据上下文生成的修复建议 |

示例：

```json
{
  "code": "COMPACT_LAYOUT_HEIGHT_OVERFLOW",
  "category": "layout",
  "severity": "error",
  "componentId": "content_area",
  "message": "子节点最小占用高度超过容器可用高度",
  "actual": {
    "minimumRequiredHeight": 142
  },
  "expected": {
    "maximumHeight": 126
  },
  "fixHint": "至少释放16vp高度。当前可调整间距足以释放所需高度，优先缩减间距，保留必要内容和当前字号。"
}
```

诊断约定：

- 错误码与规则含义绑定，不随文案改变。
- 不通过匹配现有报错字符串推断错误码、位置和修复方式。
- 不确定的实际值或位置保持缺省，不填入伪值。
- 原始 Compact DSL 是行式格式，不将转换后的 A2UI 路径冒充源码位置。
- 校验模块不反向依赖生成流水线，由适配层转换为现有质量问题结构。
- 初期保留异常的字符串错误列表和原有异常文本，同时新增结构化诊断集合。

## 5. 可配置的修复建议策略

`fixHint` 不采用“一个错误码对应一条固定文案”的方式，而采用“一条校验规则＋默认建议＋多个条件变体”。

三个职责分开：

```text
校验规则：判断违规，记录实际值和约束
建议策略：结合上下文，选择适用的修复方向
建议渲染：填入组件、尺寸差值和合法范围
```

规则的判定逻辑仍由 Python 实现。配置负责选择建议和组织文案，不执行任意表达式，不改变校验结果。

### 5.1 修复策略上下文

只纳入会影响修复合法性的输入和环境信息：

| 维度 | 示例 |
|---|---|
| 卡片约束 | 尺寸、布局类型、允许的组件 |
| 操作模式 | 创建、编辑及明确的编辑保留要求 |
| 协议环境 | 当前协议版本、明确声明的功能支持 |
| 数据语义 | 字段类型、单位规则、格式化字符串 |
| 需求约束 | 明确保留的内容、明确可选或重复的内容 |
| 校验事实 | 高度差值、可调整间距、允许字号档位 |
| 候选范围 | 本次允许的数据、事件和素材 |

上下文必须来自可信的生成约束和确定性计算。不得把用户文本直接当作策略指令，
也不得仅凭组件名称猜测字段是否可删除。

条件未知时不视为成立。例如，无法确定全部内容必须保留，就不能伪造 `all_content_required: true`；
同时，缺少这一信息也不代表可以删除内容。

### 5.2 配置示例

```yaml
version: 1

rules:
  COMPACT_LAYOUT_HEIGHT_OVERFLOW:
    default:
      template: >
        最小占用高度为{required_height}vp，可用高度为{available_height}vp。
        请调整当前容器内的高度、边距或间距，并保留必要内容。

    variants:
      - id: reduce_adjustable_spacing
        priority: 100
        when:
          spacing_can_cover_overflow: true
        template: >
          当前超出{overflow}vp。可调整间距足以释放所需高度，
          优先缩减间距，并保持当前内容和字号。

      - id: preserve_required_content
        priority: 80
        when:
          all_content_required: true
        template: >
          当前超出{overflow}vp，全部内容均需保留。
          请调整为当前尺寸允许的紧凑结构，
          不得通过删除必要内容解决。
```

上述条件由代码计算。例如，`spacing_can_cover_overflow` 必须根据布局允许的最小间距和实际溢出量确定，
不能只根据“存在间距”判断。

同一错误的修复方向可以随上下文变化：

| 本次情况 | 建议方向 |
|---|---|
| 可调整间距足以释放高度 | 优先缩减间距 |
| 主数值允许降低字号 | 按合法字号档位逐级降低，并复查宽高 |
| 所有内容明确要求保留 | 调整为同尺寸允许的紧凑结构 |
| 存在明确重复或可选内容 | 优先删除重复内容，必要时删减可选项 |
| 编辑要求保持布局 | 优先局部调整，无法满足时再考虑允许的结构修改 |

### 5.3 匹配与回退规则

1. 根据错误码找到对应策略集合。
2. 使用受控上下文评估条件。
3. 选择优先级最高的适用变体。
4. 无匹配变体时使用默认建议。
5. 校验模板参数完整性后生成 `fixHint`。

初期每条诊断只选择一个主策略。需要多步修复时，由该策略输出有序步骤，不拼接多个可能矛盾的建议。

配置检查应覆盖：

- 错误码和策略 ID 的合法性、唯一性。
- 条件字段与运算符是否受支持。
- 模板占位符是否有确定来源。
- 默认建议是否存在。
- 可识别的同优先级条件冲突。

运行时若出现无法预先发现的匹配冲突或参数缺失，应记录原因并使用安全的默认建议；
建议生成失败不能吞掉原始校验错误，也不能改变校验结论。

配置随代码发布，第一期不引入远程热更新。

### 5.4 可追踪性

日志记录：

- 校验错误码。
- 命中的策略 ID。
- 配置版本。
- 是否使用默认回退及原因。

不需要记录全部输入或敏感数据。策略 ID 和版本主要用于排障，不必全部传给模型。

## 6. 接入模型修复链路

沿用现有质量问题及修复提示词机制：

```text
解析并建立上下文
    → 分类规则产生诊断事实
    → 策略层生成适用的修复建议
    → 校验异常携带诊断
    → 生成流水线适配为质量问题
    → 修复提示词接收完整诊断
    → 模型输出完整 Compact DSL
    → 重新执行完整校验
```

修复提示词需要明确：

- 根据原始 DSL 的组件和属性定位问题。
- 对照实际值与期望约束理解错误。
- 根据本次 `fixHint` 做最小必要修改。
- 保留未受影响的内容和用户必需信息。
- 修复建议不覆盖协议、能力、素材和业务约束。
- 修改结构后复查父子引用、相邻节点、绑定及尺寸预算。
- 输出修复后的完整 DSL，继续接受完整校验。

建议只有方向而没有唯一答案时，应给模型合法选择空间，不强制复制固定模板。

## 7. 错误依赖与重复诊断

首次接入结构化诊断时保持原有错误数量和顺序，避免同时改变行为。

后续再优化：

- 以组件、绑定或父容器组织相关诊断。
- 优先呈现结构、绑定和类型等上游问题。
- 只有明确证明下游诊断依赖无效前提时，才抑制该诊断。
- 保留独立错误，不根据文本相似度随意合并。
- 修复后重新运行全部校验，确认上游问题和下游问题均已消失。

例如，某字段类型已经错误，则依赖正确字段类型才能成立的主数值排版建议可能没有意义；
但同一组件存在非法素材时，该错误仍应保留。

## 8. 分阶段实施

| 阶段 | 工作内容 | 完成标准 |
|---|---|---|
| 一：建立基线 | 盘点规则、辅助函数、调用方、配置和测试；补充方案文档 | 明确模块归属、兼容边界和当前行为 |
| 二：等价拆分 | 提取分类模块和公共上下文，保留兼容入口 | 判定、文案、顺序、去重和警告行为一致 |
| 三：结构化诊断 | 引入诊断类型与稳定错误码，逐类迁移 | 不依赖报错字符串反向解释规则 |
| 四：建议策略 | 实现上下文、条件匹配、模板渲染、回退及配置检查 | 同一规则可按不同条件生成正确建议 |
| 五：贯通修复 | 流水线传递诊断，更新提示词及独立修复入口 | 模型实际收到定位、约束和建议 |
| 六：反馈优化 | 基于固定案例处理重复诊断及明确依赖 | 根因更清晰，且不遗漏独立错误 |

诊断和策略优先覆盖：

1. 绑定与数据类型。
2. 单位和展示语义。
3. 高度预算。
4. 主数值排版。
5. 各类特定布局。

各阶段形成独立、可审查的变更。等价拆分阶段不混入规则放宽、收紧或视觉参数调整。

## 9. 验证计划

| 验证层 | 主要检查 |
|---|---|
| 行为等价 | 正常和违规样例的判定、错误顺序、去重、警告及异常表现 |
| 诊断正确 | 错误码、组件位置、属性位置、实际值和期望约束 |
| 策略正确 | 不同输入和环境下的选择、优先级、未知条件及默认回退 |
| 配置正确 | Schema、错误码、策略 ID、条件字段、模板参数及冲突 |
| 链路完整 | 诊断字段是否进入实际修复请求，是否在中间环节丢失 |
| 修复回归 | 修复产物重新执行全部校验，避免引入新违规 |

回归范围包括 Compact 校验、转换、双动作、主数值排版、Few-shot、修复提示词、相关生成流水线和模板调用链路。

每阶段执行：

- 修改文件的 Ruff 检查。
- 与行为直接相关的单元测试。
- 对应配置检查。
- `git diff --check`。
- 按影响范围补充链路回归。

模型修复效果使用固定案例集比较：

- 一次修复通过率。
- 同类错误重复出现的比例。
- 修复后新增违规的比例。
- 必需内容和语义的保留情况。

比较时记录模型、生成提示词、策略配置和重试设置。单元测试通过不等于真实模型修复效果已改善。

## 11. 交付与验收标准

重构完成应满足：

- 主入口只承担兼容与编排，规则按职责归属清晰。
- 原有校验行为通过等价回归，任何有意变更单独说明。
- 已迁移规则具有稳定错误码和可靠的错误定位。
- `fixHint` 能根据明确的输入、环境和校验事实选择不同策略。
- 配置不改变校验判定，建议不会绕过协议或业务约束。
- 诊断完整进入模型修复输入，修复结果重新接受完整校验。
- 配置错误、策略冲突或参数缺失不会丢失原始校验结果。
- 交付报告逐项列出实际修改文件、执行的检查、测试数量及通过或失败结果。

实施中如果发现现有代码与方案总文档冲突，单独列出差异并确认依据，不借此次重构顺带改变规则。
