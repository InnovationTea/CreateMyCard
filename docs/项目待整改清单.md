# 项目待整改清单

登记日期：2026-10-29。状态：待实施。

本清单汇总项目架构阅读、旧路线核查和目录归类讨论中的整改建议，目标是降低维护成本，并尽量保持现有功能、协议和运行行为。当前仅登记工作项，不代表已经批准退出兼容路线，也不代表已完成任何代码整改。

云侧边界和业务规则以[云侧方案设计](云侧方案设计.md)为准，开发和验证遵循[AGENTS.md](../AGENTS.md)。本清单不替代方案，不复制 CodeCheck 规则；涉及既有方案变化的事项，实施前先确认范围并同步对应方案。

## 优先级与执行边界

| 优先级 | 含义 | 实施原则 |
| --- | --- | --- |
| P1 | 先消除误导、补齐回归保障和迁移前置条件 | 优先选择不改变业务行为的整理 |

所有条目当前均未实施。优先级表示建议处理顺序，不代表紧急故障等级；未发现需要在本清单中列为 P0 的已确认阻断问题。

目录迁移首先保持文件名、公开接口、调用顺序、异常、诊断和重试预算不变。删除旧路线属于支持范围调整，不能仅以“默认关闭”或“当前主链路不用”为依据执行。

## P2 目录归类与旧路线解耦

### P2-01 将 services 按职责归类

登记时，[services 根层](../widget_service/cloud/services/)有 91 个 Python 文件。建议先建立职责目录，保留原文件名；根层可以阶段性保留稳定入口和必要兼容转发，不要求一次清空。

| 建议目录 | 主要归入范围 | 约束 |
| --- | --- | --- |
| `generation/` | 生成服务、流水线、预检、规格构造、关联字段补齐、生成重试、结果组织及生成 Trace | 不承接组件或校验规则 |
| `capabilities/` | 能力注册、设备裁决、IDS 客户端、事件匹配 | 保持能力与设备边界 |
| `compact/` | 信息计划、动作实例、组件展开、转换、布局合同、重组和修复策略 | 不按文件名前缀机械迁移 |
| `themes/` | 后置主题、图片准入与匹配、样式角色、融球及图片扩展 | 保持共享主题配置和前景保护 |
| `editing/` | 编辑服务、编辑合同、提示词、请求继承归一化及编辑公共辅助函数 | 编辑专项校验仍留在校验包 |
| `static_content/` | 静态内容规划、展示、组件、文字容量及内容策略 | 不扩大到动态或编辑路线 |
| `artifacts/` | 完整产物保存、来源仓库、资源地址映射 | 不改变产物和来源校验语义 |
| `prompts/` | 提示词组装、源加载、案例选择与案例组装 | 保持加载内容、顺序和缓存语义 |
| `usage/` | 每日次数 API 与限制逻辑 | 保持查询和记录时点 |
| `card_validation/` | 保留现有语法、语义、布局及编辑校验分类 | 遵循既有专项方案 |
| `template_generation/` | 保留现有模板边界与内部资源 | 不反向接管公共生成流程 |

- [ ] 逐文件登记目标目录、调用方、资源路径和迁移理由。
- [ ] 优先迁移主题、次数管理、产物管理，再迁移能力、编辑和静态内容，最后迁移 Compact 与生成编排。
- [ ] 协议注册、业务归属分析等跨模块文件单独复核，不能作为难分类文件统一塞入 `utils/` 或 `common/`。
- [ ] 参数结构恢复归接口输入处理，接口整轮重试归生成编排，校验判定继续归校验模块。
- [ ] 同步生产导入、调试工具、脚本、测试替换路径以及方案中的代码导航。

验收要求：公开接口、资源加载、序列化产物、异常及诊断顺序保持一致；无新增导入环；兼容导入与测试替换生效。简单重导出不能自动证明模块身份、全局状态及 monkeypatch 行为等价。

Compact 内部首轮可以保持平铺，后续再按规划、组件、布局和修复分组。已有 `card_validation/` 不重新整体分类；新增或移动校验逻辑仍须同步专项规则归属清单。

- [ ] 新编辑及编辑校验改用公共模块，验证已解除对旧处理器文件的依赖。
- [ ] 核对旧字段补丁编辑是否仍承担部署回滚需求；退出结论确定后，先同步编辑方案，再移除旧处理器、专属提示词、开关及专属测试。

## P3 职责拆分与次要目录整理

### P3-01 拆分模板编译器

[模板编译器](../widget_service/cloud/services/template_generation/engine/cardplan/compiler.py)约一万行，混合了模板求值、业务组件展开、动作转换、主题应用、布局预算和序列化。

- [ ] 保留编译入口，先提取依赖少的参数求值和序列化，再逐个提取业务组件展开。
- [ ] 每批只迁移一个职责，核对内部私有函数调用和测试引用。

验收要求：固定输入、主题和模型返回，对比组件树、绑定、动作、节点标识、诊断与异常。不得同时改变编译算法或容量规则。

### P3-02 拆分生成总入口

[生成服务](../widget_service/cloud/services/widget_generation_service.py)的主要生成方法接近两千行，通过多个嵌套函数和 `nonlocal` 共享计划、消息历史、源格式、修复及校验状态。

- [ ] 先用具名状态对象显式表达共享状态，再逐步提取规划、源生成、质量修复和处理阶段。
- [ ] 原服务继续负责串联阶段，不同时调整重试、回退及事实省略政策。

验收要求：固定模型返回序列，逐项对比消息历史、模型调用次数、状态转换、诊断、成功结果和失败结果；保存失败不能因重构变成重新生成。

### P3-03 缩小接口路由文件职责

[路由文件](../widget_service/cloud/api/routes.py)同时负责请求包络、参数恢复、错误反馈、响应帧、心跳、次数检查和调用分发。

- [ ] 按请求归一化、响应与指令、WebSocket 生命周期提取模块，路由保留注册和分发。
- [ ] 保持业务参数恢复与传输包络解析边界，不把业务校验重新塞入传输模块。

验收要求：接口路径、关联信息、响应帧顺序、错误反馈、取消及心跳行为不变，覆盖异常参数和连接中断场景。

### P3-04 整理调试平台批跑模块

[批跑模块](../debug_tools/batch_testing/)已具备独立边界，可进一步区分任务执行、Trace 分析、质量评估和后处理调度。

- [ ] 先迁移模块归属，必要时再拆分后处理管理器；插件实现继续留在 `postprocess_plugins/`。
- [ ] 保留现有兼容入口，避免重复实现已迁入插件目录的画廊和设备截图能力。
- [ ] 同步调试平台技术方案和运行规范。

验收要求：任务和队列持久化、单批次调度、取消、进程回收、Trace 关联及插件结果历史保持一致；不改变历史数据格式。

## 暂不调整或删除的范围

- `models/`、`config/`、`core/` 规模尚可，暂不为目录对称继续细分。
- `core/errors.py` 与 `errors/` 分别承担业务错误枚举和框架异常体系，不能仅因名称相似合并。
- 调试前端现有 `routes/`、`components/` 基本合理，暂不整体改为另一套目录体系。
- 能力、协议及校验配置继续保留在当前 `data/` 分类中，迁移代码不连带搬动资源目录。
- `render/` 仍承担独立预览和运行时同步来源，不能当作与调试渲染器重复的无用目录删除。
- `protocol_profiles/widget-edit/` 仍供单步新建兜底使用，部分提示词在模块导入时读取；关闭运行开关不代表可删除资源。
- `compact-dsl-v1/*.md` 仍被协议回归测试读取；Fusion 的 `prompt_source/edit.md` 仍在提示词加载清单内。
- `widget_service/docs/*system_prompt.txt` 仍被 `.env.example` 引用，配置层保留文件加载支持。
