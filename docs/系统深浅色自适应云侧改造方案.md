# 系统深浅色自适应云侧改造方案

> 状态：设计草案，尚未实现。
>
> 本文不属于当前生效的在线链路协议。当前行为仍以 `docs/云侧方案设计.md` 为准；进入实现前，应先确认端侧 Form Catalog 能力，再同步主方案、代码、协议 profile、Compact DSL schema、校验规则、测试和灰度配置。

本文面向第三个微服务工具 `generateWidgetCardCompactDsl`，设计一份 artifact 随系统 light/dark 模式自动切换的完整云侧改造。规范依据为 [A2UI 扩展组件默认深浅色](https://gitcode.com/GenerativeUI/Docs/blob/main/concepts/extension-color-mode.md)。

## 系统深浅色自适应云侧改造

### 目标与非目标

本改造只作用于第三个微服务工具 `generateWidgetCardCompactDsl` 的生成与编辑链路。目标是在端侧能力满足时生成一份同时支持浅色和深色的 artifact；系统色彩模式变化后，由 A2UI 运行时重新求值或使用组件默认色完成切换，不重新请求云侧、不重新生成 artifact，也不维护浅色和深色两份 CardSpec。

本改造不改变数据能力裁决、权限门禁、CardSpec 数据绑定、事件候选、素材候选和生成工具内部向端侧交付 artifact URL 的规则；不在主 Agent 增加颜色协议知识；不通过 `createSurface.theme`、外层 ArkUI `WithTheme` 或运行时上传系统模式实现切换。

规范依据：[A2UI 扩展组件默认深浅色](https://gitcode.com/GenerativeUI/Docs/blob/main/concepts/extension-color-mode.md)。实现时必须锁定审核过的文档版本或 commit，不能只依赖会随主分支变化的网页内容。

A2UI 官方“扩展组件默认深浅色”能力从 API Version 20 起提供，并要求启用扩展 Catalog。其颜色优先级为：

1. DSL 显式颜色优先。
2. DSL 未设置颜色时，组件使用当前 light/dark 模式的默认颜色。
3. 显式颜色需要跟随模式变化时，通过 `$__colorMode` 表达式返回两组颜色。

当前 Form 子协议仍使用 `ohos.a2ui.extended.catalog.form`，且现有 profile 明确排除了 `$__colorMode`。因此正式开发前必须由端侧完成兼容性 PoC，确认 Form Catalog 是否已经具备以下能力：

- Surface 能收到系统 light/dark 变化并触发重渲染。
- 未显式设置的扩展组件颜色可以自动切换。
- 允许动态颜色字段读取 `$__colorMode`。
- 卡片重新进入前台、重新添加和系统重启后能恢复正确模式。

若现有 Form Catalog 不具备上述能力，端侧必须先发布支持该能力的 Form Catalog/profile 版本。云侧不得自行把 `catalogId` 改为通用 `ohos.a2ui.extended.catalog`，避免绕过 Form 的组件、事件、尺寸和生命周期约束。

### 总体链路

```text
小模型侧版本记录或服务灰度配置
 -> 选择 legacy Form profile 或 color-mode Form profile
 -> PromptBuilder 注入颜色模式策略和 Compact DSL Token 约束
 -> A2UI 模型生成 Compact DSL，不直接生成 $__colorMode 表达式
 -> CompactDslCompiler 校验并解析语义颜色 Token
 -> 按 profile 将 Token 编译为“省略颜色 / 固定颜色 / $__colorMode 表达式”
 -> CompactDslValidator 校验 Compact DSL 与 Token
 -> ArtifactValidator 校验最终 A2UI DSL、两种模式对比度和 artifact 元数据
 -> 上传一份 artifact
 -> 端侧随系统模式重渲染同一份 DSL
```

### 第三个工具契约

`generateWidgetCardCompactDsl` 的主 Agent 可见入参和出参保持不变，不新增 `colorMode`、`isDarkMode`、`theme`、`lightColors` 或 `darkColors`：

- 系统当前模式是端侧运行时状态，不属于生成请求输入。
- 同一 artifact 必须同时包含两种模式的行为，不能按调用时模式固化。
- 是否启用能力由 `protocolProfileId` 和服务灰度配置决定，遵循现有 profile 选择边界。
- 用户明确要求“始终深色”或“始终浅色”时，由 `userQuery` 表达固定视觉意图，不新增协议字段；未明确指定时默认跟随系统。

主 Agent 不选择颜色 Token、不构造深浅色值、不传 `$__colorMode`，也不向用户暴露 profile、Token 或端侧模式字段。

微服务内部由 `ColorModePolicyResolver` 在调用 A2UI 模型前产出受控策略：

```text
system          默认策略，生成随系统切换的卡片
system-required 用户明确要求必须跟随系统；profile 不支持时返回 unsupported
fixed-light     用户明确要求始终使用浅色
fixed-dark      用户明确要求始终使用深色
legacy          端侧或灰度配置不支持颜色模式，且用户未把系统跟随声明为硬要求
```

解析优先使用明确的用户措辞和服务默认值；无法确定时使用 `system`，不向用户追问。解析结果只进入协议 profile 摘要、Prompt、编译器和 artifact `meta`，不进入 CardSpec，也不改变数据权限流程。

### 协议 profile 与兼容性

新增独立的颜色模式 profile，例如 `form-v0.9-color-mode-v1`；现有 profile 继续作为 legacy profile。新 profile 至少记录：

```json
{
  "supportsSystemColorMode": true,
  "minimumApiVersion": 20,
  "catalogId": "由端侧 PoC 确认的 Form Catalog ID",
  "systemColorModeVariable": "$__colorMode",
  "systemColorModeValues": ["light", "dark"],
  "colorTokenVersion": "color-token-v1",
  "defaultColorTableVersion": "a2ui-api20-v1",
  "modeAwareColorFields": {}
}
```

其中 `modeAwareColorFields` 是按组件和字段维护的动态颜色白名单，只允许协议 schema 明确声明可使用 Expression 的颜色属性。profile 不支持时，validator 继续拒绝 `$__colorMode`；不得在所有 profile 中全局移除禁用项。

profile 选择仍由小模型侧版本记录或服务配置完成，微服务不根据 ROM/App 字符串自行猜测。灰度配置至少包含：

```text
enable_form_color_mode_v1
color_mode_rollout_allowlist
color_mode_default_policy = system | legacy
enable_legacy_artifact_color_mode_migration
```

旧端侧或未命中灰度的请求继续使用 legacy profile，不输出 `$__colorMode`。这属于版本兼容路径，不记为 `degraded`。若用户明确要求必须跟随系统，而当前 profile 不支持，则返回 `unsupported` 且不生成固定主题替代品。

### Compact DSL 颜色模型

Compact DSL 新增版本化的语义颜色 Token。模型在组件样式中只引用 Token，不直接拼接 A2UI 表达式。推荐结构：

```json
{
  "designTokens": {
    "colors": {
      "surface": {
        "light": "#FFF7F7F7",
        "dark": "#FF1C1C1E"
      },
      "onSurface": {
        "light": "#E5000000",
        "dark": "#E5FFFFFF"
      },
      "accent": {
        "light": "#FF0A59F7",
        "dark": "#FF317AF7"
      }
    }
  },
  "components": [
    {
      "id": "root",
      "component": "Column",
      "styles": {
        "backgroundColor": {"token": "surface"}
      }
    }
  ]
}
```

Token 使用稳定语义名，第一版只开放：

```text
surface
surfaceVariant
onSurface
onSurfaceSecondary
outline
accent
onAccent
success
warning
error
```

每个 Token 必须同时提供 `light` 和 `dark`，颜色格式只允许 `#RRGGBB` 或 `#AARRGGBB`。禁止模型创建组件 ID 绑定型、业务数据型或任意字符串型 Token，避免同义 Token 泛滥和跨模式遗漏。

颜色生成遵循以下优先级：

1. 组件默认色满足语义和对比度时，Compact DSL 省略该颜色字段，编译后继续省略。
2. 需要跟随系统的业务色、根背景色或语义状态色使用双色 Token。
3. 固定品牌色只有在两种背景下都满足可读性时才输出静态颜色。
4. 用户明确要求固定浅色或固定深色时允许输出静态配色，但 artifact `meta` 必须记录固定策略。

根组件默认透明色可能受到桌面背景影响。跟随系统的卡片默认要求 root 使用 `surface` Token；只有产品明确确认透明卡片效果和两种桌面环境可读性后才允许省略 root 背景。

第一版只支持 profile 白名单中的标量颜色字段。渐变色数组、阴影对象、背景图片和 SVG 内部硬编码颜色不自动改写为 `$__colorMode`：

- 需要模式切换的渐变在第一版降级为双色纯色背景。
- 单色可着色 SVG 仅在 `Image.styles.fillColor` 支持动态表达式时使用 Token。
- 不可着色插画必须在两种背景下均可读；第一版不新增 light/dark 双素材协议。
- 固定素材无法满足两种模式时移除非核心素材；若素材是用户声明的核心要求，则返回 `unsupported`。

### Compact DSL 编译规则

`CompactDslCompiler` 对颜色做确定性编译，不让模型直接决定最终表达式：

```text
样式字段缺失
 -> 最终 DSL 同样省略，使用组件默认深浅色

样式值为静态颜色
 -> 原样输出，但执行双模式对比度校验

样式值为颜色 Token 且 light == dark
 -> 输出一个静态颜色

样式值为颜色 Token 且 light != dark
 -> 输出 {{ $__colorMode == 'dark' ? '<dark>' : '<light>' }}
```

编译器只允许上述标准三元表达式，不接受 Compact DSL 携带任意 `$__colorMode`、任意系统变量或手写表达式。输出示例：

```json
{
  "styles": {
    "backgroundColor": "{{ $__colorMode == 'dark' ? '#FF1C1C1E' : '#FFF7F7F7' }}"
  }
}
```

表达式只能出现在当前 profile `modeAwareColorFields` 允许的字段中。`theme` 继续禁止，`$__widthBreakpoint` 和 `$context` 继续禁止，结构字段、事件 call、CardSpec 和 DataModel 写入路径均不得引用 `$__colorMode`。

### Prompt 与模型职责

首次生成和编辑系统提示词都需要加入相同的颜色模式章节，规则由文件化 prompt 配置维护：

- 未指定固定主题时按“跟随系统”生成。
- 优先省略可使用扩展组件默认色的颜色字段。
- 必须显式控制时只使用已声明语义 Token。
- 不直接输出 `$__colorMode`、`theme`、未声明 Token 或两套组件树。
- light/dark 只改变颜色，不改变组件、文案、数据绑定、事件、尺寸和 children 关系。
- 固定品牌色必须搭配两种模式下均可读的前景/背景。
- 不使用固定白字配透明或浅色背景，也不使用固定黑字配透明或深色背景。

颜色模式策略放入协议 profile 摘要和美观规则，不扩展 TaskSpec 顶层字段。A2UI 模型仍只负责 Compact DSL；最终 `$__colorMode` 表达式由编译器生成。

### 校验与错误处理

颜色模式校验分三层执行：

1. `CompactDslValidator` 校验 Token 名称、结构、颜色格式、完整 light/dark 色对和引用存在性。
2. `CompactDslCompiler` 校验目标字段是否进入 `modeAwareColorFields`，并生成唯一规范表达式。
3. `ArtifactValidator` 校验最终 DSL、profile、Catalog、系统变量、默认色解析和双模式对比度。

最终 artifact 必须分别构造 light/dark 有效颜色视图。显式透明度先与有效背景做 Alpha 合成，再检查：

- 普通文本对比度不低于 `4.5:1`。
- 大号文本对比度不低于 `3:1`。
- 关键图标、分割线、控件状态和必要热区边界对比度不低于 `3:1`。
- 有效背景无法静态确定时，不允许依赖固定前景色通过校验。
- 省略颜色字段时，从 profile 的 `defaultColorTableVersion` 读取该组件在两种模式下的默认色。

以下错误属于阻断型硬错误，最多修复重试 1 次；重试后仍失败时返回 `failed`，不得上传 artifact：

```text
COLOR_MODE_PROFILE_UNSUPPORTED
COLOR_MODE_CATALOG_UNSUPPORTED
COLOR_TOKEN_INVALID
COLOR_TOKEN_REFERENCE_NOT_FOUND
COLOR_MODE_FIELD_UNSUPPORTED
COLOR_MODE_EXPRESSION_INVALID
COLOR_CONTRAST_LIGHT_FAILED
COLOR_CONTRAST_DARK_FAILED
COLOR_MODE_ASSET_INCOMPATIBLE
COLOR_MODE_MIGRATION_UNSUPPORTED
```

服务配置、profile 与端侧 Catalog 声明不一致属于服务异常，使用 `failed`；用户明确要求必须跟随系统但设备版本不支持属于能力边界，使用 `unsupported`。内部错误码只写日志和排障结果，不向用户展示。

颜色模式硬错误不适用“校验失败仅观测、仍上传最后产物”的旧策略。其它已有非阻断质量校验仍按原开关处理。

### Artifact 与多轮编辑

CardSpec 不新增颜色字段。颜色策略只存在于 DSL 和 artifact `meta`：

```json
{
  "colorModePolicy": "system",
  "colorModeProfileVersion": "form-v0.9-color-mode-v1",
  "colorTokenVersion": "color-token-v1",
  "defaultColorTableVersion": "a2ui-api20-v1",
  "modeAwareFieldCount": 6,
  "defaultColorFieldCount": 4,
  "fixedColorFieldCount": 2,
  "legacyArtifactMigrated": false
}
```

多轮编辑规则：

- 新 profile 生成的 artifact 默认继承 `colorModePolicy` 和 Token 版本。
- 纯布局、文案、尺寸或数据参数编辑不得静默改为固定主题。
- 用户明确要求固定浅色/深色时允许把策略改为固定，并生成新的 artifact。
- legacy artifact 默认继续使用来源 profile，避免一次普通视觉编辑引发全卡配色迁移。
- 只有 `enable_legacy_artifact_color_mode_migration` 开启且来源 artifact 结构完整时，才允许完整重编译为颜色模式 profile。
- 迁移必须重新执行 Compact DSL 校验、双模式对比度校验和端侧兼容校验；失败时保留来源 artifact，不覆盖、不回退为部分迁移。

### 云侧实施改动清单

实现阶段必须同步修改以下模块和资产：

| 模块 | 必须改动 |
| --- | --- |
| `A2UIProtocolRegistry` | 注册颜色模式 profile、Catalog 能力、动态颜色字段白名单、API 最低版本和默认色表版本 |
| `ColorModePolicyResolver` | 将用户视觉意图、服务默认策略和 profile 支持度裁决为受控内部策略 |
| Compact DSL schema | 增加 `designTokens.colors` 和颜色 Token 引用结构，保持 schema 版本化 |
| `PromptBuilder` | 向首次生成和编辑 prompt 注入默认色优先、语义 Token、固定主题覆盖和素材限制 |
| `CompactDslCompiler` | 解析 Token，确定性生成省略字段、静态色或规范 `$__colorMode` 表达式 |
| `CompactDslValidator` | 校验 Token 名称、色对、引用、格式和字段目标 |
| `ArtifactValidator` | 加载 profile 默认色表，构造 light/dark 有效颜色视图并执行协议与对比度硬校验 |
| `RetryController` | 将 `COLOR_MODE_*` 纳入最多 1 次的可修复重试，重试失败阻断上传 |
| `ArtifactStore` | 在 `meta` 写入颜色模式版本、计数、迁移和校验摘要 |
| 配置中心 | 增加颜色模式总开关、灰度名单、默认策略和 legacy 迁移开关 |
| 测试资产 | 增加 Compact DSL schema 样例、编译 golden、非法表达式样例和 light/dark 渲染基线 |

实现提交必须包含：profile 配置、Compact DSL schema、默认色映射、prompt 版本、校验规则、错误码、单元测试、集成测试和灰度配置；不得只提交 prompt 或模型示例。

### 灰度、回滚与发布门槛

发布分四阶段：

1. **端侧 PoC**：确认 Form Catalog、系统切换和 `$__colorMode` 支持，冻结 Catalog/profile 契约。
2. **云侧影子校验**：继续返回 legacy artifact，同时生成但不上传颜色模式候选，记录双模式校验结果。
3. **小流量新建灰度**：只对首次生成启用，新旧 profile 按版本记录分流。
4. **编辑与迁移灰度**：先支持新 artifact 连续编辑，再单独开放 legacy 迁移。

任一阶段可关闭 `enable_form_color_mode_v1` 回退到 legacy profile。回滚不修改第三个工具 schema，不影响已生成的模式感知 artifact；端侧仍按 artifact 自身 profile 渲染。禁止通过删除 `$__colorMode` 分支或把深色值替换成浅色值执行在线降级。

正式放量门槛：

- 2x2/2x4 目标组件集在 light/dark 下全部可渲染。
- 系统切换无需云侧请求即可完成。
- 双模式协议硬校验通过率达到发布阈值。
- 深色和浅色截图人工验收均无文字不可读、背景穿透、状态色误导或素材消失。
- legacy 请求成功率、P95 和 artifact 大小无显著回归。

## 验收测试方案

### 单元测试

- `ColorModePolicyResolver` 覆盖默认 system、强制 system、固定浅色、固定深色和 legacy 回退。
- Compact DSL schema 接受完整语义 Token，拒绝未知 Token、缺少 light/dark、非法颜色格式和悬空引用。
- 编译器分别覆盖颜色字段省略、静态颜色、light/dark 相同和 light/dark 不同四条路径。
- legacy profile 继续拒绝 `$__colorMode`；颜色模式 profile 只在动态颜色字段白名单中接受规范表达式。
- 继续拒绝 `theme`、`$__widthBreakpoint`、`$context`、结构字段表达式和手写非规范三元表达式。
- 默认色映射按 `defaultColorTableVersion` 加载，找不到版本时阻断生成。
- Alpha 颜色先完成背景合成，再分别计算 light/dark 对比度。
- 普通文本、大号文本和关键控件分别执行 4.5:1、3:1 和 3:1 阈值。
- 固定渐变、阴影和不可着色素材无法兼容两种模式时，按核心程度移除或返回 unsupported。

### 集成测试

- 2x2、2x4 各生成至少一张纯默认色卡片和一张双色 Token 卡片。
- 天气、日程、设备状态、静态入口和带按钮卡片均通过双模式校验。
- 同一 artifact 在 light → dark → light 切换中不请求云侧，不改变 CardSpec、DataModel 或事件状态。
- 卡片前后台切换、重新添加和系统重启后恢复正确模式。
- 用户明确要求固定浅色或固定深色时生成固定策略 artifact。
- 用户明确要求必须跟随系统但当前 profile 不支持时返回 unsupported，不生成固定主题替代品。
- 未命中灰度或低版本设备继续使用 legacy profile，不记为 degraded。
- 新颜色模式 artifact 连续编辑时继承原策略和 Token 版本。
- legacy artifact 在迁移开关关闭时不被静默升级；迁移失败时保留来源 artifact。
- OBS 上传失败、编译失败、双模式硬校验失败均不返回 artifactUrl。

### 渲染验收

- 对 Text、Divider、Progress、Button、Checkbox、Image、Row、Column、List、Stack 建立 light/dark 截图基线。
- 检查文字不可读、透明背景穿透、状态色语义错误、素材消失、边界不可见和模式切换闪烁。
- 真机验证系统切换、手动 `updateThemeMode`、前后台恢复和桌面重载。
- 验收 Catalog 必须是端侧确认支持 Form 生命周期和颜色模式的版本，不以通用扩展 Catalog 替代。

## 日志与监控方案

每次生成或编辑记录：

```text
requestId
protocolProfileId
colorModePolicy
colorModeProfileVersion
colorTokenVersion
defaultColorTableVersion
modeAwareFieldCount
defaultColorFieldCount
fixedColorFieldCount
legacyArtifactMigrated
colorModeFallbackReason
contrastValidationLight
contrastValidationDark
colorModeRetryCount
status
errorCode
latencyByStage
artifactDigest
```

关键指标：

- 颜色模式 profile 命中率与 legacy 回退率。
- 模式感知 artifact 生成成功率、硬校验失败率和修复重试成功率。
- light/dark 对比度失败率及失败组件、字段分布。
- 默认色、双色 Token、固定色字段数量分布。
- legacy artifact 迁移尝试率、成功率和失败原因分布。
- 颜色模式 artifact 大小增量、模型耗时、编译耗时、校验耗时和端到端 P95 增量。
- 按 profile、App/ROM 版本和首次生成/编辑拆分成功率，不把 legacy 回退计入 degraded。

## 实施前确认项

1. 端侧确认 `ohos.a2ui.extended.catalog.form` 是否支持系统模式、组件默认色切换和 `$__colorMode`。

4. 确认颜色模式硬错误是否统一阻断 artifact 上传。
5. 确认 legacy artifact 是否允许迁移，以及迁移灰度范围。
6. 上述决策完成后，先更新 `docs/云侧方案设计.md`，再进入代码实现。
