# 第一、第二、第四接口内部流程图

本文按当前代码展示三个 WebSocket 接口从请求进入、版本选择、业务处理到插件响应的真实执行路径。
接口契约仍以 [`云侧方案设计.md`](./云侧方案设计.md) 为准，Mermaid 源文件用于后续维护和重新导出图片。

图中黄色菱形表示条件判断，灰色矩形表示处理动作，绿色节点表示正常产出，红色节点表示失败、降级或
提前终止。文档嵌入的是高清 PNG；流程较大时建议打开 SVG，SVG 是矢量图，任意放大都不会模糊。

当前实际存在两套互相独立的并发资源：

| 资源 | 默认上限 | 使用者 | 等待行为 |
| --- | ---: | --- | --- |
| AnyIO 默认线程令牌 | 80/进程 | 第一、第二接口的完整同步 Service；第四接口的短同步岛 | 协程等待，不占工作线程，没有单独的令牌排队超时 |
| 模型共享 Semaphore | 20/进程 | 第三至第五接口全部真实物理模型调用 | 协程等待，不占线程，受独立的模型排队超时控制 |
| llmclient 专用线程池 | 20/进程 | 只有物理 provider 为 llmclient 的调用 | 先取得模型令牌再提交，不占 AnyIO 默认线程池 |

`running_tasks` 统计的是正在处理的 WebSocket 消息，因此既包含真正执行中的任务，也包含等待 AnyIO
令牌、等待模型令牌、模型网络响应、重试退避和 repair 的任务。模型并发上限按进程生效，不是整个部署
的全局分布式上限。

典型并发场景：

| 场景 | 实际行为 |
| --- | --- |
| 同时有 100 个第一/第二接口同步任务到达 | 最多 80 个取得 AnyIO 令牌执行，其余任务以协程状态等待令牌 |
| 同时有 25 次真实模型物理调用到达 | 前 20 次取得模型令牌，后 5 次协程排队；任一令牌释放后继续进入 |
| 模型排队超过默认 120 秒 | 当前物理调用产生 `MODEL_QUEUE_TIMEOUT`，再由模型异常重试/fallback 策略决定是否重排 |
| 模型排队 100 秒后执行 110 秒 | 合法；排队超时和执行超时分别计算，不共用 120 秒总预算 |
| llmclient 执行超过 120 秒 | 对调用方已判定超时，但该物理线程及模型令牌要等真实调用结束后才释放 |
| 第四接口等待模型令牌或进行退避 | 请求协程不占工作线程，6 秒 heartbeat 协程仍可正常调度 |
| 心跳发现响应通道断开 | 只停止心跳；内部生成、模型排队、repair 和保存仍继续 |

## 公共 WebSocket 行为

三个接口都经过 `_serve_operation_websocket()`：

- 每个连接先 `accept`，更新 `active_connections/total_connections`；每条消息更新 `running_tasks`。
- 原始请求体使用 JSON 规范记录；非法 JSON、非法包络和 Pydantic 参数错误都在路由层终止。
- 插件最外层 `errorCode` 始终为 `"0"`、`errorMessage` 始终为空、`reply.items` 始终为空数组。
- 业务成功或失败信息放入 `reply.streamInfo.streamContent`，内容是完整旧业务消息的字符串形式。
- 第一、第二接口在线程池执行同步 Service，不发送周期心跳；第四接口直接 `await` 异步 Service，并每
  6 秒发送一次 `partial` 心跳。
- 心跳发送失败不会取消第四接口内部生成、repair 或 artifact 保存；最终响应通道也断开时只记录发送失败。
- 同一 WebSocket 连接可以继续接收下一条请求；连接关闭时更新连接统计。

关键条件和结果：

| 条件 | 内部动作 | 对外结果 |
| --- | --- | --- |
| 请求 JSON、包络或字段非法 | 不进入 Service | `INVALID_ARGUMENTS` 业务错误放入 `streamContent` |
| App/ROM 唯一命中能力区间 | 加载命中的 `registryVersion` | 继续 IDS 和能力过滤 |
| 区间未命中，默认目录回退开启 | 加载 `capability_registry_version` | 继续能力过滤，并记录 fallback 日志 |
| 区间未命中且回退关闭，或默认目录无效 | Service 捕获 `ValueError` | 返回四个空数组，不查询 IDS |
| 注册表没有配置过滤范围内的依赖包 | 跳过 IDS | data/event 按可用处理 |
| IDS mock 开启 | 只读本地 mock，不访问远端 | mock 失败时使用空安装快照 |
| IDS mock 关闭 | 使用 `content.odid`，缺失时用固定兜底值请求远端 | URL 未配置、超时、HTTP/JSON 异常都降为空安装快照 |
| data/event 的受检依赖包未安装 | 从有效列表移除 | ID 进入 `unavailableCapabilities` |
| requiredPackages 不在配置过滤范围 | 不执行安装校验 | 能力不会因该依赖被移除 |
| asset 能力 | 不检查安装状态 | 注册表中的素材全部返回 |
| 能力清单 JSON 加载或模型解析异常 | `resolve_capability_overview()` 未捕获并上抛 | `FAILED` 服务异常 final |

第一接口只给数据能力返回 `id + description`；完整 `inputSchema/outputSchema` 由第二接口按需加载。

并发方面，整个同步 Service 只占一个 AnyIO 工作线程令牌，但 IDS 远端 `requests` 等待也包含在占用
时间内。80 个令牌全部被占用时，新请求在事件循环中等待令牌，不新建第 81 个工作线程；该接口没有
周期心跳，因此等待期间客户端只能保持连接并等待最终结果。

![getDataCapabilitySchemas 详细流程图](./get-data-capability-schemas-flow.highres.png)

  [`get-data-capability-schemas-flow.highres.png`](./get-data-capability-schemas-flow.highres.png)
- 矢量图：[`get-data-capability-schemas-flow.svg`](./get-data-capability-schemas-flow.svg)
- Mermaid 源：[`get-data-capability-schemas-flow.mmd`](./get-data-capability-schemas-flow.mmd)

关键条件和结果：

| 条件 | 内部动作 | 对外结果 |
| --- | --- | --- |
| 缺少 `dataCapabilityIds` 或类型非法 | Pydantic 构造失败 | `INVALID_ARGUMENTS` final |
| `dataCapabilityIds=[]` | 不执行 ID 查找 | found/missing 都为空，正常成功 |
| 能力区间命中 | 加载对应数据能力注册表 | 按输入顺序逐项查找 |
| 区间未命中且默认回退开启 | 加载默认能力目录 | 按输入顺序逐项查找 |
| 区间未命中且回退关闭 | 不执行查找 | `dataCapabilities=[]`，所有请求 ID 进入 missing |
| 当前 ID 已注册 | 返回完整 `DataCapability` | 包含 input/output Schema 和依赖等定义 |
| 当前 ID 未注册 | 不阻断其它 ID | 当前 ID 进入 `missingCapabilityIds` |
| 输入包含重复 ID | 当前实现不去重，逐项处理 | found 或 missing 中可能保留重复项 |
| IDS 或应用安装状态 | 第二接口完全不查询 | 只回答“当前版本注册表是否存在该定义” |
| 注册表文件发生未捕获异常 | 上抛路由层 | `FAILED` 服务异常 final |

第二接口也以一个 AnyIO 令牌覆盖整个同步 Service。它没有 IDS 网络查询，通常只执行注册表文件读取和
逐 ID 查找；当共享的 80 个令牌被其它同步任务占满时，本接口同样在事件循环中等待且不发送周期心跳。

### 入口、版本和编辑模式

| 条件 | 内部动作 | 终止/继续 |
| --- | --- | --- |
| 请求非法 | 不构造模型上下文、不调用 Service | `INVALID_ARGUMENTS` |
| 协议 App/ROM 区间命中 | 同时选择最终 A2UI Profile 与 Design Profile | 继续 |
| 协议区间未命中、Profile 回退开启 | 校验并使用默认 Profile/PROMPT | 继续 |
| 协议区间未命中且不能回退 | 不进入生成主流程 | `APP_VERSION_UNSUPPORTED` |
| 未出现 `sourceArtifactUrl` | Create；缺少 size 时使用 `2x2`，候选数组缺失时使用空数组 | 继续 |
| 出现非空 `sourceArtifactUrl` | Edit | 进入编辑开关和来源加载 |
| Edit 开关关闭 | 不下载来源 | `WIDGET_EDIT_DISABLED` |
| 来源缺失、超限、Markdown/Artifact 无效 | 不回退 Create、不覆盖来源 | `SOURCE_ARTIFACT_*` |
| 来源缺少/为空/格式错误的 `designcompactdsl` | 不使用标准 genui 兜底 | `SOURCE_ARTIFACT_INVALID` |
| Edit 来源有效 | 省略字段继承，显式字段替换，显式空数组清空 | 继续 |

### 能力裁决

| 对象 | 校验 | 无效后的行为 |
| --- | --- | --- |
| data binding | 注册状态、arguments JSON Schema、`/data` 写入路径、父子路径冲突 | 进入 removed |
| event | `capabilityId` 是否注册 | 进入 removed |
| asset | `assetId` 是否注册 | 进入 removed |
| IDS | 第四接口不查询；依赖第一接口已经做过的可用性裁决 | 无 |

原请求包含数据绑定，但最终数据绑定和事件都为空时，直接返回 `NO_EFFECTIVE_CAPABILITY`，不调用模型。

### 模型异常重试和 fallback

每个“首次生成”或“quality repair”都是一个独立模型阶段，并从配置的 master 重新开始：

| 配置 | 单阶段模型调用行为 |
| --- | --- |
| 模型 mock 开启 | 按最终 size 读取本地 Design mock，不占真实模型并发令牌 |
| `enable_model_failure_retry=false` | master 只调用一次，不调用 fallback |
| 模型重试开启、fallback 关闭 | master 最多 `1 + M` 次，耗尽后失败 |
| 模型重试开启、fallback 开启 | master 最多 `1 + M` 次，耗尽后 fallback 最多 `1 + F` 次 |
| 任一真实调用 | 重新等待共享 Semaphore；排队超时和执行超时分别配置；退避等待不占令牌 |
| 连接、超时、显式模型错误、非法事件或空输出 | 归为模型异常，按上述策略处理 |
| master 成功但 Design Token 转换失败 | 不立即切 fallback，归为 conversion quality error |
| master 成功但 Validator error | 不立即切 fallback，归为 validation quality error |
| master/fallback 全部失败 | `A2UI_GENERATION_FAILED`，不进入转换、校验或保存 |

每一次真实物理调用都必须单独取得同一个模型 Semaphore 令牌。首次生成、master 重试、fallback、
每轮 quality repair 都不会复用上一调用的令牌；指数退避期间先释放令牌，下一次尝试重新排队。默认
`model_max_concurrency=20` 表示单进程任何时刻最多 20 个真实模型物理调用，而不是最多 20 个
WebSocket 请求。

模型排队和执行使用两个独立超时：排队默认最多 120 秒，取得令牌后执行又有独立的 120 秒。MEP 和
DeepSeek Platform 使用异步网络；llmclient 使用专用线程池。llmclient 超时后线程无法强制停止，因此
会继续持有模型令牌直到后台物理调用真正结束，再丢弃迟到结果并按超时进入模型异常重试策略。

### Conversion、Validation 和 repair

| 条件 | 行为 |
| --- | --- |
| conversion warning | 记录后继续，不触发 repair |
| 已知 conversion error | 不进入 Validator，生成 `stage=conversion` 结构化错误 |
| conversion 未知运行时异常 | 作为服务异常上抛，不交给模型修复 |
| Artifact Validator 关闭 | 仍必须完成 Design → A2UI 转换，只跳过 Validator |
| Validator warning | 记录后继续，不触发 repair |
| Validator error | 生成 `stage=validation` 结构化错误 |
| Validator 未知运行时异常 | 作为服务异常上抛，不进入 repair |
| quality retry 关闭 | 第四接口严格失败，不保存 artifact |
| quality retry 开启且次数未达上限 | 携带最新源 Design Token、format、stage/code/message 重新请求模型 |
| repair 从 conversion error 变为 validation error | 消耗一次 repair 次数，允许继续下一轮 |
| error 全部消失 | 提前结束 repair，进入保存 |
| repair 次数耗尽仍有 error | `VALIDATION_FAILED`，不保存 artifact |
| repair 内发生模型异常 | 当前 repair 的模型阶段独立执行 master 重试和可选 fallback |

### 保存和响应

成功时：

- `genui` 保存转换后的标准三段 A2UI。
- `designcompactdsl` 保存最终模型源 Design Token，供下一轮编辑使用。
- 保存完整 CardSpec、TaskSpec、有效/移除能力、generationPlan、Profile 和来源摘要。
- `ResponsePlanner` 根据能力移除情况返回 `success` 或 `degraded`。
- Artifact/OBS 保存异常不伪造成功 URL，由路由输出 `FAILED` final。
