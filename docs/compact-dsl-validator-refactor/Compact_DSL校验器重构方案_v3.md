# Compact DSL 校验器重构方案 v3

- 版本：v3
- 日期：2026-09-30
- 状态：评审修订版，尚未实施；既有规则待决项见第 2.5 节
- 修订说明：基于 v2 补齐诊断完整性、兼容兜底、警告边界及既有冲突登记，明确后续反馈优化另行验收。
- 适用范围：微服务侧 Compact DSL 转换前校验及模型修复反馈
- 配套清单：[现有校验规则分类清单 v1](Compact_DSL现有校验规则分类清单_v1.md)，用于查阅现有检查项、源码位置及迁移归属。

本方案采用“先等价拆分校验器，再解耦错误事实与修复建议，保留简单配置接口，最后贯通模型修复反馈”的路线。
目标是让校验规则更容易维护，并让模型清楚知道：哪里出错、违反什么约束、在本次输入和环境下应该如何修改。

当前处于重构设计阶段，仅维护本方案及配套规则清单，暂不修改 `docs/云侧方案设计.md`。
本文为重构提案，不替代方案总文档；设计定稿并确认进入实施后，再于代码修改前同步已确认的相关约定。
如果发现现有代码与方案总文档冲突，单独列出差异并确认依据，不借重构顺带改变规则。

## 1. 重构目标与范围

本次重构覆盖：

- Compact DSL 转换前校验器及其辅助规则。
- 校验结果向生成流水线的传递。
- 错误事实与修复建议解耦、默认建议配置，以及按输入和环境生成建议的可选函数接口。
- 模型修复提示词和相关测试。
- 实施前需同步到方案总文档的校验与修复约定，设计阶段先在本文维护。

基本原则：

1. 保持现有公开校验入口、通过与失败判定、异常行为、警告级别和模板跳过逻辑。
2. 保持现有生成及重试策略，不在重构中增加重试次数或改变失败处理。
3. 转换器继续负责原有解析和转换职责，本次不重新划分转换器与校验器的边界。
4. 等价拆分阶段保持错误文案、顺序和去重语义，结构化诊断作为后续独立增强。
5. 修复建议不能放宽校验规则，也不能改变用户需求和数据语义。
6. 进入实施后，先将已确认设计同步到 `docs/云侧方案设计.md`，再修改代码、配置、提示词和测试；
   当前设计阶段不修改总方案，不向 `AGENTS.md` 复制方案细节。

## 2. 校验规则分类与模块结构

### 2.1 分类依据与边界

一级分类采用“语法与结构契约校验”和“语义校验”。分类依据是检查的性质，不是被检查对象的名称。
原方案的结构、绑定、素材、排版和布局划分来自当前函数职责，适合局部拆文件；
本次调整以校验层次统一组织，再在各类别内按职责划分模块。

“语法”在本文中包含结构契约，不仅指文本能否解析；“语义”包含展示含义和布局约束。
类别不决定严重程度，也不直接决定执行先后。布局错误可以继续阻断，原有警告不会因重新分类升级为错误。

| 一级分类 | 二级分类 | 检查边界 |
|---|---|---|
| 语法与结构契约 | 协议 | DSL 行格式、记录类型、必填结构、协议版本支持 |
| 语法与结构契约 | 组件 | 组件类型、属性名称与类型、必填属性、父子结构及组合组件契约 |
| 语法与结构契约 | CardSpec | CardSpec 自身字段结构、必填项、类型与格式 |
| 语法与结构契约 | 表达式 | 表达式包装、引用语法、允许的运算形式与函数调用结构 |
| 语法与结构契约 | 素材 | 素材引用格式、允许的表示形式与属性结构 |
| 语义 | 数据绑定 | DSL 引用与首帧数据的对应关系、绑定值及使用位置的类型相容性 |
| 语义 | 跨文件一致性 | DSL、CardSpec 与生成上下文中的结构化声明、类型及使用关系是否一致 |
| 语义 | 有效能力 | 数据、事件及素材是否在本次实际允许的范围内 |
| 语义 | 展示语义 | 内容与必要动作是否完整，单位、标签、值形态和文案是否准确，是否重复展示 |
| 语义 | 布局与视觉约束 | 尺寸预算、字号、对齐、密度、布局组合及染色规则 |

语义分类按以下问题判定，不以函数读取了哪份输入作为分类依据：

| 分类 | 核心问题 |
|---|---|
| 数据绑定 | 引用能否取得数据，绑定源类型是否适合目标组件？ |
| 跨文件一致性 | DSL、CardSpec 和生成上下文中的结构化声明是否一致？ |
| 有效能力 | 使用的数据、事件或素材是否在本次允许范围内？ |
| 展示语义 | 内容是否完整、含义是否准确、是否重复或遗漏必要信息和动作？ |
| 布局与视觉约束 | 内容如何摆放，尺寸、字号、密度和颜色是否符合约束？ |

读取外部上下文不自动属于跨文件检查，读取候选能力也不自动属于有效能力检查。
展示语义内部包含需求完整性和动作使用约束，不新增一级或二级类别。

边界示例：

- 素材引用格式是否合法属于语法；是否来自本次允许的素材集合属于有效能力；染色方式属于布局与视觉约束。
- 表达式引用格式是否合法属于语法；绑定能否解析到首帧数据属于数据绑定；是否违反上下文声明属于跨文件一致性。
- 事件处理器的对象结构属于组件契约；具体调用与参数是否匹配本次候选属于有效能力。
- CardSpec 自身结构属于语法；CardSpec 声明是否与 DSL 实际使用一致属于跨文件一致性。
- Progress.value 的绑定源是字符串而目标需要数值，属于数据绑定；首帧值与外部声明 schema 的类型不一致，属于跨文件一致性。
- 布尔值可以是合法数据，但直接展示 true/false 不符合用户表达要求，属于展示语义。
- 用户要求的动作被遗漏，或 W9 中可见动作数超过候选数量，属于展示语义中的完整性与动作使用约束。
  数量超限不能单独证明使用了未授权事件；具体 handler 是否匹配候选仍由有效能力检查负责。
- 跨文件包括内存中的结构化对象，不要求输入必须来自物理文件，也不能成为所有上下文检查的兜底类别。

每个具体检查项只有一个主要归属。复合函数按内部检查项拆分，不能只凭函数名整体搬迁。
辅助解析和计算可复用，同一检查项只有一个负责模块，不因分类拆分新增重复报错。
既有不同检查项即使约束相近，也先保留各自调用位置和诊断；是否合并按第 7 节另行评审，不能借归属调整改变错误数量。

### 2.2 外部依赖与不变边界

本次重构主体是 Compact 校验器及其诊断输出。分类与现有校验体系对齐，但不要求 Compact 实现所有类别。
外部依赖仅保留以下调用边界，不作为本次待拆分规则：

- 入口继续调用 `parse_compact_dsl_rows`，沿用解析、归一化和现有异常行为，不复制或重构解析器。
- 组件契约检查继续委托 `validate_card_header_layout`、`validate_timeline_unit_layout`，保留调用位置和异常转发；
  这些转换器辅助函数的实现及转换器自身的调用方式保持不变。
- 标准 A2UI 转换、完整 CardSpec 和完整产物校验沿用现状，不迁入 Compact，也不纳入本次模块拆分。
- 调用方仅做传递上下文、兼容旧错误和由诊断生成模型错误说明所必需的适配；生成、转换、重试和产物保存策略保持不变。

### 2.3 建议模块结构

保留 `compact_dsl_validator.py` 作为兼容入口，在同级新增 `compact_validation/`：

```text
card_validation/
├── compact_dsl_validator.py       # 保留公开接口
└── compact_validation/
    ├── api.py                    # 校验流程编排
    ├── context.py                # 公共校验上下文
    ├── diagnostics.py            # 诊断类型、汇总及兼容输出
    ├── syntax/
    │   ├── components.py         # 组件结构及事件处理器结构
    │   └── expressions.py        # 表达式与 PathBinding 引用语法
    ├── semantic/
    │   ├── bindings.py           # 首帧路径解析与绑定源/目标类型相容性
    │   ├── cross_file.py         # DSL 与声明上下文、CardSpec 的一致性
    │   ├── effective.py          # 本次允许的素材、事件等范围
    │   ├── display.py            # 单位、指标含义、需求完整性与动作使用
    │   └── layout/
    │       ├── routing.py        # 布局适用条件与规则调度
    │       ├── typography.py     # 主数值字号与文字压力
    │       ├── geometry.py       # 高度预算及尺寸计算
    │       ├── assets.py         # 素材染色策略
    │       ├── two_by_two.py     # 2×2 布局规则
    │       ├── two_by_four.py    # 2×4 布局规则
    │       └── fusion.py         # 融球组合规则
    └── repair_guidance.py        # 默认建议读取、统一接口及可选专用函数注册
```

协议解析、素材表示形式和完整 CardSpec 结构检查沿用已有负责模块，不在上述目录中创建占位实现。
后续只有发现确属 Compact 转换前的独立检查时，才补充对应模块并同步归属表。

配置放入现有校验规则目录：

```text
cloud/data/validator_rules/
└── compact/
    └── repair_hints.json          # 具体规则码到静态默认建议的映射，可缺省部分规则
```

分类依据是规则职责，不以文件行数机械切分。某个布局文件仍包含多个独立规则簇时，再按具体布局拆分。

现有双动作校验器先保留实现，由编排层接入。公共函数放入对应职责模块，避免建立不断膨胀的通用工具文件。

数据绑定负责“引用能否取得和正确使用值”；跨文件负责“各声明与产物是否一致”；
有效能力负责“本次是否允许使用”。同一检查可能依赖多个对象，归属仍按主要约束确定。

重构验收前，规则清单必须覆盖当前全部报错及告警分支；每项记录原函数、主要类别、目标模块、输入、
Compact 内部调用位置、执行前提、错误码和测试用例。归属表不意味着当前已覆盖整体体系中的全部规则。

## 3. 公共上下文与执行流程

本文的“上下文”指本次处理需要一起使用的相关信息，代码中通常用一个具名对象保存，再作为参数传给函数。
它不是模型的聊天历史，也不是新增的一份对外业务协议。文中有两种用途：

| 名称 | 通俗含义 | 作用 | 与现有代码的关系 |
|---|---|---|---|
| 校验上下文 | 本次校验所需信息 | 帮助规则判断是否违规，例如查组件父子关系、绑定字段类型和卡片尺寸 | 大部分信息已存在，当前分散在参数、局部变量及计算过程；统一组织与复用是本次设计 |
| 修复建议上下文 | 本次修复的额外条件 | 帮助 fixHint 选择合法的修改方向，例如调用方明确要求保留字号 | 接收这些条件的可选接口是本次新设计；已有信息按需接入，尚无来源的条件只预留、不假定存在 |

因此，“设计了上下文对象”不等于“新增了对象里的全部信息”。本章主要整理现有校验资料，
第 5.4 节主要说明修复建议的可选扩展条件；两者目前都属于待实施方案，不能当作代码已经落地。
上下文仅用于本次处理，不在不同请求之间共享可变数据，也不会全部原样发送给模型。
模型只接收由可靠诊断事实、位置、约束和可选建议组织出的错误说明。

### 3.1 上下文内容

拟议的公共校验上下文统一组织以下信息，各项按原执行位置取得，不要求入口一次计算完毕：

| 内容 | 用途 |
|---|---|
| 原始修复文本、校验文本、解析后的组件行和数据行 | 区分源码版本，按第 3.4 节映射位置 |
| 组件原始记录、有序父子边及兼容索引 | 复用计算，同时保留重复 ID、多父节点和顺序语义 |
| 全部绑定路径、可见内容绑定路径 | 区分事件参数与展示内容 |
| 首帧数据及字段约束 | 校验路径、类型和展示语义 |
| 尺寸、布局和本次生成约束 | 判断规则适用范围 |
| 可可靠获得的源行号、组件及属性位置 | 定位模型需要修改的位置 |

上下文只服务于校验，不修改输入 DSL。构建索引前保留原始记录，避免重复组件 ID 被字典覆盖而丢失错误。
例如，检查绑定不能只看表达式，还需要知道引用的数据是否存在、字段类型是什么；检查布局还需要组件父子关系
和尺寸。统一保存这些可复用资料，是为了减少重复查找与计算，不改变各规则的判断依据。
原始文本与校验文本的区分、可靠源位置映射等仍需按第 3.4 节补齐；不能因为列在上下文中就声称当前已经具备。

### 3.2 索引与遍历兼容

公共上下文保留原顺序的组件记录和父子边，包括重复 child 引用，不在收集阶段去重或只留一个父节点。
当前规则对非法输入的读取方式并不统一，等价阶段提供与原规则对应的兼容视图：

| 当前用途 | 当前读取语义 | 兼容要求 |
|---|---|---|
| 父子结构检查 `_collect_component_parent_errors` | 保留首先遇到的父节点以识别后续冲突 | 使用 first 视图，并保留原始重复边 |
| `_is_large_2x4_panel`、`_has_parent_column` 等祖先判断 | 收集全部父节点 | 使用有序 all 视图 |
| 多数布局中的单父索引 | 后出现的父节点覆盖前者 | 使用 last 视图，不擅自改为 first |

组件 ID 索引也保留原规则的覆盖行为，重复 ID 的原始记录另行留存，不提前合并或增加结构门禁。
后代遍历顺序、“第一个文本”的选择和尺寸取值优先级保持原样；例如高度预算与布局路由不能因共用上下文
而被强行统一为同一个尺寸来源。合法树上的视图复用可以优化，但非法输入的容错语义应单独变更、单独验收。

### 3.3 事实收集与诊断发布

现有 `_collect_binding_context` 在提取路径的同时追加表达式错误。原入口在素材、组件、主数值和高度等检查之后
才进行正式绑定扫描；可见属性的第二次扫描使用独立的空错误列表，避免重复发布。

公共上下文不得在构建时直接向全局错误集合发布这些诊断。等价阶段可在原调用位置惰性补齐上下文，
或缓存解析事实与待发布诊断，再在原位置、按原顺序发布一次。仅用于识别布局和可见绑定的扫描继续抑制错误输出。
不得将“先跑全部语法、再跑全部语义”当作等价迁移，也不得先去重路径再执行原本逐次输出的检查。

模块依赖保持单向：

```text
兼容入口
    → 校验流程编排
        → 分类规则
            → 公共上下文与诊断类型
        → resolve_fix_hint
            → 默认建议配置与可选专用函数
```

分类规则不调用入口，也不互相串联。跨类别的执行依赖由编排层管理。

首次拆分保留原有执行顺序。后续再根据明确依赖，减少非法结构、绑定或类型引发的无效下游诊断；
不因某一类别失败就跳过全部其他检查。

### 3.4 源码版本与定位契约

明确区分以下三个层次：

| 名称 | 含义 | 使用方式 |
|---|---|---|
| `originalSource` | 当前修复轮次模型实际收到的 `invalidSourceDsl`，即该轮确定性修复前的输入 | 所有面向模型的源码位置以此为准 |
| `validationSource` | `repair_compact_dsl_binding_paths` 等既有确定性处理后传入校验器的文本 | 产生校验事实与 actual，不冒充原始源码 |
| 解析记录 | 解析器归一化、排序后得到的组件与数据记录 | 供规则计算；记录下标不是源行号 |

当前处理器会改写路径和事件、重新序列化，部分内联操作还会删除数据行；重试控制器传给修复回调的仍是
该轮原始输入。因此处理器须在预处理前保存 `originalSource`，在诊断上下文中同时保留校验版本，
每轮刷新，不沿用上一轮映射。兼容阶段保持传给修复模型的原始文本不变，不通过替换修复对象规避位置问题。

`sourceLine` 为 `originalSource` 按实际换行计算的 1-based 行号，保留空行及代码围栏的偏移。
只有存在可靠的原文对应关系时才输出。未实现可靠映射时省略行号，不能使用解析器重排后的数组下标、
归一化后的行号或转换后标准 A2UI 的位置代替。

`componentId` 回退定位必须确认该 ID 在原始文本中唯一存在；`propertyPath` 还须确认原文属性对应关系，
属性被别名改写时不能直接套用新属性名。路径或事件被替换、数据行被移除且无法映射时，省略不可靠的源码位置，
仅保留明确标识来源的校验事实。无需为了输出位置而修改解析器现有修复行为。

`actual` 表示实际校验得到的事实，使用 `evidenceSource` 标识 `original` 或 `validation`；
它不是可以直接对原文执行替换的补丁。修复提示词必须区分原文定位与校验事实，并结合本轮约束判断修改。
旧的直接校验调用若没有外部原文上下文，传入文本同时作为 originalSource 和 validationSource，
但解析阶段发生重排或归一化后仍不能伪造源行信息。

## 4. 结构化诊断设计

每条诊断应回答：哪里出错、为什么出错、应满足什么约束；有可靠修改方向时再附加修复建议。

建议采用具名诊断对象，包含以下信息：

| 字段 | 用途 |
|---|---|
| `code` | 内部诊断的稳定规则错误码；保留在诊断记录中并显示在模型说明内，不覆盖旧外层 `code` |
| `validationClass` | 一级分类：`syntax` 或 `semantic` |
| `category` | 二级分类：`protocol`、`component`、`cardspec`、`expression`、`asset`、`binding`、`cross_file`、`effective`、`display`、`layout` |
| `severity` | 本期结构化诊断覆盖 error；warning 保留原结果出口，不升级为错误或进入模型修复列表 |
| `message` | 只描述违规事实，与修复建议分开 |
| `legacyMessage` | 精确保留原有错误文案，用于生成兼容的字符串错误、异常文本和去重键 |
| `componentId` | 原始 DSL 中的组件 |
| `propertyPath` | 组件内部的属性位置 |
| `sourceLine` | 可靠映射到 originalSource 时提供的 1-based 行号，不能使用解析或转换后的序号 |
| `actual` | 本次校验得到的实际值，不视为原文的替换目标 |
| `evidenceSource` | actual 等证据的来源：`original` 或 `validation`；与原文位置分开解释 |
| `expected` | 规则要求的合法范围或硬约束，不因缺少修复建议而省略 |
| `fixHint` | 默认配置或专用函数提供的可选建议；无可靠建议时省略，不填空建议或伪值 |

内部诊断示例（与第 6 节面向修复模型的质量问题载荷区分）：

```json
{
  "code": "COMPACT_LAYOUT_HEIGHT_OVERFLOW",
  "validationClass": "semantic",
  "category": "layout",
  "severity": "error",
  "componentId": "content_area",
  "message": "content_area 的内容最小高度为 142vp，可用高度为 126vp，超出 16vp。",
  "legacyMessage": "component content_area: vertical layout requires at least 142vp within 126vp; it overflows by 16vp. Reduce child heights, margins, or gaps instead of relying on clipping, flex shrink, or distributed alignment.",
  "actual": {
    "minimumRequiredHeight": 142
  },
  "evidenceSource": "validation",
  "expected": {
    "maximumHeight": 126,
    "overflowConstraint": "不能依靠裁剪、flex shrink 或分布式对齐消除高度超限。"
  },
  "fixHint": "检查并调整子组件高度、边距或间距，保留必要内容；调整后重新校验。"
}
```

诊断约定：

- 错误码与规则含义绑定，不随文案改变。
- 不通过匹配现有报错字符串推断错误码、位置和修复方式。
- 不确定的实际值或位置保持缺省，不填入伪值。
- 原始 Compact DSL 是行式格式，不将转换后的 A2UI 路径冒充源码位置。
- 校验模块不反向依赖生成流水线，由适配层转换为现有质量问题结构。
- 初期保留异常的字符串错误列表和原有异常文本，同时新增结构化诊断集合。
- 一级分类、二级分类、Compact 内部调用位置和严重程度是独立维度。新分类先用于 Compact 诊断，
  不直接改写标准校验器已有 category 或流水线 stage 的语义；适配层明确映射，保留原有来源信息。

示例中的禁止项限制的是用裁剪等方式掩盖负剩余空间，不是一概禁止这些布局属性；合法预算内仍沿用原有规则。
该约束必须同时出现在新诊断与模型说明中，不能因旧文案退出模型请求而丢失。
本期 warning 继续通过 `CompactDslValidationResult.warnings` 返回字符串，并沿用流水线已有的
`COMPACT_DSL_VALIDATION_WARNING` 及日志路径；不增加成功返回结果上的诊断字段，不将警告转成待修复错误。

## 5. 修复建议解耦与简单配置接口

当前 Compact 校验器直接向字符串错误列表追加文案，部分文案包含建议，尚无独立的 `fixHint` 生成逻辑。
本期先拆开错误事实、硬约束和可选建议，再提供“默认建议配置＋按规则码注册的可选专用函数”。
`fixHint` 由程序读取或计算，不额外调用模型，也不通过解析旧错误字符串生成。

### 5.1 先拆分现有报错

迁移时逐个报错分支按原规则语义拆分，不按句号或“必须”“建议”等字样自动切割：

| 原有情况 | 迁移方式 |
|---|---|
| 只有违规事实 | 写入 `message`；保留可确定的 `actual`、`expected`，允许没有 `fixHint` |
| 违规事实与修改建议混写 | 事实写入 `message`，约束写入 `expected`；审阅建议适用范围后放入默认配置或专用函数 |
| 文案看似指导修改，实际表达硬约束 | 保留为 `expected`，不能只放入可省略的 `fixHint` |

例如，“onClick 必须只有一个 handler”是硬约束；“优先调整间距”是建议。
对齐、字号、padding 或间距上限等必需条件，即使使用祈使句描述，也不能随建议一起变成可选项。
原文中的删减内容、移除动作等方向必须经过适用性审阅；不能仅为拆字段就把原句当作通用建议。

所有迁移分支都将原有完整文案逐字保存在 `legacyMessage`，旧异常继续使用它。
内部 `message` 和 `fixHint` 分开保存；不得通过重新拼接两者重建旧文案，也不得要求每条错误都有建议。
模型输入可按第 6 节将这些字段组织成一段说明，不回写内部字段。
纯字符串的兼容调用保留原文，不从中猜测事实、约束或建议。

### 5.2 fixHint 的取值流程

统一接口为 `resolve_fix_hint(diagnostic, context=None) -> str | None`。
`diagnostic` 提供具体规则码和本轮校验事实；`context` 是可选的可信输入及环境信息。
校验编排层在规则产生诊断后调用该接口；分类规则只输出事实和约束，不读取建议配置。

```text
规则产生诊断（code、message、actual、expected、legacyMessage）
    → 根据 code 查找已注册的专用函数
        → 返回有效建议：使用该建议
        → 未注册或返回 None：读取该 code 的默认建议
            → 存在有效默认建议：使用默认建议
            → 没有默认建议：省略 fixHint
    → 旧异常使用 legacyMessage，模型输入由拆开的事实、约束和建议格式化生成
```

`None` 只表示“没有专用覆盖，继续使用默认建议”，不同时表示禁用默认建议。
每个规则码最多注册一个专用函数，一次返回一条建议；需要多步修改时可在该建议内明确步骤。
建议内容不拼回 `message` 或 `legacyMessage`，不参与旧错误的去重与排序。

### 5.3 默认配置与专用函数

默认配置为 `repair_hints.json`，只保存具体规则码到非空静态建议的映射：

```json
{
  "COMPACT_LAYOUT_HEIGHT_OVERFLOW": "检查并调整子组件高度、边距或间距，保留必要内容；调整后重新校验。"
}
```

没有可靠通用建议的规则不配置对应项。默认文案必须适用于该规则的所有适用场景；
如果某个修改方向只在特定条件下合法，就只放在专用函数中，不放进默认配置。
配置不含条件表达式、优先级或动态占位符。建议中的动态数值由专用函数直接使用本轮校验事实格式化，
例如根据已经计算出的高度差给出“至少释放 16vp”，不重新解析错误文案，也不重新判定规则。

专用函数签名与统一接口一致，由 `repair_guidance.py` 中的规则码注册表显式关联；
配置文件不提供函数导入路径，不引入自动发现或插件系统。
只有确有场景差异、输入来源已接通时才增加专用函数，本期不要求为每条规则创建函数。

例如，高度超限的专用函数可按以下方式工作：

| 本轮情况 | 专用函数结果 | 最终 fixHint |
|---|---|---|
| 调用方明确要求保留字号，且所需事实已知 | 给出保留字号、检查子组件高度及合法边距/间距的建议，不保证一定有解 | 使用专用函数结果 |
| 没有适用的特殊要求，或条件未知 | 返回 `None` | 使用本规则的默认建议 |
| 其他规则没有专用函数和默认建议 | 无建议 | 省略 `fixHint` |

“保留字号”等条件只是接口使用示例，不表示当前服务已有该字段。启用实际函数时再接通可信来源并补充测试，
不得为了运行示例从用户自由文本或组件名称推断约束。当前可以先完成默认建议解耦，只预留专用函数注册接口。
可参考标准校验器 `card_validation/diagnostics.py` 已有的默认建议及显式覆盖思路，不直接复用其错误数量或阶段语义。

### 5.4 上下文与失败处理

这里的“修复建议上下文”是本次修复的额外条件，与诊断中已经确定的错误事实分开：

| 接口输入 | 表示什么 | 高度超限示例 |
|---|---|---|
| diagnostic | 校验已经发现的具体问题及约束 | 最小占用 142vp，可用 126vp，超出 16vp |
| context | 会影响修改方向的已知输入或环境条件 | 调用方明确要求保留字号 |

相同的高度错误，没有特殊条件时使用默认建议；明确要求保留字号时，已注册的专用函数可给出保留字号的调整建议。
不知道是否需要保留字号时保持未知，不能自行假定。“保留字号”只是扩展示例，并非当前已有入参。
创建或编辑模式等信息在调用链中可能已有来源，但接入建议函数仍需显式传递；edit 不自动代表禁止改变布局。
新增的是可选接口及其传递方式，不要求同时新增完整的环境信息体系；context 为 None 时仍可使用默认建议，
也不影响原有校验判定与异常输出。

上下文按需接入，不为预留接口而提前构建完整的环境字段体系：

| 信息 | 来源与边界 |
|---|---|
| 实际值、合法范围、高度差等事实 | 使用本轮规则计算结果；调用方不能覆盖或伪造 |
| 尺寸、字段类型、单位、素材及事件范围 | 读取规则已使用的可信上下文，保持原尺寸来源和约束 |
| create/edit、协议版本和功能支持 | 仅转交调用方已确定的信息；edit 本身不等于要求锁定布局 |
| 保留内容、字号或布局等特殊要求 | 仅使用调用方明确提供且可追溯的约束；未接通时保持未知 |

需要传入建议上下文时，在现有处理上下文末尾增加可选 `repair_context`，校验入口增加同名仅关键字参数，
默认 `None`，保持原参数与旧调用有效。第 3.4 节的原文及校验文本来源仍须可靠传递，不能因建议缺省而丢失定位依据。
不向 CardSpec 或 TaskSpec 对外字段随意追加建议参数，不使用进程级可变状态传递请求上下文。
条件缺失、`None` 或类型不符都表示未知，不按 false 处理，不据此推断可以删除内容或调整布局。

建议获取失败只影响建议本身：

- 专用函数返回无效值或执行失败时记录原因，回退到该规则的默认建议；不把异常文本发送给模型。
- 默认配置缺失、加载失败或校验不通过时禁用本次默认建议；专用函数仍可提供可靠建议，两者都不可用则省略。
- 默认配置仅检查格式、规则码有效性、重复键和非空字符串；函数注册表检查规则码和唯一性，随代码发布。
- 相关检查在构建及测试时发现错误应阻止交付；运行时失败不得吞掉原错误、改变严重程度或把校验失败当作通过。

无建议时保留错误事实与硬约束，继续既有异常和修复流程；只在旧字符串兼容路径使用原始错误说明。
专用函数的失败隔离不能扩大到整个校验器，也不能吞掉其他原本会抛出的异常。
日志仅需记录规则码、建议来自专用函数/默认配置/缺省，以及必要的失败原因。
本期不引入条件配置语言、建议优先级引擎、独立模板渲染器、策略版本体系或远程热更新。

## 6. 接入模型修复链路

### 6.1 目标链路

内部结构化诊断、旧异常字符串和面向模型的说明分别承担存储、兼容和表达职责。
结构化保存不要求模型直接接收全部诊断 JSON；本期在构造修复请求时按固定格式组织错误说明。

```text
分类规则产生结构化诊断 → resolve_fix_hint 补充可选建议 → 汇总为质量问题
    ├─ 旧异常与重试控制：沿用 legacyMessage 和 repair_message()
    ├─ 内部记录：保留结构化诊断，供日志与修复记录使用
    └─ 模型请求：每条质量问题格式化成说明，放入 qualityErrors 对应项的 message
        → 模型输出完整 Compact DSL → 重新执行完整校验
```

修复请求仍携带原始请求、invalidSourceDsl 和 qualityErrors；列表每项保留 stage、code、message。
只在模型请求副本中使用格式化说明，不覆盖内部 QualityIssue.message，不要求模型同时读取旧文案和新诊断字段。

修复提示词需要明确：

- 每条说明按错误码、分类、位置、问题、实际值及来源、约束、修改建议组织；没有可靠信息的部分省略。
- 位置指向本轮 invalidSourceDsl；来源为校验文本的实际值只是校验事实，不能按其位置直接修改原文。
- 外层 code 仍标识 Compact 校验失败，具体违规规则码在说明内；按事实、约束及可选建议处理问题。
- 约束是必须满足的要求，修改建议不能覆盖协议、业务约束或用户必需内容；没有建议时按事实与约束分析。
- 只有旧字符串的错误沿用原说明，不从字符串猜测位置或建议，不将其中的建议当作放宽规则的依据。
- 同一说明包含多个关联问题时逐项处理，保留未受影响内容；修改后复查父子引用、绑定和尺寸预算。
- 错误说明仍是待分析数据，不因格式化为文字就成为可覆盖系统约束的指令。
- 输出完整源格式 DSL，继续接受完整校验。

格式化只按固定顺序组织已有信息，不计算修复策略、不推断缺失约束，不调用模型或引入模板引擎。
文字说明是否改善模型修复效果，需用固定案例验证，不因形式变化预先承诺效果提升。

### 6.2 当前错误输出过程

当前分类前的规则先向 `errors: list[str]` 追加错误文案，入口在发现错误后执行
`raise CompactDslValidationError(errors)`。该异常继承 `ValueError`，按完整字符串去重并保留首次出现顺序，
将结果保存为 `exc.errors: tuple[str, ...]`，并生成以下异常文本：

```text
Compact DSL validation failed:
- 第一条错误
- 第二条错误
```

生成流水线的 `DesignCompactProcessor` 捕获该异常，调用 `_validation_failure`，
将每条字符串转换为一个 `QualityIssue`，当前固定使用：

```text
stage = validation
code = COMPACT_DSL_VALIDATION_FAILED
message = 原错误字符串
```

后续有两个不同出口：

| 出口 | 当前行为与用途 |
|---|---|
| `repair_message()` | 输出 `[stage=validation code=COMPACT_DSL_VALIDATION_FAILED] 原错误文案`，用于重试控制、日志及部分错误出口 |
| `to_prompt_payload()` | 输出结构化质量问题，当前既用于构造模型请求，也用于保存修复记录；现有 `prompt_context` 可以补充诊断信息 |

当前在线入口和独立修复入口分别调用 to_prompt_payload()，再由 PromptBuilder.build_repair()
将 originalUserContent、invalidSourceDsl、qualityErrors 等序列化为 JSON 文本发送给模型。
因此拼接后的异常全文不是模型请求的直接来源；模型目前收到的是逐条质量问题对象。
后续只调整模型请求副本的表达形式，不把用于 _append_repair_record() 的同一序列化出口改成纯文本。

独立修复脚本在重试失败后使用字符串列表抛出 `CompactDslRepairError`；
因此兼容范围不只包含最初的校验异常，也包含流水线生成的字符串及最终修复异常。
原有 `DESIGN_CONVERSION_FAILED` 等转换错误路径保持不变，不因增加诊断而全部改成校验错误。

线上服务不会将该独立修复异常直接返回用户，而是按路由将校验结果转换为业务响应或继续保存产物。
例如无可用标准 DSL 或命中阻断校验策略时，现有实现返回 FAILED、VALIDATION_FAILED 及既有中文提示；
非阻断路径仍可能记录错误后继续保存。新增诊断不改变这些分支，也不追加到用户可见业务响应中。

### 6.3 双出口异常兼容

采用“保留字符串错误出口，新增结构化诊断出口”的方式，继续保留：

- 异常类名 `CompactDslValidationError`、`ValueError` 继承关系及公开导入路径。
- `CompactDslValidationError(errors)` 的原有构造方式。
- `exc.errors` 的字符串元组类型、文案、顺序及按完整文案去重的行为。
- `str(exc)` 的前缀、换行、项目符号及 `exc.args` 中的原异常文本。
- 解析失败时通过 `raise ... from exc` 保留的异常链。
- 其他原本未包装的异常路径；本次不扩大捕获范围或吞掉底层异常。

异常新增 `diagnostics: tuple[CompactDiagnostic, ...]`，用于保存结构化诊断。
旧调用方继续读取 `exc.errors` 或捕获 `ValueError`，无需修改；新流水线通过显式适配器读取诊断。
异常类搬迁到公共诊断模块后，旧模块应重新导出同一个类，不能另建同名异常类导致旧捕获失效。

分类规则逐步改为输出诊断对象，由适配层使用 `legacyMessage` 生成旧字符串列表。
旧构造方式仅传入纯字符串时，`diagnostics` 为空；不伪造基础诊断或通过字符串猜测类别、位置和修复建议。
新入口可通过专用工厂接收按原顺序收集的字符串与诊断记录，按第 6.5 节统一分组，避免改变旧位置参数的含义。
未迁移规则、解析异常包装和外部委托返回的字符串继续使用旧路径，不因异常新增属性而自动进入新格式化流程。

已迁移规则的 `message` 只说明违规事实，但旧出口始终使用 `legacyMessage`。
可选 `fixHint` 独立存储，不拼回事实或兼容文案；否则会改变异常文本、去重结果及依赖文本的旧测试。
建议获取失败时保留原错误，不改变异常是否抛出和原文案内容。

### 6.4 内部记录与模型说明分离

内部 QualityIssue 保持已有 stage、code、message 的含义，新增诊断作为附加数据保存：

| 内部内容 | 保存方式 | 用途 |
|---|---|---|
| 执行路径 | stage 继续为 validation | 保持原来源与控制逻辑 |
| Compact 校验失败总码 | code 继续为 COMPACT_DSL_VALIDATION_FAILED | 不用具体规则码替换旧总码 |
| legacyMessage | QualityIssue.message | 旧错误、重试字符串及最终异常继续使用原文 |
| 本组结构化诊断 | 本组记录全部迁移后，在 prompt_context 中新增 compactDiagnostics 列表 | 每项保留内部诊断的 code、message、可靠位置、actual、evidenceSource、expected、可选 fixHint 等字段；部分迁移按第 6.5 节兜底 |

compactDiagnostics 是内部附加记录，具体规则码和错误事实直接使用原诊断字段，不再另建改名字段。
没有结构化诊断的旧调用不提供该列表，部分迁移的分组也不提供；仅有空列表或异常属性不视为已迁移。
适配器不得借 prompt_context 覆盖原 stage、code、message。
to_prompt_payload() 保留返回字典的职责；允许增加上述诊断记录，不把返回值整体替换成文字。
该方法还用于 _append_repair_record()，保存的 validation_errors 继续保持结构化对象列表，旧字段值不变。
其他转换错误和标准产物校验的输出沿用现状，本次格式化仅针对带有新诊断的 Compact 校验问题。

在 PromptBuilder.build_repair() 组装模型输入时增加一个普通辅助函数，建议名为
`format_compact_issue_for_model(payload) -> str`。它读取一条质量问题及其诊断列表，返回错误说明。
在线入口先按原链路还原素材标识，格式化读取还原后的请求副本；独立入口沿用当前直接传递载荷的方式，
不新增素材还原步骤。格式化不能修改原记录或内部诊断。

模型输入的构造顺序：

1. 在线及独立修复入口继续取得逐条质量问题字典，并保留当前错误数量检查。
2. 在构造修复请求的边界为每项创建新对象；仅当该 Compact 问题具有非空且完整的 compactDiagnostics 时生成新说明。
3. 新对象保留原 stage、code，把格式化说明放入 message；不再把 compactDiagnostics 或旧错误全文重复发送给模型。
4. 未迁移的纯字符串错误及其他来源的质量问题沿用原载荷；最后仍由 json.dumps 序列化完整修复请求。

内部 QualityIssue.message、repair_message() 和用于保存修复记录的字典均不被这个模型请求副本覆盖。
保留完整内部字段便于排障；模型看到的是位置、事实、约束和建议组成的说明，而非两套重复文案。

单条质量问题的模型输入示例（与第 4 节内部诊断对应，实际换行由 JSON 序列化处理）：

```json
{
  "stage": "validation",
  "code": "COMPACT_DSL_VALIDATION_FAILED",
  "message": "错误码：COMPACT_LAYOUT_HEIGHT_OVERFLOW\n分类：semantic / layout\n位置：组件 content_area\n问题：content_area 的内容最小高度为 142vp，可用高度为 126vp，超出 16vp。\n实际值（来源：本轮校验文本）：{\"minimumRequiredHeight\":142}\n约束：{\"maximumHeight\":126,\"overflowConstraint\":\"不能依靠裁剪、flex shrink 或分布式对齐消除高度超限。\"}\n修改建议：检查并调整子组件高度、边距或间距，保留必要内容；调整后重新校验。"
}
```

格式化规则保持简单且确定：

- 依次输出具体规则码、分类、可靠位置、错误事实、实际值及来源、硬约束和可选修改建议。
- 数组或对象按稳定 JSON 格式展示，保留路径、类型、数值和全部约束，不为了改成自然语言而概括、翻译或猜测含义。
- 未知位置不输出；没有 fixHint 就省略“修改建议”。合法的 0、false 或空容器等事实不能因假值判断而丢失。
- 一个兼容分组有多条诊断时，用编号分段保留所有关联问题，不合并成缺失位置或约束的一句概括。
- 只有旧字符串时直接沿用它。格式化失败时记录原因并回退该项旧说明，移除模型副本中的 compactDiagnostics，
  不把不完整的新诊断与旧说明重复发送；不吞掉错误、不改变错误数量。
- 格式化函数只读取数据并生成新字符串，不反向解析旧文案，不改变规则判定、建议选择或去重结果。

这里只允许在最终模型说明中按标签组织事实与建议；“不拼回文案”的兼容约束仍适用于内部事实字段和旧异常文案。

### 6.5 去重、数量对应与关联诊断

当前按旧错误字符串去重，在线及独立修复入口均检查质量问题数量与传给重试器的字符串数量一致。
因此不能分别去重字符串和诊断，再按下标拼接，也不能把所有质量问题压成列表中的一个元素。

从同一份有序记录生成兼容分组；记录可以是未迁移字符串或已迁移诊断，前者以自身为键，后者以 legacyMessage 为键：

```text
原始字符串或诊断 → 按旧完整文案分组，保留首次出现顺序
    ├─ 每组一条旧错误字符串
    ├─ 每组一个内部 QualityIssue，全部迁移的组附加 compactDiagnostics
    └─ 每组一个模型 qualityErrors 项，全部迁移则分段说明，否则保留旧说明
```

通常一组只有一条诊断，直接格式化为一段说明。不同位置或约束恰好对应相同旧文案时，
本组全部记录已迁移时，内部保留全部诊断，模型说明逐项列出各自的规则码、位置、事实来源、约束和可用建议，不能按最后一项覆盖。
格式化完成后不按新说明再次去重、不重排，不因缺少建议而删掉错误项。

同组混有未迁移字符串时，整组沿用旧说明，不提供 compactDiagnostics，避免把部分信息冒充完整迁移；
该组已有诊断仍保留在 exc.diagnostics 中。新增的修复记录暂不附加这些部分诊断，旧记录内容保持完整。
统一分组结果由诊断汇总层提供给适配器，不能只拿附加诊断反推全量错误。
exc.diagnostics 仅保留已迁移的原始诊断，数量不要求与去重后的 exc.errors 相等；适配器必须消费统一分组结果，
禁止将两个属性直接 zip。始终保证内部质量问题、模型 qualityErrors 和传给重试器的错误字符串数量一致。

上述兼容针对固定校验输入和固定每轮模型返回的 DSL 序列。模型说明允许改变，旧异常文本仍保持不变；
真实模型因收到新说明可能产生不同结果，不能要求两套真实模型运行最终返回相同异常或成功状态。
本节分组仅复现原文去重；第 7 节的根因合并、排序和下游抑制属于后续独立变更。

## 7. 错误依赖与重复诊断

首次接入结构化诊断时保持原有错误数量和顺序，避免同时改变行为。

以下属于后续可选的独立变更，不计入本次重构范围与验收：

- 以组件、绑定或父容器组织相关诊断。
- 优先呈现结构、绑定和类型等上游问题。
- 只有明确证明下游诊断依赖无效前提时，才抑制该诊断。
- 保留独立错误，不根据文本相似度随意合并。
- 修复后重新运行全部校验，确认上游问题和下游问题均已消失。

例如，某字段类型已经错误，则依赖正确字段类型才能成立的主数值排版建议可能没有意义；
但同一组件存在非法素材时，该错误仍应保留。

## 8. 分阶段实施

| 阶段 | 工作内容 | 完成标准 |
|---|---|---|
| 一：建立基线 | 盘点诊断分支、调用方和测试，记录源码版本与 BASE-01 等差异，建立固定模型返回序列 | 规则归属与清单一致；差异明确登记，不将现状当作已获批准的业务规范 |
| 二：等价拆分 | 提取分类模块和公共上下文，保留索引兼容视图、原诊断发布时机及入口 | 合法及非法输入下判定、文案、顺序、去重和警告行为一致 |
| 三：诊断与文案解耦 | 引入规则码，拆分事实与硬约束，审阅并分离已有建议，逐字保留旧文案；保存源码版本及可靠位置 | 无建议也能表达完整错误；不从字符串猜测字段，无可靠映射时省略位置 |
| 四：简单建议接口 | 接入默认建议配置与 resolve_fix_hint，预留按码注册的专用函数；确有场景需求时再接通可信上下文 | 专用函数、默认建议及缺省三种路径明确；未知条件不臆测，建议失败不影响原错误 |
| 五：贯通修复 | 内部保留诊断，模型请求逐项格式化；更新提示词并贯通在线及独立修复入口 | 模型说明包含可靠事实与建议；旧异常、数量顺序、内部记录及线上响应保持兼容 |

诊断和已有建议的解耦优先覆盖：

1. 绑定与数据类型。
2. 单位和展示语义。
3. 高度预算。
4. 主数值排版。
5. 各类特定布局。

各阶段形成独立、可审查的变更。等价拆分阶段不混入规则放宽、收紧或视觉参数调整。
本次实施范围止于阶段五。第 7 节的反馈优化单独立项，届时明确批准后的数量、顺序及抑制行为，重新建立验收基线。

## 9. 验证计划

| 验证层 | 主要检查 |
|---|---|
| 行为等价 | 正常和违规样例的判定、错误顺序、去重、警告及异常表现 |
| 公共上下文兼容 | 重复组件 ID、重复 child、多父节点的 first/last/all 视图；原遍历顺序、尺寸来源及模板豁免 |
| 诊断发布时间 | 同一 DSL 同时触发素材错误和表达式错误时顺序不变；可见绑定及布局识别扫描不重复发布 |
| 分类与边界 | 所有诊断分支均有归属；复合规则按检查项拆分；不重复实现解析、CardSpec 或完整产物校验 |
| 诊断正确 | 错误码、原文组件和属性位置、实际值来源与期望约束；不可映射时位置缺省 |
| 文案解耦 | 纯报错允许无建议；混合文案按规则语义拆分；硬约束完整保留；高度错误的负预算禁止规避约束同时出现在 expected 与模型说明；legacyMessage 逐字不变 |
| 源码版本 | 路径修复、事件替换、数据行内联删除、组件重排、空行与代码围栏；每轮修复使用自己的原文和映射 |
| 异常兼容 | 旧构造方式、公开导入、异常继承、`errors`、`str(exc)`、`args`、异常链及原有去重顺序 |
| 输出兼容 | 固定校验输入和每轮模型返回的 DSL 序列时，`repair_message()`、最终 `CompactDslRepairError`、重试次数及外层 code/stage 保持不变 |
| 线上响应兼容 | 固定模型返回序列与路由配置时，业务状态、错误码、中文提示、是否阻断及是否保存产物保持不变 |
| 分组与适配 | 相同旧文案对应不同诊断时完整保存并分段说明；纯旧构造、委托字符串及同组混合迁移保留旧说明，不误入新格式；内部质量问题、模型列表和重试字符串数量一致，不按新文案再次去重 |
| 警告出口 | 无错误时的发布时机、warnings 字符串元组、原警告码及日志保持不变，不进入 qualityErrors 或触发模型修复 |
| 建议接口 | 专用函数返回有效建议、返回 None、未注册、无默认建议四种路径；已知条件可区分建议，未知不等于 false；未接入真实场景时用测试函数验证扩展接口 |
| 配置与失败处理 | 配置格式、规则码、重复键、字符串和注册唯一性检查；文件缺失、函数缺少所需事实、异常或非法返回时，按约定回退或省略建议且保留原错误 |
| 说明格式化 | 字段顺序稳定，代码、位置、事实来源、全部约束和建议不丢失；无位置或建议时省略，0/false/空容器保留；仅旧字符串或格式化失败时回退 |
| 链路完整 | 在线和独立修复使用同一格式化函数，素材标识按既有顺序还原；模型仅获得新说明，不重复发送旧文案和内部诊断 |
| 记录与对象隔离 | 格式化不修改内部 QualityIssue.message、诊断或序列化字典；修复记录仍为对象列表，旧字段不变，其他来源质量问题保持原状 |
| 建议与约束 | 旧文案和新建议方向不同时，全部记录已迁移的分组只发送新说明；无建议时保留硬约束，字符串兜底也不允许放宽规则 |
| 修复回归 | 修复产物重新执行全部校验，避免引入新违规 |

回归范围包括 Compact 校验、转换、双动作、主数值排版、Few-shot、修复提示词、相关生成流水线和模板调用链路。

兼容测试使用确定性的模型替身，为新旧实现提供完全相同的逐轮 DSL 返回序列，固定本轮候选、配置和环境。
至少覆盖首次通过、重试关闭、修复后通过、重试耗尽、转换失败，以及既有阻断和非阻断路由；
后两者必须分别核对是否保存产物，不能把所有 error 统一改为失败响应。
旧调用不提供可选上下文时也应纳入兼容测试。

BASE-01 的测试暂用于记录现有行为和比较等价性，不能作为 160vp 业务规范已经实现的证据。
确认尺寸依据并单独修正后，再更新相关预期和基线；变更前后结果及裁决原因应可追溯。
BASE-02 至 BASE-04 分别保留结构冲突、按旧建议修复后出现新错误、条件表达式被计数展示规则检查的复现案例；
裁决前区分已知失败与本次回归，不能通过删除检查、放宽断言或更新快照宣称全部通过。

每阶段执行：

- 修改文件的 Ruff 检查。
- 与行为直接相关的单元测试。
- 对应配置检查。
- `git diff --check`。
- 按影响范围补充链路回归。

模型修复效果使用固定案例集比较：

- 一次修复通过率。
- 同类错误重复出现的比例。
- 修复后新增违规的比例。
- 必需内容和语义的保留情况。

比较时记录模型、生成提示词、默认建议配置及专用函数的代码版本和重试设置。真实模型评估允许修复输出、最终异常及成功状态发生变化，
以修复效果和需求保留情况评估，不用于证明字节级错误兼容。单元测试通过不等于真实模型修复效果已改善。
评估文字说明与直接发送诊断 JSON 时使用同一组诊断事实和约束，避免把信息增减误当作格式收益。

## 11. 交付与验收标准

本次阶段一至五的重构完成应满足；第 7 节的后续优化另行验收：

- 主入口只承担兼容与编排，规则按职责归属清晰。
- 实施交付时，将第 10.1 节已确认的归属检查规范同步到 AGENTS.md；后续新增和修改校验均核对分类、实际文件及理由，规则清单与实现保持同步。
- 规则按语法与结构契约、语义两级分类，每项主要归属唯一；分类不改变 Compact 内部调用位置、严重程度或执行顺序。
- 原有校验行为通过等价回归，任何有意变更单独说明。
- 固定校验输入和逐轮模型返回序列时，旧异常、字符串出口、重试行为及线上业务响应保持兼容；具体规则码不替换外层通用错误码。
- 公共上下文保留非法输入的索引和遍历语义，表达式诊断按原位置发布一次，不因复用提前或重复输出。
- 面向模型的位置指向本轮原始修复文本；校验事实明确来源，无可靠映射时不输出伪造位置。
- 已迁移规则具有稳定错误码；可映射时提供可靠错误定位，无法映射时明确缺省并保留校验事实。
- 错误事实、硬约束和可选建议已解耦；纯报错允许没有 fixHint，旧完整文案仍由 legacyMessage 保留。
- `fixHint` 优先使用按码注册的专用函数结果，无覆盖时读取默认配置；接口可接收可信上下文，真实场景按需接入，未知信息不臆测。
- 配置不改变校验判定，建议不会绕过协议或业务约束。
- 完整迁移的诊断以逐条说明进入模型请求，不重复携带旧文案；部分迁移保留旧说明，警告沿用原出口；错误数量与顺序保持一致，修复结果重新接受完整校验。
- 模型说明不回写内部字段，to_prompt_payload() 与修复记录仍保留结构化对象；未迁移或格式化失败时保留原说明。
- 专用函数返回 None 时读取默认建议；函数失败、配置错误或事实缺失不会丢失原校验结果，无可用建议时省略 fixHint。
- BASE-01 等既有差异具有明确状态和裁决记录；待决时不得宣称相关业务规范已满足。
- 交付报告逐项列出实际修改文件、执行的检查、测试数量及通过或失败结果。

实施中如果发现现有代码与方案总文档冲突，单独列出差异并确认依据，不借此次重构顺带改变规则。
