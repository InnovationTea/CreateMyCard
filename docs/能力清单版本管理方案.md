# 能力清单版本管理方案

## 1. 文档目的

本文档整理项目当前的版本控制机制，并给出已有版本发布后新增能力清单的管理方案。目标是：

- 已发布版本可追溯、可重现，不因后续修改而发生漂移。
- 新增能力可按 App 版本和 ROM 版本精确投放。
- 当前仅维护两个完整版本，保持发布和回滚流程简单。
- 生成的产物可以定位到当时使用的能力清单和协议版本。
- 发布、灰度、回滚和后续增量添加有统一规则。

本文档是版本管理专项说明。当前线上行为仍以 `docs/云侧方案设计.md` 为准；本文档中标记为“建议演进”的内容尚未在代码中实现，落地时应先同步云侧方案总文档，再修改代码、配置和测试。

## 2. 核心结论

当前能力清单采用“两个完整快照 + 版本区间路由”的管理模型：

1. 已发布的能力目录视为不可变快照，不再直接修改。
2. 新增、调整或停用能力时，生成一个新的能力清单版本。
3. `registry_ranges.json` 只负责将 App/ROM 二维区间路由到某个完整快照。
4. 新版本直接复制上一版的三份完整 JSON，再在新目录中添加能力。
5. 能力清单版本、A2UI 协议版本、代码发布版本分开管理，不强制一起升级。

## 3. 当前版本控制现状

### 3.1 代码和 Skill 发布版本

项目使用 Git 管理源码历史。当前的 GitHub Actions 发布流程在推送 `v*` tag 时触发，通过 `release.sh` 打包 `skills/` 下的各个 Skill，并创建 GitHub Release。

该流程当前只打包 Skill，不会独立发布微服务代码或能力清单。因此，Git tag 能标识仓库源码状态，但不能单独替代运行时的能力清单版本。

文档创建时的仓库基线为：当前分支 `main` 跟踪 `origin/main`，HEAD 为 `576e9d6`，本地未检出 Git tag。该信息只是整理现状时的快照，实际发布以当次提交和远端 tag 为准。

### 3.2 能力清单版本

当前能力清单位于：

```text
widget_service/cloud/data/capabilities/
├─ registry_ranges.json
├─ app-11.7.5.205_rom-6.0/
│  ├─ data_capabilities.json
│  ├─ event_capabilities.json
│  └─ asset_capabilities.json
└─ app-11.7.7.300_rom-7.0/
   ├─ data_capabilities.json
   ├─ event_capabilities.json
   └─ asset_capabilities.json
```

`CapabilityRegistry` 先规范化请求中的 App 版本和 ROM 版本，再在 `registry_ranges.json` 中查找唯一匹配的二维区间。当前配置为：

| App 版本区间 | ROM 版本区间 | 能力清单版本 |
| --- | --- | --- |
| `[11.7.5.205, 11.7.7.330)` | `[7.0, 7.2)` | `app-11.7.5.205_rom-6.0` |
| `[11.7.7.330, 12.0.0.0)` | `[7.0, 8.0)` | `app-11.7.7.300_rom-7.0` |

区间采用左闭右开规则。加载器会校验目标目录存在、区间合法且不重叠；同一请求不允许同时命中多个能力清单。

能力目录名只标识快照内容，不用于推导实际适用区间。当前索引没有 App 版本边界空档，但 ROM 6.x、
旧 App 搭配 ROM 7.2 及以上等组合不直接命中；这些请求按回退开关决定是否使用默认清单。

未命中区间时，若 `enable_default_capability_registry_fallback` 开启，服务回退到配置的默认能力清单。当前默认版本为 `app-11.7.5.205_rom-6.0`。

### 3.3 A2UI 协议版本

A2UI 协议与能力清单分开路由。`protocol_profiles/registry_ranges.json` 按 App/ROM 区间选择协议 profile 和 Design profile。当前配置为：

| App 版本区间 | ROM 版本区间 | A2UI profile | Design profile |
| --- | --- | --- | --- |
| `[11.7.5.205, 12.0.0.0)` | `[6.0, 7.0)` | `a2ui-form-rom6.0-v1` | `design-compact-dsl` |

仅新增数据、事件或素材能力，且新能力仍使用现有组件、属性、数据绑定和事件协议时，不需要升级 A2UI profile。只有端侧协议能力发生变化时，才应新建协议 profile 并配置对应区间。

### 3.4 Artifact 产物版本

每个生成产物都在 `meta` 中记录生成时使用的关键版本，包括：

- Artifact schema 版本。
- API、TaskSpec、CardSpec 和 DSL 协议版本。
- Skill 版本。
- `protocolProfileId`。
- `capabilityRegistryVersion`。
- 生成模式、唯一 `artifactId`、创建时间和来源产物摘要。

这些字段用于服务端日志、问题定位和产物追溯，不暴露给主 Agent 的用户可见返回。

多轮编辑不覆盖原产物。每次编辑生成新的 UUID 对象名，并通过 `generationMode: "edit"` 和 `sourceArtifactDigest` 建立来源关系。

### 3.5 当前机制的限制

- 已发布目录仍可被直接编辑，尚无自动的不可变校验。
- 每个版本都是三份完整 JSON，手工复制和增量修改容易遗漏或产生无关差异。
- 路由维度只有 App 版本和 ROM 版本。同一 App/ROM 组合在同一时刻只能命中一个能力清单，无法直接做两个清单版本并行灰度。
- 默认回退开关可以提高可用性，但也可能掩盖新版本区间缺失，需要日志和告警配合。
- GitHub Release 当前只打包 Skill，能力清单与微服务的发布物管理还需要由部署流程补齐。

### 3.6 ROM 版本口径

`docs/云侧方案设计.md` 规定 ROM `< 7.0` 不加载本 Skill，ROM `>= 7.0` 才允许加载。当前能力索引将
App `[11.7.5.205, 11.7.7.330)`、ROM `[7.0, 7.2)` 路由到旧快照，并将 App
`[11.7.7.330, 12.0.0.0)`、ROM `[7.0, 8.0)` 路由到新快照。ROM 6.x 不直接命中能力索引。

能力清单和 A2UI 协议 profile 分开路由；ROM 7.x 的协议 profile 仍需由小模型侧版本记录和
`protocol_profiles/registry_ranges.json` 单独维护，不能从能力清单版本推导。

## 4. 已发布后新增能力的版本控制

### 4.1 基本原则

#### 原则一：已发布快照不可变

一旦某个能力清单被生产环境使用，对应目录便应冻结。即使只是修正描述、示例值或依赖信息，也应生成新版本，不应原地修改已发布目录。

这保证历史 Artifact 中记录的 `capabilityRegistryVersion` 始终指向同一份内容。

#### 原则二：能力版本和协议版本解耦

新增能力时先判断端侧现有框架是否已经支持。

- 若只是在现有协议内新增一条数据、事件或素材定义，只升级能力清单版本。
- 若需要新的 A2UI 组件、属性、绑定表达式、事件结构或端侧解析行为，同时新增协议 profile，并对 App/ROM 兼容区间分别路由。

#### 原则三：版本号标识内容，区间配置标识适用范围

`registryVersion` 是能力快照的唯一标识；`appVersion` 和 `romVersion` 区间表示该快照可以分发给哪些客户端。两者不应被当成同一个概念。

近期为了保持现有命名习惯，可继续使用 `app-<起始App版本>_rom-<起始ROM版本>`。如果同一 App/ROM 后续需要多次云侧能力发布，建议改用独立快照编号，例如 `cap-2026.08.28.1`，避免版本名与客户端版本过度绑定。

### 4.2 当前落地：复制新快照并拆分区间

已发布版本是 `app-11.7.5.205_rom-6.0`，App `11.7.7.330` 及以上且 ROM 7.x 使用的新版本为
`app-11.7.7.300_rom-7.0`，当前实现为：

1. 保留 `app-11.7.5.205_rom-6.0/` 不变。
2. 创建 `app-11.7.7.300_rom-7.0/`，在新目录中增加二期能力。
3. 按 App 和 ROM 二维范围配置能力清单区间：

```json
{
  "schemaVersion": "v1",
  "ranges": [
    {
      "registryVersion": "app-11.7.5.205_rom-6.0",
      "appVersion": {
        "minInclusive": "11.7.5.205",
        "maxExclusive": "11.7.7.330"
      },
      "romVersion": {
        "minInclusive": "7.0",
        "maxExclusive": "7.2"
      }
    },
    {
      "registryVersion": "app-11.7.7.300_rom-7.0",
      "appVersion": {
        "minInclusive": "11.7.7.330",
        "maxExclusive": "12.0.0.0"
      },
      "romVersion": {
        "minInclusive": "7.0",
        "maxExclusive": "8.0"
      }
    }
  ]
}
```

这种做法不需要修改运行时加载逻辑。同时满足 App `11.7.7.330` 及以上和 ROM `[7.0, 8.0)` 的请求
使用新快照；满足 App `[11.7.5.205, 11.7.7.330)` 和 ROM `[7.0, 7.2)` 的请求使用旧快照。
其它组合不直接命中，后续是否使用默认快照由回退开关决定。新能力只添加到 `300/7.0` 目录，
不修改 `205/6.0` 目录。

若新能力不依赖 App 升级，需要对同一 App/ROM 的所有用户一次性切换，可直接将原区间指向新快照，并保留旧快照供回滚和历史 Artifact 读取。

### 4.3 当前不引入增量合并

当前只有两个能力清单版本，不引入 `base`、`patches`、release manifest
或快照生成器。新版本始终保存可独立加载的三份完整 JSON。

当能力清单版本数量明显增多、手工复制已成为主要维护成本时，再单独评估
是否引入增量生成机制。

### 4.4 同 App/ROM 的灰度发布

当前 App/ROM 二维区间只能选中一个能力快照。如果同一 App/ROM 需要新旧清单并行灰度，需要在服务端增加第三个发布选择维度，例如受控的 release ID、白名单或实验分组。

建议的选择顺序为：

```text
App/ROM 兼容性过滤
        ↓
服务端发布规则选择 release
        ↓
得到唯一 registryVersion
        ↓
加载不可变快照
```

该能力会改变现有路由边界，实现前必须先在云侧方案总文档中明确灰度上下文来源、分组稳定性、日志字段和回退规则。

## 5. 能力本身的兼容性规则

### 5.1 新增能力

- 使用新的全局唯一能力 ID。
- 补齐能力类型所需的 schema、依赖、样例和描述。
- 确认端侧实现已在目标 App/ROM 范围内可用，不得只在云侧清单中声明一个尚未实现的动态能力。

### 5.2 兼容性增强

以下变更通常可以在新能力清单版本中沿用原能力 ID：

- 新增可选输出字段。
- 放宽不会改变旧产物语义的可选配置。
- 修正描述、样例或其他不影响运行时契约的元数据。

即使兼容，也仍需要新建能力清单快照，不修改旧快照。

### 5.3 破坏性变更

出现以下情况时，应新建能力 ID，例如从 `SomeCapability` 演进为 `SomeCapabilityV2`：

- 删除、改名或改变已有输出字段类型。
- 改变参数或返回值的原有语义。
- 将原可选字段改为必选字段。
- 改变事件目标、动作语义或必需依赖。

旧 ID 在新快照中可以保留一段兼容期，再通过 `enabled: false` 停用。不建议直接删除已发布过的能力 ID，以免影响历史产物解析和问题追溯。

## 6. 标准发布流程

### 6.1 发布前

1. 明确新能力支持的 App/ROM 范围和端侧实现版本。
2. 判断变更是新增、兼容增强还是破坏性变更。
3. 按第 4.2 节复制上一版完整目录，在新目录中添加或调整能力。
4. 输出新旧快照差异，确认只包含预期的新增、更新或停用项。
5. 根据上线范围拆分 `registry_ranges.json`，确保无重叠；若有未覆盖区间，明确其回退或拒绝行为。
6. 若协议也发生变化，同步新建协议 profile 及其区间；否则保持原 profile 不变。

### 6.2 必须验证

- 三份能力 JSON 可正常解析，并通过对应数据模型校验。
- App/ROM 区间可唯一命中，新旧边界值符合预期。
- 旧版本仍命中旧快照，新版本命中新快照。
- 默认回退开启和关闭两种行为符合预期。
- 新增能力在概述查询、schema 查询、生成、校验和降级链路中均有覆盖。
- Artifact 中记录的 `capabilityRegistryVersion` 与实际加载快照一致。
- 用户可见返回不暴露内部版本字段。
- 变更同步更新云侧方案、能力配置、Skill 参考资料和相关测试。

### 6.3 发布和回滚

1. 将能力快照、区间索引、代码和测试置于同一个可追溯的 Git 提交中。
2. 使用 Git tag 标记完整发布源码状态，并在发布记录中列出新旧 `registryVersion`、适用区间和变更摘要。
3. 上线后观测区间命中、默认回退、能力过滤、生成成功率和校验失败情况。
4. 回滚时恢复上一版区间映射或部署上一个 Git tag，不删除已产生的新快照和 Artifact。

## 7. 版本管理职责划分

| 对象 | 负责内容 |
| --- | --- |
| Git 提交/tag | 记录代码、配置、Skill、测试和生成源的整体状态 |
| 能力 release manifest | 记录某个能力快照由哪个 base 和哪些 patch 组成 |
| 能力快照目录 | 提供微服务运行时直接加载的完整、不可变 JSON |
| `registry_ranges.json` | 将 App/ROM 兼容区间路由到唯一能力快照 |
| 协议 profile 索引 | 将 App/ROM 兼容区间路由到 A2UI 和 Design profile |
| Artifact meta | 记录每次生成实际使用的能力、协议和产物版本 |

## 8. 推荐实施顺序

### 阶段一：立即可用

- 冻结已发布的 `app-11.7.5.205_rom-6.0` 目录。
- 新增能力时创建新的完整快照目录。
- 按 App/ROM 边界拆分 `registry_ranges.json`。
- 补充新旧版本路由、能力加载和 Artifact 追溯测试。

### 后续按需：支持精细灰度

- 在 App/ROM 兼容性过滤之后增加服务端 release 选择。
- 支持白名单、实验分组和稳定回滚。
- 将实际选中的 release 和 `registryVersion` 记录到日志和 Artifact meta，但不暴露到用户可见返回。

## 9. 本次新增能力的最小执行清单

当前已有一个版本发布，如果现在需要新增能力，建议至少完成以下事项：

- [ ] 确认新能力从哪个 App/ROM 版本开始可用。
- [ ] 确认端侧能力已实现，并明确输入、输出、依赖和失败语义。
- [ ] 保留已发布能力目录不变，新建能力快照版本。
- [ ] 只在新快照中添加或调整能力。
- [ ] 拆分 App/ROM 区间，保证新旧版本唯一命中。
- [ ] 判断是否真的需要新增 A2UI 协议 profile。
- [ ] 更新云侧方案、能力配置、Skill 参考资料和测试。
- [ ] 验证能力加载、区间边界、生成、校验、降级和 Artifact 版本记录。
- [ ] 为发布提交打 tag，记录能力快照版本、兼容区间和回滚方式。
