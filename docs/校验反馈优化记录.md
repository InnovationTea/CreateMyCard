# 校验反馈面向修复模型的精简化记录

## 结论

修复模型真正需要的是“位置、问题、原因（必要时）、修改建议”，而不是校验器的内部阶段、分类和规则编号。此次调整采用双层反馈：完整诊断继续用于日志、指标和测试；修复模型只接收精简的 `repairTasks`。

## 调整前

模型收到的每条诊断包含 `stage`、`category`、`code`、`validatorStage`、`fileKind`、`message`、`line`、`jsonPointer`、`actual`、`expected`、`fixHint` 等字段。该结构便于排障，但存在三个问题：

1. 校验器内部术语占用 token，不能直接指导模型修改。
2. `message` 和 `fixHint` 经常重复表达问题，反馈不够聚焦。
3. 模型容易关注“哪条规则失败”，而不是“具体改哪里、改成什么”。

## 调整后

`Diagnostic` 和 `Reporter` 的完整结构保持不变，新增 `QualityIssue.to_repair_payload()`，生成面向模型的最小对象：

```json
{
  "at": "genui:2 /updateComponents/components/0/styles/width",
  "problem": "root 宽度使用固定值",
  "fix": "改为 \"matchParent\""
}
```

当当前值和期望值对修复有帮助时，才附加 `current`、`expected`；位置不明确的转换错误只保留 `problem`。修复请求中的字段由 `qualityErrors` 改为 `repairTasks`，指令同步要求模型逐项处理修复任务，并只输出完整源格式 DSL。

## 设计取舍

- 保留 `line + jsonPointer`：这是模型精确定位的最小可靠信息。
- 不向模型传 `stage`、`category`、`validatorStage` 和规则码：这些信息继续留在日志、指标和测试中。
- 不默认传 `actual/expected`：只有无法从修改建议直接得出目标值时才传，避免重复。
- 不改变 `to_prompt_payload()`：兼容已有回放记录和内部结构化诊断。
- 通过 `repairTasks` 表达“待执行修改”，避免把模型输入塑造成校验器报告。
- 全局输出约束仍由 repair system/user 指令统一传递，不在每条错误中重复。

## 反馈示例对比

调整前：

```json
{"stage":"validation","category":"ARTIFACT_VALIDATION_FAILED","code":"DSL_ROOT_WIDTH_INVALID","validatorStage":"semantic","fileKind":"genui","line":2,"jsonPointer":"/updateComponents/components/0/styles/width","message":"root 宽度必须为 matchParent","actual":160,"expected":"matchParent","fixHint":"把 root.styles.width 设为 matchParent。"}
```

调整后：

```json
{"at":"genui:2 /updateComponents/components/0/styles/width","problem":"root 宽度必须适配宿主尺寸","fix":"把 width 改为 \"matchParent\"。"}
```

调整后的反馈保留了定位和动作信息，同时去掉了不能直接帮助修复的内部元数据。复杂绑定、数组下标等错误仍可在 `problem` 或 `fix` 中补充必要原因，避免为了节省 token 而损失语义。
