# 批跑失败案例分析指南

本文面向使用 Debug Tools 批跑后排查失败样本的同事和 AI 助手，提供从任务定位、证据提取到归因与复验的流程。
重点是区分生成错误、模型可执行的修复、工程展开错误和校验误报，避免仅凭最后一条错误调整提示词或放宽校验。

本文是排障方法，不新增接口、组件、校验或降级规则。业务依据以
[云侧方案设计](../docs/云侧方案设计.md)为准；平台行为见
[调试平台运行规范](调试平台运行规范.md)，代码组织见
[调试平台技术方案](调试平台技术方案.md)。下文事件名、附件名及目录是当前实现的检索入口，
分析历史批次时应以该次记录和对应版本代码为准。

## 1. 快速执行清单

1. 核对实际链接中的任务 ID，选择明确的运行 ID；同一任务可能有多次执行。
2. 固定本次运行、样本、请求、版本、模型和重试上下文，不用当前默认配置解释历史行为。
3. 分别统计首次 DSL 失败、内部修复、批跑重试及最终状态，并按尺寸分组。
4. 保留所有 `attempt_*`，逐轮读取模型源、实际校验输入、错误、修复策略和真正发给模型的消息。
5. 区分 error 与 warning、首个根因与修复引入的新错误、模型输入与确定性展开结果。
6. 对高频问题检查组件合同、视觉配方、语义布局展开、转换器与最终协议是否一致。
7. 用原始上下文离线复现；必要时只在独立进程内改变一个因素，验证归因，不覆盖历史产物。
8. 核验正式 Few-shot 能否通过当前完整发布检查，再讨论示例覆盖和提示词精简。
9. 给出逐样本证据、主因与次因、置信度、修复优先级和未验证范围。
10. 修改后先复验原失败源，再建立独立模型批次比较；测试通过、生成成功与视觉验收分别报告。

## 2. 定位任务与固定分析上下文

### 2.1 任务、运行、样本、请求尝试不能混淆

| 层级 | 标识或目录 | 分析用途 |
| --- | --- | --- |
| 任务 | `taskId` | 保存数据集、样本选择和任务配置 |
| 运行 | `runId` | 一次独立执行；是统计与报告的基本单位 |
| 样本 | 样本 ID，如 `Q055` | 对应一条需求和请求 |
| 批跑尝试 | `attempt_000`、`attempt_001` | 首次请求及批跑器额外重试，不等于模型修复轮次 |
| 请求内尝试 | Trace 的 `attempts`、终态计数 | 区分 Plan、接口、模型传输和质量修复 |

Markdown 链接的显示文字与实际地址可能不同，先检查真实地址，不能从显示文字猜任务。
报告写明运行 ID，不能只引用会随再次执行变化的“最新结果”。

在运行所在机器上，可用以下接口查询。端口按实际平台地址替换；查询单样本会返回较大的 Trace 视图，
不要直接向终端打印整个任务或所有样本正文。

```powershell
$debugBase = 'http://127.0.0.1:8888'
$taskId = '替换为实际任务ID'
$task = Invoke-RestMethod "$debugBase/debug/batch/tasks/$taskId"
$task | Select-Object taskId, name, datasetId, backendMode
$task.runs | Select-Object runId, status, createdAt, total, success, degraded, failed

$runId = '替换为明确选定的运行ID'
$sampleId = 'Q055'
$sample = Invoke-RestMethod "$debugBase/debug/batch/runs/$runId/samples/$sampleId"
$sample.summary
$sample.attempts | Select-Object name
```

API 的 `get_sample` 在特定缺失 Trace 场景下会尝试刷新导入结果。需要严格保持分析证据原状时，
优先读取已保存的运行目录，并在其它输出位置保存分析结果。

### 2.2 保存哪些上下文

- 运行时间、完成或中断状态、数据集快照、样本选择、请求覆盖、并发和超时。
- 已部署或受管后端、目标服务地址；代码提交、协议、能力清单及提示词版本，能够获取多少就记录多少。
- 实际模型路由与阶段、mock、模板、JSX、Plan、主题后处理等是否执行。
- 实际校验开关、质量修复次数、批跑额外重试、接口整轮重试、传输重试和后端 fallback。
- Few-shot 是否启用、是否筛选、实际注入案例；运行时容量上下文是否启用。

已部署模式的任务配置未必包含服务有效配置。优先使用历史请求、模型消息和 Trace 计数，
配置无法确认时明确写“未知”；不能用今天的 `.env`、默认 YAML 或文件修改时间反推历史服务状态。
模型路由名称也不必然等于实际模型版本，没有记录就不要补写。

## 3. 获取与检查原始证据

### 3.1 从运行目录读取

当前实现的典型目录如下，文件是否存在取决于执行阶段与结果：

```text
debug_tools/batch_output/<runId>/
├── manifest.json
├── summary.json
├── summary.md
├── trace_blob_manifest.json
├── trace_blobs/<sha256>
├── <sampleId>/
│   ├── result.json
│   ├── attempt_000/
│   │   ├── request.json
│   │   ├── response.json
│   │   ├── result.json
│   │   ├── artifact.md / blocks.json / genui.jsonl
│   │   └── trace/
│   │       ├── import_manifest.json
│   │       ├── view.json
│   │       └── source/manifest.json / trace.jsonl
│   └── attempt_001/...
└── postprocess/...
```

先枚举实际目录，不假设所有历史版本都使用同样结构。最终失败没有 artifact 或最终 DSL，
不表示没有模型输出；首轮和各轮 repair 的 Compact 源通常仍可从 Trace 附件取得。

### 3.2 正确解引用 Trace 附件

读取 `trace/source/trace.jsonl` 时：

1. 按 `event` 和 `sequence` 查事件，不把 `name` 当成事件字段。
2. 保留 `spanId / parentSpanId / attempts / status`，不要只按附件文件名判断轮次。
3. 从事件的 `artifacts` 取得附件描述，再用 `sha256` 读取运行级 `trace_blobs/<sha256>`。
4. 附件中的 `path: artifacts/...` 是来源 Trace 的路径；批跑导入后不一定存在于样本目录。
5. 原服务 Trace 目录若保留附件，也可按其受控相对路径读取；不能把运行级 blob 不存在自动解释为空正文。
6. 按 `mediaType` 解析 JSON 或 UTF-8 文本，核对 SHA-256 和字节数；缺失、哈希不匹配、解析失败分别记录。

附件按内容去重，相同哈希可能被多个阶段或轮次引用。**文件名不是时间线，事件序号与尝试上下文才是。**
Windows 终端出现中文乱码时，先按 UTF-8 读取并设置 Python 输出编码，例如
`$env:PYTHONIOENCODING='utf-8'`，不要将解码问题误报为模型生成了乱码。

### 3.3 Trace invalid 不等于生成失败

分别检查生成业务状态、Trace 生命周期、视图解析告警和附件完整性。
视图提示“语义记录结构不合法”时，定位具体记录，确认它影响的是显示、计数还是原始证据。
原始事件与附件可完整读取时，可以继续分析，但必须保留这项诊断限制；
缺少关键消息时则不能断言“模型没收到反馈”或“模型原样返回”。

开发 Trace 可能包含完整请求和业务信息。对外分享报告按需引用最小片段，不复制密钥、个人信息或完整敏感请求。

## 4. 统计必须分层

| 指标 | 统计口径 |
| --- | --- |
| 首次 DSL 校验失败率 | 每个样本 `attempt_000` 中第一次 DSL 评估失败的数量 / 有该评估的样本数 |
| 生成前失败 | 参数、前置门禁、Plan、模型调用等未进入首次 DSL 评估的样本，单独统计 |
| 内部修复效果 | 同一次请求内首轮失败、经质量修复成功或耗尽的请求数 |
| 批跑重试率 | 执行了额外 `attempt_*` 的样本数 / 本次样本总数 |
| 批跑重试挽救率 | 前一次请求失败、后续批跑尝试成功的样本数 / 发生批跑重试的样本数 |
| 最终结果 | success、degraded、failed、unsupported、cancelled 等实际状态及数量 |
| 分组结果 | 至少区分尺寸；必要时按业务组合、字段量、操作数、模型、协议版本分组 |
| 调用与成本 | Plan、DSL、质量修复、主题等物理调用数，以及对应 tokens 和耗时 |

缺记录不算零次失败，不把取消、中断和未执行样本算成模型生成失败。
成功率是否含 degraded 必须写明；一个样本多个错误不能重复增加失败样本数。
错误频率还要区分“受影响样本数”和“跨轮累计出现次数”，否则原样返回会夸大某类根因占比。
同一问题可有主因和次因，按类别统计时注明是否允许多标签。

不要用最后一次请求的 `retryCount` 代表整个样本的所有重试。批跑重试、接口重跑、Plan 合同重试、
质量修复、模型传输重试、fallback 应分别统计；运行时间也不能把嵌套 Span 耗时直接相加。

## 5. 逐样本还原失败链

对全部最终失败样本、全部批跑重试样本，以及每类高频问题的修复成功对照样本，建立下表：

| 请求尝试 / 阶段 | 源输出摘要 | 实际处理结果 | 阻断错误与告警 | 发给模型的策略和反馈 | 下一轮变化 |
| --- | --- | --- | --- | --- | --- |
| attempt_000 / initial | 组件、布局、事实和操作 | 展开、校验、转换结果 | 分开记录 | 是否开始 repair | 保留、替换或遗漏了什么 |
| attempt_000 / repair 1…N | 最近一次提交 | 同上 | 同上 | 实际消息中的内容 | 是否消除根因、引入新错或原样返回 |
| attempt_001 / initial… | 从新请求开始 | 同上 | 同上 | 不与前一次请求混算 | 解释重跑为何成功或仍失败 |

当前常用检索入口：

| 事件 | 优先读取的附件或属性 |
| --- | --- |
| `generation_preflight.completed` | `task_spec`、`card_spec`、前置问题 |
| `plan.validation.completed` | `accepted_plan`、`plan_validation_errors`、warnings |
| `dsl.prompt.finalized` | `dsl_prompt_final` |
| `model.physical_call` | 对应阶段的 `*_model_messages`、`*_assistant_raw` |
| `dsl.model.completed` / `repair.model.completed` | `dsl_extracted_output` / `repair_extracted_output` |
| `dsl.semantic_layout.expanded` | 语义源、展开源、来源映射 |
| `dsl.processing` | `dsl_processing_input/output/issues` |
| `dsl.plan_coverage_validation.completed` | `plan_coverage_result` |
| `dsl.compact_validation.completed` | 校验输入、errors、diagnostics 或成功结果 |
| `repair.strategy.selected` | category、scope、strategy、noProgress、fingerprint |
| `repair.prompt.built` | `repair_prompt`、本轮实际质量错误与策略 |
| `artifact_validation.completed` | `artifact_validation_result`、实际标准 A2UI |
| `model.transport_metrics` | 实际路由、阶段、tokens、耗时 |

事件和附件并非每轮都齐全，遇到未出现的名称应检查该次版本实现，不虚构空结果。
最终协议错误可能不在 `dsl_processing_issues` 中，必须继续读取 Artifact 校验结果。
判断模型收到什么，以物理调用的模型消息为最直接证据，再对照 PromptBuilder 的中间组装结果。

每轮重点回答：

- 首个阻断点在哪里？后面的布局、覆盖或协议错误是新根因，还是同一问题的派生结果？
- 模型是不是只改了节点 ID、包装层或布局名字，实际容量和绑定完全不变？
- 是否只在数据行写了字段，却没有可见落点？是否丢失了操作、完整参数、单位或对象标签？
- 错误是否由服务安全修复、语义展开、组件 Recipe、转换或资源映射引入？
- warning 是否真的触发了 repair？不能仅凭控制台出现警告就当作失败原因。
- 策略是否按预期升级？无进展与错误类型切换是否让模型反复回到已失败方案？

## 6. 按证据归因

| 类别 | 确认所需证据 | 优先处理位置 |
| --- | --- | --- |
| 请求或能力边界问题 | 原始请求、前置校验、有效输入与候选一致性 | 数据集、调用方或前置处理 |
| 模型生成错误 | 模型可控制的源中存在非法角色、遗漏、重复、错误绑定或操作 | 生成合同、示例、模型能力 |
| 修复反馈不可执行 | 反馈要求修改禁止输出的属性或不可编辑的内部节点 | 来源映射、反馈组织与责任分流 |
| 修复路由错误 | 结构化诊断与选中 category/scope 不符，轨迹显示错误升级或回退 | 修复策略编排 |
| 工程合同冲突 | 合法源经确定性展开产生不合法样式、必然超预算或无界依赖 | Recipe、语义展开、转换器及配置一致性 |
| 校验误报或边界不合理 | 在相同协议、Recipe 和渲染上下文下，判定与真实合同或可复验行为不符 | 对应校验规则；按专项方案确认归属 |
| Few-shot 与执行链漂移 | 真实发送的正式案例不能通过完整处理和协议校验 | 示例与其依赖的生成源 |
| 容量规划不足 | 候选组件和布局没有完整承载全部事实，重组后持续溢出 | Plan、信息合组及生成引导 |
| 基础设施问题 | 模型传输、超时、下载、存储等异常证据 | 对应基础设施，不能当作 DSL 质量错误 |

### 6.1 判断“校验太严格”之前

先手工复算组件固定尺寸、标签与单位、padding、间距、标题和动作预算，再对照共享运行时。
例如合同允许四项，但最小宽度之和超过其唯一合法槽位，是合同或配方冲突，不是校验计算错误。
放宽容差可能只是把失败转成端侧裁切。

宽度压力估算与精确字体测量不同，最小内容高度与实际可分配高度也不同。
怀疑误报时记录假设、公式、反例、同源 Web 或端侧证据，不凭“看起来能放下”修改门禁。
无法找到合法组合不等于已证明需求无解；应区分“模型没有找到”“有限搜索未找到”和“合同下已证明不可行”。

### 6.2 判断“反馈不充分”之前

核对错误是否进入实际模型消息，再检查反馈是否同时说明了源位置、实际值、约束和合法修复范围。
信息量多不代表可执行：模型只能改语义组件时，要求它修改展开后的 `alignItems` 或几何没有意义。
已有结构化错误码时，复查路由是否仍只依赖英文关键词而遗漏类型；不能只增加一段更长的提示文字。

### 6.3 判断“提示词或 Few-shot 有问题”之前

读取该轮实际发送的消息，确认尺寸、案例、Plan 和修复合同，而非只看当前源文件。
先检查示例的结构、绑定、容量、转换后协议和完整产物，再评估是否缺少密集组合或合法替代路径。
同时检查禁止项与兜底建议是否矛盾，如只允许语义节点，却建议模型直接填写 Row/Column 或内部几何。

输入很长、原样返回较多可以作为优化线索，不能单独证明因果。
全量案例与筛选案例、长短提示词、不同模型的比较应固定样本、协议、组件合同及重试预算，另建批次对照。

## 7. 离线复现与验证边界

1. 使用项目对应 Python 环境，保存版本信息。缺依赖导致的导入失败不计作业务回归失败。
2. 从原 Trace 取源、任务输入、卡片运行配置、Plan、尺寸、协议和校验开关，按原阶段顺序复现。
3. 区分原始模型源、安全处理源、语义展开源、标准 A2UI 和最终主题产物；不要拿错阶段做比较。
4. 先复现相同错误，再在独立进程内只改一个因素，例如候选变体或配方约束，观察同一源是否解除该错误。
5. 内存实验不代表已经修复；不能为得到通过结果删字段、删操作、关闭相关校验或偷偷换更高版本。
6. 对正式 Few-shot 运行同一处理链。仅能解析、能转换或 Compact 校验通过，不等于最终协议和视觉通过。
7. 需要渲染时复用平台的 Python 转换入口和同源 SDK，保留该次实际尺寸与版本。

## 8. 报告模板与复验顺序

建议每次报告包含以下内容，确定事实、推断和待验证项分开表达：

```text
分析对象：taskId / runId / 时间 / 数据集 / 后端与版本
证据范围：样本、请求尝试、附件完整性、缺失项与 Trace 限制
统计口径：首轮 DSL、内部修复、批跑重试、最终状态、尺寸分组
逐样本：需求 → 首个错误 → 每轮反馈/策略 → 源变化 → 最终阻断点
根因：主因 / 次因 / 置信度 / 原始证据与源码位置
验证：原源复现 / 单因素实验 / 示例检查 / 测试 / 渲染与未运行范围
建议：工程合同 → 反馈路由 → 生成与示例 → 额度和成本
变更记录：实际修改文件及用途；未修改则明确说明
```

优先处理确定性工程冲突，再处理模型可执行的反馈，最后调整生成策略。
增加修复次数不能消除固定配方矛盾；关闭最终校验不能证明成功率提高。

实施修复后先验证原失败源和邻近组件/变体，再运行相关回归及差异检查，最后在新运行中复跑原样本。
报告保留首轮与最终结果，不能只展示被多轮重试提高的最终成功率。
模型成功生成、协议合法、Web 质量和真机验收是不同结论，分别列证据。
