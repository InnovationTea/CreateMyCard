# 信息理解与组织

## 1. 识别候选信息

1. 结合 `userQuery`、`data` 和 `actions` 识别用户希望卡片表达的事实与操作。
2. `userQuery` 中明确给出的对象、地点、时间或状态优先于同一字段的预览样例；不得补造输入不支持的事实。
3. 默认保留能够说明对象、时间范围或必要上下文的标题信息。只有省略后仍不会丢失这些上下文时，才采用无标题表达。
4. Action 与数据一样参与信息组织。Action 可以属于某个信息分区，也可以在表达完全不同的目标时形成独立分区。

## 2. 划分信息分区

1. 先按业务对象、场景和任务目标划分信息分区。一个分区表达一个可独立理解的主题。
2. 同一领域不等于必须放在同一分区；当信息分别服务不同场景或任务时可以拆分。不同领域也不等于必须拆分；存在明确使用关系时可以放在同一分区。
3. 判断关联时优先看真实使用关系，例如设备状态与设备电量、日程与对应天气、运动与健康状态、耳机与当前音乐。
4. 不因输入字段顺序或 `userQuery` 的点名顺序机械分区。信息应按语义关系重新组织。
5. 每条保留的数据或 Action 只归入一个分区，避免同一事实在多个分区重复表达。

## 3. 组织分区内关系

1. 在分区内区分以下关系：
   - 汇总—明细：汇总值在事实含义上概括其明细。
   - 主体—属性：对象与其状态、数值、时间或地点。
   - 同级并列：同一维度下可直接比较的对象或指标。
   - 事件—要素：事件与标题、时间、地点等成立条件。
   - 内容—操作：信息与直接作用于该信息的 Action。
2. 相关信息不自动构成汇总—明细。只有一项在事实含义上概括其他项时，才使用该关系。
3. 标签和值保持语义配对；不得把一个事实的标签和值拆入不同分区或不同关系。
4. 普通清单与日程事件应区分：时间是事件成立或排序的核心条件时按事件组织，否则按清单组织；同一数据不得重复映射。
5. 多日天气中，同一天的日期／星期属于时间标识，天气、温度、降雨概率属于天气属性。标题已说明日期范围时，不必同时保留所有重复的时间表达。

## 4. 判断主要与辅助信息

1. 只有能够明确判断时才建立视觉主次；无法判断时保留同级关系，不强造主次。
2. 优先级依据依次为：
   - 真实汇总关系：汇总通常高于构成它的明细。
   - `userQuery` 的明确焦点：用户明确要求关注的内容优先。
   - 结构兜底：概括信息通常高于零散明细。
   - 行动或告警：当卡片目标是促成操作或处理告警时，必要 Action 或告警可成为重点。
3. 点名顺序不等于优先级。多个同级对象可以保持相同层级。
4. 一张卡片可包含多个信息分区，但主要数据焦点应清晰；必要 Action 的重要性独立判断，不因强调数据而被降级或删除。

## 5. 核查、保留与省略

1. 核查算术、单位、时间范围、百分比、总分关系和语义一致性。
2. 保留用户明确要求、表达对象所必需、具有独立决策价值或与必要 Action 直接相关的信息。
3. 只用卡面其他信息即可无歧义推导、重复表达、与目标无关或缺少必要语境的信息可以省略。
4. 省略是容量不足时的最后选择；不得先删必需 Action、用户明确点名的事实或信息分区的关键上下文。
5. 补齐所选字段不可缺少的静态标签、单位、主语、基准期和时间范围，但不得改变业务值。

## 6. 内部信息清单

生成前在内部形成简短清单，至少确认：

- 信息分区及每个分区的主题；
- 每个分区内的汇总、主体、属性、并列、事件和操作关系；
- 能明确判断的主要信息与辅助信息；
- 必须保留的数据 ID、Action ID，以及可省略项。

该清单只用于后续组件与布局选择，不作为额外输出。信息分区是组织候选内容的软引导；后续可依据组件语义和真实槽位容量合并或拆分分区，但不得拆散必要语义配对、改变事实与绑定，或改变 Action 的作用对象和范围。
