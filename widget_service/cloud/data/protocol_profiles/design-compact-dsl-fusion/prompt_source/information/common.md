## 2.6 信息理解与组织

### 2.6.1 识别候选信息

1. 结合 `userQuery`、`dataModelSchema` 和 `eventCandidates` 识别用户希望卡片表达的事实与操作。候选集合只规定最多允许使用什么，不表示必须全部使用。
2. `userQuery` 中明确给出的对象、地点、时间、状态和目标优先于预览样例；不得补造输入不支持的事实、关系或操作。
3. 默认保留能够说明对象、时间范围或必要上下文的信息。只有省略后仍不会产生歧义时，才省略这些上下文。
4. `assetCandidates` 不产生新的业务对象或事实，也不改变信息优先级；素材是否使用由组件规则决定。

### 2.6.2 划分信息分区

1. 先按业务对象、场景和任务目标划分信息分区。一个分区表达一个可独立理解的主题。
2. 同一领域不等于必须合并；信息服务于不同场景或任务时可以拆分。不同领域也不等于必须拆分；存在明确使用关系时可以合并。
3. 判断关联时看真实使用关系，不按输入字段顺序、候选顺序或 `userQuery` 的点名顺序机械分区。
4. 同一业务根下的名称、状态和多个指标仍属于同一对象，不得按字段数量伪造多个对象。
5. 每条保留的事实或操作只归入一个分区，避免在多个分区重复表达。

### 2.6.3 组织分区内关系

分区内只使用能够由输入证明的关系：

- 汇总—明细：一项在事实含义上概括其他项；相关不等于汇总。
- 主体—属性：对象与其状态、数值、时间或地点。
- 同级并列：同一维度下可直接比较的对象或指标。
- 事件—要素：事件与标题、时间、地点等成立条件。
- 内容—操作：事实与直接作用于该事实或对象的操作。

标签和值必须保持语义配对。时间是事件成立或排序的核心条件时按事件组织，否则按普通清单组织；同一数据不得重复映射。多日天气中，同一天的日期或星期是时间标识，天气、温度和降雨概率是该日属性；标题已经说明日期范围时，不重复表达等价时间信息。

### 2.6.4 判断主要、辅助与并列

1. 只有能够明确判断时才建立主次；无法判断时保留同级并列，不强造第一名。
2. 优先级依据依次为：用户明确焦点与直接答案；真实汇总、整体结果或主状态；组成项和局部指标；日期、来源和更新时间等元信息。
3. 卡片目标是促成操作或处理告警时，必要操作或告警可成为重点；其重要性不因数据被强调而自动降低。
4. 多个同级对象可以保持并列。全卡应有一个清晰的主要数据焦点，或一个由用户需求和事实关系共同支持的并列焦点组。

### 2.6.5 核查、保留与省略

1. 核查算术、单位、时间范围、百分比、总分关系和语义一致性；不得把缺失值当作零，也不得把真实零值改成缺失。
2. 用户必须能识别“谁的、什么指标、是什么值”。对象名称优先使用动态字段；只有用户明确指定且不会随数据变化的对象名才使用字面量，不得猜测名称或用占位名称冒充真实对象。
3. 指数、等级、评分、概率、风险、质量等不能自解释的短值，必须保留能够消除歧义的指标标签。
4. 将候选事实和操作归类为：`mustKeep` 表示用户明确要求或用途成立所必需；`shouldKeep` 表示有助理解但可在容量不足时省略；`drop` 表示重复、无关、缺少必要语境或仅由候选存在而产生。
5. 同一事实只显示一次。可以从卡面其他信息无歧义推导、与目标无关、重复表达或没有可靠语境的信息应省略。
6. 容量不足时先删除 `drop`，再删除低优先级 `shouldKeep`。不得先删除用户明确点名的事实、必要操作或对象的关键上下文，也不得改变业务值来适配容量。
7. 可补齐所选字段不可缺少的静态标签、单位、主语、基准期和时间范围，但不得补造动态值。

### 2.6.6 确定动作归属

1. 操作可以属于某个信息分区；只有用户明确要求一个独立于各分区的全卡目标时，才把它作为全卡操作。
2. 同时核对用户要求的行为、作用对象和候选的完整调用目标及参数。相同调用名、同一应用或相邻候选不代表同一操作。
3. 多对象卡的操作必须归属于真实目标；没有匹配操作的分区保持纯展示，不为对称补造入口，也不把无主操作塞入剩余位置。
4. 按实际行为、目标和完整参数去重。同一操作默认只保留一次；目标或参数不同的操作不得只按调用名合并。
5. 按事件合同保留显式操作、裁决隐式入口，并丢弃未获用户授权的副作用操作。按钮文案不得夸大或改写候选实际能力。

### 2.6.7 内部信息清单

生成前在内部确认：信息分区及主题；分区内的汇总、主体、属性、并列、事件和操作关系；主要、辅助或并列信息；必须保留的数据路径与操作，以及可省略项。该清单只供后续组件与布局选择使用，不作为额外输出。后续可按真实槽位容量合并或拆分分区，但不得拆散必要语义配对、改变事实与绑定，或改变操作的作用对象和范围。
