# 信息组织

<!-- prompt:contract -->
## 2.6 信息理解与组织

### 识别对象与事实

结合 userQuery、数据说明及事件候选识别要表达的事实和操作，不把所有候选当需求。用户明确给出的对象、地点、时间、状态和目标优先于预览样例，不补造事实或关系；素材不产生新事实。
保留“谁的、什么指标、什么值”及必要时间范围、对象名称。指数、等级、评分、概率等短值必须能识别指标，百分号或颜色不能代替标签。对象名优先来自动态字段，只有明确且不变的名称才用静态事实。

### 可展示事实准入

逐项判断候选是否直接回答用户要从卡片中看到或执行的内容，再组织主次；不得因为字段或 query 片段存在就收入 Plan：

1. **直接答案**：用户明确要求的业务值、对象、时间、状态、必要标签与操作可以进入；仅帮助理解直接答案的上下文再按 must/should 取舍。
2. **运行时标识**：城市代码（如 `60814`）、城市 ID、实体 ID、记录 ID、查询键、路由键及仅供事件传参的号码、地址或链接，不是默认可见事实。它们继续保留在数据模型、绑定或事件参数中，但不进入 `info_required`；只有用户明确要求查看该代码或标识本身时才展示。
3. **查询包装语**：`关怀提醒`、`温馨提醒`、`做一张卡片`、语气、风格、版式及“帮我看看”等任务表达只指导主题、标题语气或布局，不作为 `text` 事实。只有用户明确要求“显示／写上／标题为”该原文时才可进入可见内容。

过滤只改变可见事实准入，不删除原始数据、事件候选或 Action 参数，也不能借此省略用户明确要求的业务内容。

### 分区与关系

按真实对象、场景和共同任务聚合，不按输入或点名顺序。相同领域可因任务不同拆分，不同领域也可因真实使用关系合并；同一对象多个字段不因此变成多个对象。
分区内使用输入支持的关系：汇总—明细、主体—属性、同级并列、事件—要素、内容—操作。只有一项真实概括其它项时才是汇总，相关不等于汇总。每条事实归属唯一对象或分区；后续可按容量调整组织，但不能打散必要配对。

| 关系 | 必须保留的含义 |
|---|---|
| 同级对象/指标 | 各自对象与标签，不能按顺序或样例大小指定主次 |
| 平均/最高/最低 | 各自统计口径，不把两种口径拼成范围或统称 |
| 事件 | 真实标题、完整时间及必要地点；普通时间属性不冒充事件 |
| 多日数据 | 每一天自己的时间标识与属性；集合标题不代替逐日标识 |
| 日期与星期 | 默认去掉等义重复，用户分别要求时两者都保留 |

格式化时间保留完整动态含义，不根据样例追加上午/下午或把同一时刻两种写法并列。需要区分角色时只说明开始/结束。

### 主要、辅助与并列

优先级依次参考：用户明确焦点与直接答案 → 真实整体结果/主状态 → 局部指标与组成项 → 日期、来源、更新时间等元信息。无法明确判断时保留并列，不强造第一名；必要操作或告警的重要性不因突出数据而下降。
一个短标签、唯一读数/结论及紧密支撑组成完整单焦点；另一指标、地点或备注等可独立回答问题的信息属于独立补充。无真实核心且用户要求逐项查看时是同级清单。全卡形成一个主要焦点或一个有依据的并列焦点组，不将所有字段视为多个主要信息。

### 核查与取舍

- 核查单位、时间范围、百分比、总分及语义，不把缺失当零或把零当缺失。
- 候选中用户明确要求或用途成立必需的内容为 mustKeep；有助理解的可选补充为 shouldKeep；重复、无关或缺可靠语境的为 drop。容量不足先去掉 drop，再取舍可选补充，不改变业务值。
- 已进入接受 Plan 的事实不再属于可随意删减的候选；正常生成与无删除授权的修复保留全部事实。必要标签、对象、范围和单位不因“去重”丢掉。
- 同一事实只展示一次；能无歧义推导且未独立要求的重复说明可省略。必要长地点、日期、时区保持完整含义，不用占位名称替代对象或裁掉尾部。

### 动作归属

行为、作用对象和完整参数共同确定动作，不按调用名、应用名或候选邻接关系合并。直属动作跟随对应信息，不因其它分区更空而移到无关对象；独立任务操作不要求同名数据根。
无匹配操作的分区保持展示，不为对称补入口。同一操作一次，不同目标或参数分别保留。动作简写仍保留必要目标限定，不夸大候选能力；具体授权执行 Core 事件分级。
