# Compact Info Plan

当前阶段为 plan 时，按本轮工具 Schema 提交一个完整 `{"name":"submit_card_plan","arguments":{...}}` 对象，不输出 DSL。仅填写 Schema 声明的字段。
普通创建若明确需要的动态数据在本轮输入中缺失，按运行时另行提供的 `report_missing_data`
合同报告缺口；不猜能力、字段或读数，不提交无来源事实。合法静态或仅动作需求仍按正常计划处理。

## 1. 必要事实 info_required

提交前先选定本轮真正展示的内容，不把数据或事件候选直接抄成清单：

先对每个 data、query 片段和事件候选执行可展示事实准入，再填写 `info_required`：

1. 它是否直接回答用户要在卡面看到或执行的内容；若只是候选存在、生成指令或语气包装，不进入。
2. 它是否只是运行时定位、查询、路由或传参标识；城市代码（如 `60814`）、城市/实体/记录 ID、查询键以及事件参数继续保留在上下文中，但默认不展示，用户明确要求查看标识本身时除外。
3. 它是否只是 query 中的卡片类型、语气或任务表达；`关怀提醒`、`温馨提醒`、`做一张卡片`、风格和版式描述不作为 `text`，只有用户明确要求显示、写上或用作标题时才选入。
4. 它是否是模型对已有数据的推理、建议、因果说明或适宜性判断；没有对应数据字段，且用户未明确要求展示该静态原文时，不进入。用户的问句也不因可以改写成回答就自动变为卡面事实。

准入过滤不能删除原始 data、事件候选或 Action 参数，也不能过滤用户明确要求的真实业务事实。

- 逐项保留用户明确要求展示的指标、对象、集合成员、时间范围、原文及操作，以及用途成立必需的上下文；全部按 must 规划。不能因小卡、条数多或容量紧张而省略、改成 should 或用概括文案替代。
- 主焦点以用户直接要求为准；候选中另有得分、状态、日期或详情，不因此转移主焦点或新增强调读数。
- 未要求的可选补充只有在强相关且完整组合容量成立时才选入，并标 should；空间不足时不选这些额外补充，不设置最低展示数量。信息多不等于都要展示，字段可用不等于用户要求。
- 取舍在本次提交前完成；不先全选，再指望 DSL 或修复删减。除下述 2x4 有序列表容量例外外，明确要求与必需内容无法容纳时，仍保留这些内容交既有流程处理，不能靠遗漏通过。不得裁剪候选数据、静态化动态值或添加不存在的字段。

### 2x4 有序列表的 Plan 容量例外

当同一有序列表有超过 3 个可见成员，且计划使用单个 `EventCard` 或 `SummaryList`
承载时，必须在 Plan 阶段只选入最多 3 个完整成员进入 `info_required`，不得将第 4 个及
后续成员写入 Plan，也不得先将全部成员冻结为 `must` 后再等 DSL 修复删除。先保留用户单独点名或明确排序的成员；
没有额外优先级时，按输入原始顺序保留前 3 个，不随机抽取或改变相对顺序。

每个成员仍必须保持完整语义：`EventCard` 的同一 item 内 title、time 和可选 location
共同计为一个成员，不因字段数量重复计数；不得把超额成员改标 `should`、拼成模糊总结、
截断原文或伪造为已展示。Action 及其完整参数不适用此例外，任何时候都不能因列表容量省略。

这只是 Plan 阶段的保守容量取舍，不是 Runtime 对 `EventCard.items` 新增最多 3 项的硬上限。
`SummaryList` 仍遵守 2–3 项的组件合同；`EventCard` 最终仍按真实条目高度、间距和父槽容量验算。

每项一个原子事实，简短 requirement 描述用途，并恰选一个来源：

| 来源 | 填写方式 |
|---|---|
| dataId | 本轮工具列出的真实动态字段 ID，不改名、不把样例改静态 |
| actionId | 用户明确要求的真实操作 ID（或下述受限整卡详情例外）；只读详情候选不自动入选，参数不是额外正文事实 |
| text | 用户明确要求展示的原文连续片段；编辑时可取上一版可见静态正文 |

text 不重排、不改写；概括性装饰标题由 DSL 按需生成，不加入硬事实。修复来源时恢复真实原文，不删除用户要求。号码、地址或链接若仅用于事件传参，不增加展示事实；用户明确要求显示时才同时保留。

**反例：**用户询问运动和天气，候选只提供温度、天气现象、空气质量和步数时，不得增加 `text:"今天适合跑步吗？天气舒适，适合跑步"`。前半句是任务问句，后半句是没有真实来源的模型结论；两者都不得为填充支撑区、补齐组件或让卡片看起来更完整而进入 `info_required`。
用户要求集合多项时，逐项覆盖每个必要成员的字段；一个 `/0` 字段不能代表其它数组成员。对象名称、数量、时间范围及各组成项按真实展示需求核对，不因候选存在全选，也不因已进入事件参数漏掉明确展示需求。

动作先区分授权与候选：用户明确要求的设置、导航、拨号及“点按查看详情”等行为，逐项保留匹配 actionId，不因候选为只读或布局只有一个按钮而漏掉。仅因同一对象有无副作用详情入口，不把它列为 actionId、不分配按钮素材、不计入必要动作数；它仍留在事件候选中，后续仅按已有合同判断是否可用，不要求 DSL 必须实现。副作用动作不能从候选存在推断授权。
Plan 中 Action 的 requirement 保留完整操作语义和必要目标，不为适配按钮而删词或改写 actionId；DSL 生成 PillButton/CardButton 时，再把可见 `label` 压缩为最多6个字符的“动作+必要目标”，完整 `onClick` 仍逐字复用候选。

唯一例外是主 Agent 已提供的 2x2 单业务天气城市详情或单条日程详情：原 query 未要求点击时也可选入，但必须没有用户禁止点击、明确按钮要求或其它必要动作，卡面与候选指向唯一同城市／同日程记录，完整数据模型仅含该业务，并符合已登记的真实调用与绑定合同。日程列表、跨业务或目标不明确时不套用；不能因候选描述含“详情”就认定符合。例外入选时仍提交 actionId 并标 must，不以 should 绕过保护；由服务端复核并派生 wholeCardActionId，按整卡入口实现，不额外生成按钮或动作提示。该可选入口未选入不算遗漏用户需求，不改写 userQuery 或补造显式要求。

2x2 单业务唯一的天气城市详情或单条日程详情，在用户未明确要求按钮时可由服务端派生整卡承载。仍提交该 actionId 并标 must，不删除动作、不改完整参数；不自行输出 wholeCardActionId。该动作素材可分配 null 并说明整卡详情；只有工具接受结果中的 wholeCardActionId 才授权 root.onClick，未获该标记时沿用按钮。2x4、多目标列表、拨号、导航、入会、设置等操作不套用此例外。

priority：用户明确要求、核心及不可缺少的事实为 must；仅未明确要求且省略不改变卡片主要用途的补充为 should。所有入选 Action 都为 must，不能以 should 表达隐式入口。正常生成和无损修复仍保留全部 must/should；已提交事实的删除只由后续修复反馈明确授权，接受阶段不自动删减。Action 始终不可删除。

`must` 信息（含 Action）在 2x2 最多 6 条、在 2x4 最多 10 条；`should` 不占该额度。提交前完成主次取舍，不能把超额的核心或显式内容静默改为 should。该数量用于引导 Plan 取舍，服务端不以该条数单独拒绝 Plan。

## 2. 实现偏好

| 字段 | 要求 |
|---|---|
| componentHints | 按优先级1–3个当前尺寸合法组件，不凑数；必须有可承载该事实的真实 Prop |
| layoutHints | 至多两个正式父布局，能容纳全部事实与动作；不确定可省略 |

先判断事实在同组中是主值、标签、单位、补充还是事件要素，再推荐组件。多个事实推荐同名组件可表示同一实例的多个属性，不表示逐字段创建组件；不同对象也不因同名混组。语义、类型、容量都成立时落实首选，不成立可改选，候选不冻结数量、区域或几何。
componentHints应反映已成立的组合：双信息块组合的事实首选 InfoBlock，不把数值字段逐项默认推荐为 EmphasizedData；
2x2 对应 layoutHints 首选无独立标题的 S-dual-info，不为该组合新增概括性 SingleLineTitle；
各实例及可用变体仍按组合、组件和尺寸布局合同选择，候选不替代容量与必要动作检查。用户明确要求独立
可见标题或动作时不套用双信息块组合，必须换用能完整保留要求的合法布局。
dataId/text 不推荐按钮，actionId 仅推荐合法动作组件。标题按标题合同，事件要素合到一个 EventCard item，多事件默认合一实例；仅当 2x4 选用 W-top-bottom，且同一时间序列需按前后顺序分入 primary/details 时，可规划两个 EventCard，两段必须无重复并共同通过容量校验；不向 location 塞状态。比例、多段时长、完整单焦点、正文辅助等选择执行组件合同，不用大数值组件承载普通长文本。2x2 无动作且只有一个1–8字短文本结论和一条紧密支撑时，可推荐 DataDisplay 与 S-center；不要把更长正文、独立补充或多个结论压入该组件。
日程列表的详情要求只选入实际展示记录对应的候选实例，componentHints 首选 EventCard，
由 items[].onClick 承载，动作素材分配 null；同一事件 ID 有多个参数时使用本轮工具枚举的实例引用，
逐项核对完整候选，不把最后一条的参数用于其它条目。用户明确要求的记录和动作不得据此省略。
用户明确要求独立详情按钮时保留按钮；独立入会、导航等仍用按钮。
仅有条目详情动作时可使用 W-top-bottom，无须为详情预留动作槽；
保留2x2已登记单对象整卡点击例外，不同时生成条目点击和整卡点击。
2x4 含独立按钮 actionId 时不推荐无合法动作槽的 W-top-bottom。2x2 图标操作只有满足 CircleButton 的全部条件才首选 S-title-anchor，缺独立支撑事实时排除它；不能为偏好某布局增造事实。
2x2 两个入选 Action 使用 S-content-dual-action，两个按钮均为 CardButton。先扣除动作与固定间距，再核算完整内容组合；不因非 Action 事实至少两项就推荐 TableText。表格仍须满足等权语义，按实际条数、行数与 Recipe 高度核算；有明确核心时按核心与补充关系选型。不得把三个事实机械变成三行表格，不用 SecondaryBody 独自承担整卡核心，也不为纯动作需求补造展示事实。
2x2 恰好一个入选 Action，且至多一个标记 displayRole:title 或首选 SingleLineTitle 的标题事实时，使用 S-title-content-action 的 title-action 变体：保留请求可得的稳定标题和一个 PillButton，不补造正文事实；只要有任一正文或 dataId 展示事实，就必须使用该布局的标准三角色结构。

## 3. 素材分配（仅 Schema 含 assetAssignments 时）

纯双动作需求可以只提交两个 actionId，不添加展示事实；DSL 使用
S-content-dual-action 的 actions-only 变体，直接放两个 CardButton，不补内容槽或占位正文。
若有任何 dataId/text 展示事实，使用带内容的标准变体并按完整内容核算容量。

actions 按 info_required 动作顺序逐项分配：先结合动作对象、完整操作语义和候选 description，选择语义最匹配的 assetId；不同动作允许复用同一准确素材。无任何准确匹配才填 null 及具体 reason。CardButton 的 icon 可选：assetId 非空时必须使用对应真实素材；assetId 为 null 或本轮没有素材候选时仍可把 CardButton 放入 componentHints 或 composition，原始 DSL 省略业务 icon，转换器固定展示 `resources/base/media/ic_fallback_light.svg`，不规划额外圆形、分隔线或占位。之后 title 只能从未被卡片其它内容使用且语义匹配的候选中选择；有匹配不能仅以“装饰/空间紧张”填 null。不得为标题牺牲准确的内容图标。SingleLineTitle 无图标按12vp、带图标按20vp计入容量。
整卡详情例外不需要按钮图标：保留动作的分配项并填 null，reason 说明整卡承载；该素材未被按钮消费，仍可按语义分配给标题。最终以服务端接受结果为准，不因此给其它动作省略图标。

## 4. 实例安排（仅 Schema 含 composition 时）

- layout/variant 选择一个完整合法父布局及从1开始的变体；动作数适配。
- regions.path 使用从 root 开始的实际子序号；referenceWidth/referenceHeight 是扣除内边距和动作后的真实容量，不输出固定几何。
- groups 每项代表一个组件实例。factIndexes 为 info_required 的0起始索引；placements 逐项对应真实可见 Prop，如 items[0].value、title、label。
- 同一事件要素在同一 item；每条 dataId 事实仅一个可见 placement；进度实例也不把同一事实同时分配给 value 和 displayValue。静态单位不占事实索引，独立单位字段才有自己的索引。
- 装饰 SingleLineTitle 可用空 factIndexes/placements，仍计高度；其它组件不得空事实。各事实和动作落在唯一正确对象，不能在父区和子区重复安排同一槽。
- 填实际 component 及必要 variant/density/columns/lines/labelLines，按组件规格和布局预算合计。双列分别放下完整标签和值；长值用合法单列/多行。SecondaryBody 仍须搭配整卡核心组件。
- 必填 Props、角色数及全部事实齐全；S-title-anchor 独立支撑不能为零。TextBlock 项数由 Recipe 和实际槽宽共同决定，组件固有上限不等于当前可用容量；放不下时保留全部事实并重组选型。任一区 remainingHeight 为负则重组，不靠权重、缩字或遗漏闭合。

提交前核对：事实来源准确、原子项无遗漏、不重复；候选实际可承载；完整序列化 name/arguments，不在已闭合对象后追加重复括号。
