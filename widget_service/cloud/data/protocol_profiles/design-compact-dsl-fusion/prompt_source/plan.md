# Compact Info Plan（维护源）

> 维护说明不发给模型；仅 `prompt` 标记内正文参与构建。

## 边界

Plan 确定必须展示的信息与操作，同时提交分区、组件实例合组和容量计划。最终 Compact DSL 仍由创建 Prompt 生成。

先把同对象、同事件或同级属性组织成信息组，再给组内事实推荐可共同承载它们的语义组件。
第一候选是合同条件满足时应落实的首选，不是可以任意忽略的备注；其余为不适配时的备选。
同名候选不等于每项事实各生成一个实例；不得为了组件使用率删事实、伪造数值或动作。
# Compact Info Plan

本轮不要生成 Compact DSL，只调用 `submit_card_plan`：

1. 将用户要求展示的内容拆成原子事实，每项填写简短 `requirement`。
2. 动态事实使用工具合同列出的真实 `dataId`；用户明确要求的操作使用真实 `actionId`；
   只有用户原文中的静态正文才使用 `text`；编辑时也可保留 previousDesignToken 已有的可见静态正文。
   每项三者恰好选择一个。
   不为装饰标题新增硬事实：用户未指定的概括性标题由 DSL 阶段按需生成，不写入 info_required.text。
   text 必须逐字来自用户要求展示的原文（编辑时可来自上一版已有可见正文），不能重组词语生成新标题。
   Plan 修复时删除自行增加的装饰事实不等于删除用户要求；保留全部真实要求，不仅改 requirement 掩盖错误 text。
3. 先区分“卡面要看什么”和“操作要带什么参数”。号码、链接、地址即使出现在 userQuery 原文，
   也不自动成为静态正文：仅要求“打开拨号界面并带上号码”时，只保留拨号 actionId；号码由该
   事件候选参数原样携带。仅要求用链接入会或导航到地址同理。若明确要求“显示号码并可拨号”
   或“查看入会链接”，才同时保留对应展示事实；不能一律过滤号码或链接。
   不展示仅供事件传参、内部识别、背景计算或与 `userQuery` 无关的字段。不要把动态样例值改成静态文本。
4. 按已读取的信息、组件选型和组合规则，先在内部判断对象归属、主次与同级关系，再为事实推荐
   实际可承载它的组件。`componentHints` 按优先级填写一至三个组件软候选，不必凑满三个；
   同一组件出现在多项事实中，表示这些事实可以
   合并到一个组件，不表示生成多个实例。先判断各事实在同组中是主值、单位、标签还是补充信息，
   不把每个字段都单独推荐为强调组件；候选是否成立须考虑整个信息组和全部动作的组合容量。
   同名候选只是组件类型，不是信息组标识，不同对象不能据此混组。候选不冻结组件、数量、区域或几何。
   标题组件是唯一例外：单行分区标题推荐 `SingleLineTitle`，标题加紧密相关次信息推荐 `DoubleLineTitle`；
   该事实不再同时推荐正文组件。每个语义分区最多一个标题组件，2x4 左右独立分区可以分别推荐
   `SingleLineTitle`；不能把同一标题重复到多个分区。
   `actionId` 只推荐当前尺寸组件选型中明确支持事件的动作组件，不推荐 EventCard、InfoBlock 等内容组件；
   dataId/text 事实不推荐按钮。
   真实占比、完成度、使用率或余量可推荐对应进度组件；驱动字段可以是 `0–100` 数值，也可以是
   `"68%"`、`"68％"` 这类完整数值百分比字符串。普通正文、布尔值、动作参数和只有样例数字但没有
   比例语义的绝对量不推荐进度组件，也不借用其它对象的数值或从样例截取常量。
5. `layoutHints` 可按偏好填写至多两个能容纳全部事实和操作的正式父布局；不要按业务名或候选字段数
   套固定骨架；没有把握时省略，由 DSL 按完整布局合同确定。它不冻结最终布局，
   不得为了匹配布局删除事实。先考虑信息组可采用的合法组件组合，再推荐可承载它们的父布局；
   不先指定狭小内容槽，再假定权重能压小文字、图形或按钮。
6. 提交前逐句核对用户要求的对象、数量、时间范围、信息和操作；每个 text/dataId 必须对应一个
   真实展示要求，不能仅因原文或候选中存在该值就增加展示项。动作参数不额外占展示容量，
   必须展示的事实也不能因已被事件引用而省略。确保 Plan 是最终卡片的最小充分信息合同。
7. 提交工具合同的 `composition`，不再把合组只留在内部思考：
   - `layout` 与 `variant` 选一个完整合法父布局及从1开始的变体，动作数量须适配。
   - `regions[].path` 对应此变体从root开始的子序号；`referenceWidth/referenceHeight` 是扣除
     该区域内边距后的参考容量，不是输出固定宽高。分区由布局与事实关系决定，不按业务名写机型分支。
   - 每区按显示顺序提交 `groups`，一个group代表一个组件实例；`factIndexes` 是原始
     info_required 的0起始索引，`placements` 与其逐项对应，如 items[0].value、title、label。
     保留全部真实事实/动作，标题和正文不重复展示同一事实；同一事件的时间、地点等合在一个item。
   - 指定实际 component 和必要 variant/density/role/columns/lines/labelLines，先按原字号、行高
     核算 referenceHeight，再合计各组与gap。标题、按钮、环和组件内padding都参与预算，不重复预留。
     不把每个普通字段各做强调块；不因首选候选是强调组件就强行压小正文。真实核心指标仍保持原主值字号。
   - 双列必须各自容纳标签＋完整值＋单位，不能用“两项”代替宽度判断。短标签与值合计接近列宽时用单列；
     长时间、地点、状态单列分行并核算额外高度。数值图形不支持的完整文本不伪造数字。
   - 动作按其所属对象或独立动作槽落点，长CardButton文案用 labelLines:2 并保留完整目标；
     普通按钮高度不变。正文容器承接标题和动作之间剩余空间，所有文字组按原间距紧凑排列。
   - 全区合计放不下时，先重新组合/重选合法分区再提交，不能只提高权重、降低字号或省略信息。
     无必需标题事实且完整变体允许时不增装饰标题；骨架要求的标题不得省略。

选型反例自检：
- “在线/离线”“多云/晴天”等状态不是数值；作为核心结论时优先 `EmphasisText`，作为普通信息时使用 `SecondaryBody`，不推荐 `EmphasizedData` 或 `DataDisplay`。
- 多项信息都属于同一对象，不代表每项都推荐 InfoBlock；只有当前尺寸允许的固定双信息块/辅助槽才采用它。
- 先确认所有必要动作，再排除只属于无动作布局的组件；不得推荐后又通过省略操作来满足组件条件。
- 同一事件的标题、起止时间和地点共同组成 EventCard 的一个 item；1–2 个事件放在同一个 EventCard 中，
  不因事实拆分而重复创建组件或省略结束时间。
- SingleLineTitle 每个语义分区最多一个；2x4 左右独立分区可分别使用。标题事实不推荐正文组件；正文、普通
  时间、metadata 和补充说明使用 SecondaryBody，核心文本结论使用 EmphasisText。
