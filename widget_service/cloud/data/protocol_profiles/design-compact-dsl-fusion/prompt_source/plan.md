# Compact Info Plan（维护源）

> 维护说明不发给模型；仅 `prompt` 标记内正文参与构建。

## 边界

Plan 确定展示信息的优先级与操作。运行时容量上下文开启时，同时提交分区、组件实例合组和容量计划。最终 Compact DSL 仍由创建 Prompt 生成。

<!-- prompt:contract -->

先把同对象、同事件或同级属性组织成信息组，再给组内事实推荐可共同承载它们的语义组件。
第一候选是合同条件满足时应落实的首选，不是可以任意忽略的备注；其余为不适配时的备选。
同名候选不等于每项事实各生成一个实例；不得为了组件使用率删事实、伪造数值或动作。
# Compact Info Plan

当最新用户消息标记 `<agent_stage>plan</agent_stage>` 时，不生成 Compact DSL，
只提交 `submit_card_plan` JSON 工具调用包。收到该工具的成功结果和
`<agent_stage>compact_dsl</agent_stage>` 后，本阶段限制结束，继续在同一对话中生成 Compact DSL：

1. 将用户要求展示的内容拆成原子事实，每项填写简短 `requirement`。
   每项同时填写 `priority`：核心信息、用户明确不可缺少的内容以及所有操作为 `must`；
   省略后仍不改变卡片主要用途的补充信息为 `should`。用户明确提到某项信息不自动等于 `must`；
   不确定时根据它对卡片主要用途的影响及其与核心信息的主次关系选择，不因保守而默认标记为 `must`。
   正常生成、常规修复与无损紧凑阶段仍须展示全部 `must/should`。只有这些阶段全部失败后，
   最终有界兜底才能删除一个由程序锁定的非 Action 业务展示组件；优先删除只承载 `should` 事实的组件，
   没有候选时允许该唯一组件承载 `must` 事实。这不授权 Plan 模型或 DSL 模型自行删减，Action 始终不可删除。
2. 动态事实使用工具合同列出的真实 `dataId`；用户明确要求的操作使用真实 `actionId`；
   只有用户原文中的静态正文才使用 `text`；编辑时也可保留 previousDesignToken 已有的可见静态正文。
   每项三者恰好选择一个。
   不为装饰标题新增硬事实：用户未指定的概括性标题由 DSL 阶段按需生成，不写入 info_required.text。
   text 必须逐字来自用户要求展示的原文（编辑时可来自上一版已有可见正文），不能重组词语生成新标题。
   静态要求可用最短的原文连续片段作 text，把用途写在 requirement 中；不为了补“目标”等标签
   重排原句或插入空格。例如原文“今天目标是8000步”，目标事实 text 可为“8000步”，
   不能自拟“今天目标 8000 步”。修复来源错误时改回原文片段，不删除这项真实目标。
   Plan 修复时删除自行增加的装饰事实不等于删除用户要求；保留全部真实要求，不仅改 requirement 掩盖错误 text。
3. 先区分“卡面要看什么”和“操作要带什么参数”。号码、链接、地址即使出现在 userQuery 原文，
   也不自动成为静态正文：仅要求“打开拨号界面并带上号码”时，只保留拨号 actionId；号码由该
   事件候选参数原样携带。仅要求用链接入会或导航到地址同理。若明确要求“显示号码并可拨号”
   或“查看入会链接”，才同时保留对应展示事实；不能一律过滤号码或链接。
   不展示仅供事件传参、内部识别、背景计算或与 `userQuery` 无关的字段。不要把动态样例值改成静态文本。
4. 按已读取的信息、组件选型和组合规则，先在内部判断对象归属、主次与同级关系，再为事实推荐
   实际可承载它的组件。`componentHints` 按优先级填写一至三个组件软候选，不必凑满三个；
   同一组件出现在多项事实中，表示这些事实可以
   合并到一个组件，不表示生成多个实例。先判断各事实在同组中是主值、单位、标签还是补充信息，
   不把每个字段都单独推荐为强调组件；候选是否成立须考虑整个信息组和全部动作的组合容量。
   同名候选只是组件类型，不是信息组标识，不同对象不能据此混组。候选不冻结组件、数量、区域或几何。
   2x4 同时要求集合数量与成员详情时，数量可首选 Badge，与包含统计范围和集合名称的标题组成
   一个标题单元；成员的事件标题和时间首选同一个 EventCard，不把成员名称当作集合标题。
   数量不是标题字段，不推荐 SingleLineTitle 承载数量；确需完整统计句时推荐 EmphasisText。
   候选组件必须有语义匹配的真实属性；事件状态不能因属于日程就推荐 EventCard.location，
   无该属性的组件不列为该事实的候选，普通状态补充推荐 SecondaryBody。
   只有统计概览而没有成员详情时，“统计范围＋数量＋对象名称”仍作为同一主信息。
   用户主要要求概览的“统计范围＋数量＋对象名称”作为同一主信息时，优先 EmphasisText 完整承载，
   不为省空间改成次级正文；超宽用同字号分行或更换分区，不能删范围或数量后缀。辅助时间仍按普通正文表达。
   “7小时1分”等完整多段时长是文本主读数，不是一个纯数字：主信息首选 EmphasisText，
   辅助信息沿用 SecondaryBody，但只能与同一语义分区内的核心信息组件搭配；不推荐 EmphasizedData，
   不拆完整绑定或从样例取数字。
   带标签的辅助时长按完整标签＋值核算，单行不足时合法两行或重排，并预留真实行高。
   标题组件是唯一例外：单行分区标题推荐 `SingleLineTitle`，标题加紧密相关次信息推荐 `DoubleLineTitle`；
   该事实不再同时推荐正文组件。每个语义分区最多一个标题组件，2x4 左右独立分区可以分别推荐
   `SingleLineTitle`；不能把同一标题重复到多个分区。先决定动作组件，并为 `PillButton` 和 `CircleButton`
   分配与动作语义匹配的图标；再从按钮未使用的候选中为标题选择与标题或卡片主题语义匹配的素材。按钮与
   标题不得复用同一素材，但可分别使用不同的语义匹配素材。标题获得素材时按 20vp 标题区规划容量；没有
   剩余匹配素材时不推荐标题图标并按 12vp 规划容量。不得为了保留标题图标把可使用准确图标的动作改成
   纯文字按钮，也不能伪造素材路径。
   工具 Schema 提供 `assetAssignments` 时必须显式提交素材分配：`actions` 按 info_required 中的动作顺序
   逐项填写，每个动作都选择一个语义匹配的 `assetId`，没有匹配素材时填写 `null` 和具体 `reason`；完成
   动作分配后，`title` 从尚未使用的候选中选择与主标题或整张卡片主题最匹配的 `assetId`。只要仍有匹配
   素材，标题不得以“可选”“装饰”“空间紧张”等笼统理由填写 `null`；确实没有匹配素材时才填写 `null`
   和具体原因。一个素材只能分配一次，不能通过让按钮不用准确图标来给标题腾素材。
   `actionId` 只推荐当前尺寸组件选型中明确支持事件的动作组件，不推荐 EventCard、InfoBlock 等内容组件；
   dataId/text 事实不推荐按钮。
   2x2 只有一个显式动作时，若候选中存在与动作语义严格匹配的 SVG、用户未要求卡面显示动作文字，且
   正文事实可明确拆分为一个主信息组与至少一个可由核心组件承载的独立其它信息组，动作首选 `CircleButton`，其它信息进入
   左下支撑区；支撑信息不要求固定三项，但不能为零。标题、动作以及仅在标题中展示的地点、对象或范围
   上下文都不计作其它信息，也不能重复展示到支撑区凑数；左下不能只有 `SecondaryBody` 与按钮。满足这些条件时，`CircleButton` 和
   `S-title-anchor` 排在 `PillButton` 与文字动作布局之前，也不要求先证明整宽按钮会压缩正文。缺少独立
   支撑事实、准确图标，动作必须依赖
   文字解释、用户明确要求按钮文案或操作风险需要文字确认时，首选 `PillButton`。用户仅用“点击、点一下、
   打开、查看”等词描述动作，不等于要求卡面显示动作文字；只有明确要求展示按钮文案时才算文字要求。
   真实占比、完成度、使用率或余量可推荐对应进度组件；驱动字段可以是 `0–100` 数值，也可以是
   `"68%"`、`"68％"` 这类完整数值百分比字符串。普通正文、布尔值、动作参数和只有样例数字但没有
   比例语义的绝对量不推荐进度组件，也不借用其它对象的数值或从样例截取常量。
5. `layoutHints` 可按偏好填写至多两个能容纳全部事实和操作的正式父布局；不要按业务名或候选字段数
   套固定骨架；没有把握时省略，由 DSL 按完整布局合同确定。它不冻结最终布局，
   不得为了匹配布局删除事实。先考虑信息组可采用的合法组件组合，再推荐可承载它们的父布局；
   不先指定狭小内容槽，再假定权重能压小文字、图形或按钮。
   候选比较使用当前尺寸布局合同的适用信息关系和容量，不只按操作数量选布局。
   对满足单动作准确图标条件的 2x2 请求，只有正文事实能拆分为主信息与至少一个独立其它信息组时，才
   优先把 `S-title-anchor` 放在第一位，并将其它信息安排到左下支撑区。若除标题和主信息外没有独立支撑
   事实，`layoutHints` 必须排除 `S-title-anchor`，改选 `S-title-content-action` 等可承载文字动作的布局。
   它不是文字动作布局失败后的回退。
6. 提交前逐句核对用户要求的对象、数量、时间范围、信息和操作；每个 text/dataId 必须对应一个
   真实展示要求，不能仅因原文或候选中存在该值就增加展示项。动作参数不额外占展示容量，
   必须展示的事实也不能因已被事件引用而省略。确保 Plan 是最终卡片的最小充分信息合同。
7. 只有本轮工具 Schema 声明 `composition` 时才提交该字段；Schema 中没有时不输出、不猜测分区高度。
   需要提交时，不再把合组只留在内部思考：
   - `layout` 与 `variant` 选一个完整合法父布局及从1开始的变体，动作数量须适配。
   - `regions[].path` 对应此变体从root开始的子序号；`referenceWidth/referenceHeight` 是扣除
     该区域内边距后的参考容量，不是输出固定宽高。分区由布局与事实关系决定，不按业务名写机型分支。
   - 每区按显示顺序提交 `groups`，一个group代表一个组件实例；`factIndexes` 是原始
     info_required 的0起始索引，`placements` 与其逐项对应，如 items[0].value、title、label。
     保留全部真实事实/动作，标题和正文不重复展示同一事实；同一事件的时间、地点等合在一个item。
   - 某个 region 包含 `SecondaryBody` group 时，同一 region 还必须包含至少一个核心信息组件 group；
     标题、Badge、PillButton、CircleButton、CardButton、布局容器及其它 SecondaryBody 都不算核心。
     不能用其它 region 的核心组件满足该条件，也不能提交只有 SecondaryBody 加动作的 region。
     无硬事实的装饰 SingleLineTitle 用 factIndexes:[]、placements:[] 预留，仍计标题高度，
     不为填索引而把主读数重复放进标题。其它组件不能用空事实组。
     一条事实用于同一进度实例的 value 和 displayValue 时，重复该索引使 placements 逐项对应，
     不新增重复 info_required；数值附带的静态单位不占事实索引，也不把数值绑定到 unit。
     独立的数据单位字段才使用它自己的事实索引；已经包含单位的完整读数不拆分。
   - 指定实际 component 和必要 variant/density/role/columns/lines/labelLines，先按原字号、行高
     核算 referenceHeight，再合计各组与gap。标题、按钮、环和组件内padding都参与预算，不重复预留。
     不把每个普通字段各做强调块；不因首选候选是强调组件就强行压小正文。真实核心指标仍保持原主值字号。
   - 双列必须各自容纳标签＋完整值＋单位，不能用“两项”代替宽度判断。短标签与值合计接近列宽时用单列；
     长时间、地点、状态单列分行并核算额外高度。数值图形不支持的完整文本不伪造数字。
   - 动作按其所属对象或独立动作槽落点，长CardButton文案用 labelLines:2 并保留完整目标；
     普通按钮高度不变。正文容器承接标题和动作之间剩余空间，所有文字组按原间距紧凑排列。
   - 全区合计放不下时，先重新组合/重选合法分区再提交，不能只提高权重、降低字号或省略信息。
     任一区域 `remainingHeight` 为负、事实分配不完整或动作数与布局不兼容，都是不可提交的 Plan。
     无必需标题事实且完整变体允许时不增装饰标题；骨架要求的标题不得省略。
   - 已选择 `S-title-anchor` 时，右下动作 group 必须是 `CircleButton`，左下支撑与上方主内容分别落到
     合同路径；左下支撑必须分配至少一个未被标题或主信息消费的独立事实。没有该事实时不得提交
     `S-title-anchor` composition，应在 Plan 阶段整体重选带文字动作的合法 composition；不得等到 DSL
     阶段再换回 `PillButton` 后压缩、拼接或裁切正文。
   - path 必须是所选完整变体的实际承载位置：外层正文加动作的容器高度不等于内层纯正文容量，
     应读取 contentBudgets 中纯正文路径，不能把按钮已占的高度又给正文。固定双槽最多两个实例；
     同一槽不能在父区 groups 和另一个子区重复安排不同内容。动作数量变了就重新选完整变体。
   - 每个实例先核对必填 Props，再核算容量。只有时间和地点、没有真实事件标题时，不用 EventCard
     并伪造 title，改用可合组承载这些普通属性的合法正文。TextBlock 要把已分配的2–4项同级
     明细全部放入同一个 items，不另拆正文后用一个新增目标文本填成只有1项的 TextBlock。

输出严格 JSON：一次序列化完整 name/arguments 对象，不在已经闭合的 regions/composition 或
assetAssignments 后
重复追加括号。发生 text 来源错误时，静态要求仍逐字保留用户原文，不能通过删掉用户要求来修复。

选型反例自检：
- “在线/离线”“多云/晴天”等普通孤立状态不是数值；作为核心结论时使用 `EmphasisText`。但一个短标签、
  一个唯一短文本结论和一条紧密支撑共同构成完整单焦点时，2x2 无动作卡可使用 `DataDisplay`，核心字号固定 18fp。
- 多项信息都属于同一对象，不代表每项都推荐 InfoBlock；只有当前尺寸允许的固定双信息块/辅助槽才采用它。
- 先确认所有必要动作，再排除只属于无动作布局的组件；不得推荐后又通过省略操作来满足组件条件。
- 同一事件的标题、起止时间和地点共同组成 EventCard 的一个 item；多个事件放在同一个 EventCard 中，
  不因事实拆分而重复创建组件或省略结束时间。
- SingleLineTitle 每个语义分区最多一个；2x4 左右独立分区可分别使用。标题事实不推荐正文组件；辅助正文、
  普通时间、metadata 和补充说明使用 SecondaryBody，并与同区核心组件搭配；核心文本结论使用
  EmphasisText。SecondaryBody 不得成为分区唯一信息组件，按钮和标题不算核心组件。
