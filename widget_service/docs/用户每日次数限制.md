# 用户每日成功次数限制

## 职责与计次规则

Python 仅通过内部 HTTP API 查询和记录次数，不连接 MySQL，不读取数据库密码或 STS。
API 服务端由接入方实现，负责存储、唯一约束和一致性；当前两个接口及以下 JSON 是待接入契约，
不是对已部署接口的声明。`ops_metrics.py` 仅作 HTTP 调用方式参考，不改动原有指标上报。

- 默认关闭，开启后默认每个用户每天 20 次，三个生成接口的新建和编辑共享额度，查询接口不受限。
- 使用原始请求 uid 和 requestId；requestId 沿用 sessionId&interactionId 及既有兼容取值。
  不使用模型修复出来的身份。uid 或 requestId 为空时放行、不计次；上游必须保证身份可信。
- uid 和 requestId 分别进行 UTF-8 / SHA-256 小写十六进制编码。每人每天一条汇总记录，
  唯一键为 uidHash + usageDate；requestIdHash 存入该行普通字符串列表，仅当天去重。
  不使用 recordId 或 sessionId 去重。同一请求当天跨接口只计一次，次日重新请求可以再计一次。
- 已计次请求直接放行，即使当天额度用尽；不缓存生成结果，仍允许再次生成。
- 日期使用北京时间请求进入检查时的日期；跨午夜完成仍记入入口日期，无需午夜清零。
- 在 arguments 修复前等待查询 API 返回，修复和内部重试共享本次检查。
- 只有业务 success、有有效产物且实际发送 AIWidgetEnd SUCCESS 未报错才记录。
  degraded、unchanged、失败、指令关闭、开始指令未成功、结束指令发送失败均不计次。
  后续 final 帧失败不撤销计次。发送成功不是端侧 ACK。
- 记录 API 必须等待确认，不能像运维指标上报一样后台发送；查询失败拒绝生成，
  交付后记录失败最多尝试 3 次（延迟 0、0.1、0.3 秒），最终失败仅告警，不改变已交付结果。
- 不做并发预占；不同请求可能同时通过检查而超额，崩溃和最终记录失败可能少计。

## API 接入契约

参考运维上报使用 HTTP POST、application/json 和 sessionId/body 包装。
协议、域名和端口统一使用独立配置 Settings.daily_usage_slb，调用会等待响应；接口路径可配置。
此方案假设 API 在可信内网/同容器边界提供，不附加数据库凭据，不实现 API 服务端。
如后续需要跨服务认证，应另行明确认证协议，不将数据库 STS 密钥当作 HTTP 令牌。

### 共同请求体

```json
{
  "sessionId": "会话上下文标识，仅用于追踪",
  "body": {
    "recordId": "Python 在入口生成的 UUID hex",
    "uidHash": "原始 uid 的 SHA-256，64 位小写十六进制",
    "requestIdHash": "原始 requestId 的 SHA-256，64 位小写十六进制",
    "usageDate": "2026-10-23"
  }
}
```

两个接口都接收此结构；请求中不含明文 uid、明文 requestId、数据库配置。
sessionId 从任务上下文获取，缺失时使用 recordId；它不参与去重。
同一次生成后的全部记录重试使用相同 recordId、摘要和日期；同一 requestId 再次调用生成接口，
recordId 可以不同，API 仍须按 uidHash + usageDate + requestIdHash 去重。
recordId 仅在当天首次插入汇总行时作为主键使用；后续请求追加到已有行，不替换行主键。

### 1. 查询快照

默认路径：`POST /genui-agent/v1/daily-usage/snapshot`。

成功返回 HTTP 200：

```json
{"success":true,"data":{"alreadyCounted":false,"usedCount":19}}
```

- alreadyCounted：该用户在 usageDate 对应行的列表是否含 requestIdHash，严格 Boolean，不查询其它日期。
- usedCount：该用户在 usageDate 对应行的列表长度，严格非负整数，不接受字符串、浮点数或 Boolean。
- API 只读、不预占、不扣次；Python 判断 alreadyCounted 为 true 直接放行，否则比较 usedCount 与上限。
- 读写须满足成功记录返回后查询可见，不能因缓存或只读副本延迟持续返回旧计数。

### 2. 记录成功

默认路径：`POST /genui-agent/v1/daily-usage/record-success`。

完成持久化后返回 HTTP 200：

```json
{"success":true}
```

- 当天首次请求创建一条汇总行，列表包含该请求摘要；后续不同请求追加到同一列表，不新增行。
- 当天重复请求不再追加，仍返回成功；次日请求写入另一条汇总行。
- 必须使用 uidHash + usageDate 唯一键，事务内锁定当天行、精确去重后同时更新字符串和次数，禁止无锁读改写。
- 成功必须表示已提交持久化或已存在同一成功记录，不代表仅接收请求、发送 MQ 或入队。
- 数据库提交成功但 HTTP 响应丢失时，Python 会使用相同记录重试，API 仍应返回成功而非重复错误。
- [SQL](../sql/daily_usage.sql) 仅供 API 实现参考，Python 不执行它；数据库配置、密码和 STS 由 API 服务管理。

### 失败处理

业务失败可返回 HTTP 200 + `{"success":false}`；HTTP 非 200、超时、网络失败、非法 JSON、
缺少或类型错误的成功标志均按失败处理。HTTP 202 不视为持久化完成，不跟随重定向。
查询 data 或字段非法也视为失败，不默认补零放行；接口响应的附加字段忽略。
查询失败对主 Agent 返回 DAILY_USAGE_LIMIT_UNAVAILABLE；超限返回 DAILY_USAGE_LIMIT_EXCEEDED。
成功记录失败执行有限重试。日志不输出完整请求、响应正文或底层异常消息，只记录摘要、阶段及异常类型。

## 配置与部署

| 配置 | 默认值 / 说明 |
| --- | --- |
| enable_daily_usage_limit | false；总开关，与运维指标开关无关 |
| daily_usage_limit | 20；正整数 |
| daily_usage_slb | 默认空；独立地址，包含 http/https 协议、域名及可选端口；开启前必须填写 |
| daily_usage_api_snapshot_path | /genui-agent/v1/daily-usage/snapshot |
| daily_usage_api_record_path | /genui-agent/v1/daily-usage/record-success |
| daily_usage_api_timeout_seconds | 3.0；单次 HTTP 操作及整体存储操作超时 |

daily_usage_slb 例如 https://genui.example.test:8443，不允许携带认证信息、查询串或 fragment。
不再读取或回退到 hag_slb_url；该公共配置继续供原有其它业务使用，不受本次调整影响。
path 填以 / 开头的本地路径，不含查询串和 fragment；从域名根目录开始，替换基础 URL 原有路径。
例如上述基础地址与默认查询路径组合为 https://genui.example.test:8443/genui-agent/v1/daily-usage/snapshot。
已移除 daily_usage_api_host 和 daily_usage_api_port，不再回退 localhost 或容器 IP。
旧 daily_usage_mysql_* 配置已移除，包含数据库密码 STS 键名；旧配置不再参与执行。
绿区优先 spec / properties，蓝区回退 default_config.yaml，不合并；旧 spec 缺配置时总开关默认关闭。
沿用 Settings 环境变量规则，例如 WIDGET_SERVICE_DAILY_USAGE_SLB。配置变更需要重启。
开启环境升级时必须显式新增 daily_usage_slb；地址为空或非法会使初始化失败，不使用旧地址兜底。
关闭时不创建 HTTP 客户端、不校验 daily_usage_slb、不调用 API。开启时创建应用级异步 HTTP 客户端，
启动不主动请求 API，应用退出时关闭。禁用环境代理，不跟随重定向。

上线：实现并验证两个 API → 部署关闭状态代码 → 配置地址/路径 → 联调幂等、跨天和故障 → 开启。
API 未实现前保持关闭，禁止用空成功响应或固定计数模拟生产可用。
历史日期的记录仍用于处理入口日期不变的延迟交付和写入重试，不能随意删除尚在重试窗口内的数据。

## 每日汇总表与升级

`request_id_hashes` 使用普通 TEXT，Java 实体字段为 String，内容是英文逗号分隔的 64 位小写十六进制摘要。
没有方括号、引号，不是 JSON 文本，不使用 MySQL JSON 类型、函数或生成列。空字符串表示没有请求。
例如用户当天先成功 A、再成功 B、再重复 A，始终只有一行，字符串从 `A` 变为 `A,B`，次数为 2。
次日 A 再次成功会新建次日行 `A`，次数为 1。这里 A/B 代表完整摘要，不是明文 requestId。
`used_count` 是普通 INT，由 Java 按去重后的条目数计算，与字符串一起更新。TEXT 最多容纳 1008 个此类摘要；
写入前检查长度，超出时报错而非截断。如果日限额提高到此规模，须先扩容字段。

Java 写入使用独立事务：先确保当天行存在（已存在则不覆盖），按用户和日期 SELECT FOR UPDATE；
读取并严格校验字符串，已有请求直接返回，否则追加摘要并按条目数更新字符串和计数。
主键冲突但找不到对应用户日期行时必须失败；格式损坏、重复摘要或计数不一致也失败，不能当空列表覆盖。
事务提交后再返回 success。查询接口无行时返回 alreadyCounted=false、usedCount=0，不预建空行。
列表由 Java 维护，HTTP 请求仍只携带当前请求摘要，不传历史列表；Python 不直连数据库。

已有旧表不能直接执行新建脚本完成升级，也不能只替换 XML。应停用计次写入并备份，创建新结构临时表，
按 uid_hash、usage_date 聚合旧 request_id_hash 到逗号分隔字符串，保留组内一个唯一 id；核对每组条目数
与旧记录数、去重和总量后，由 DBA 切换表并部署新版 Java，再恢复开关。旧表保留用于回退。
本次不连接或修改实际数据库；没有执行自动迁移。空白测试库可以直接执行新建表 SQL。
若曾部署上一版 JSON 汇总表，也需转为文本列和普通计数列；迁移时不能受 GROUP_CONCAT 默认长度限制而截断。

## 日志排查

统一搜索 `[Daily Usage]`，请求日志沿用现有 session 上下文，查询与写入使用同一个 `record_id` 串联。
正常节点使用 INFO，超限使用 WARNING，查询或写入失败使用 ERROR；总开关关闭也会打印跳过原因。

- `initializing` / `initialized`：启动时打印有效开关、上限、超时和客户端是否初始化，不代表 API 已连通。
- `bypass`：跳过查询与计次，原因区分 `disabled`、`non_generation`、`missing_uid`、`missing_request_id`。
- `check_started` → `api_started operation=snapshot` → `api_response` → `checked`：查询开始、
  HTTP 返回状态和耗时、校验通过的 `used_count`、`limit`、`already_counted`、`remaining_count`。
  剩余次数为 `max(limit - used_count, 0)`，放行和超限日志也打印；这是本次查询时的可用次数，
  不是生成成功扣次后的次数。写入接口当前仅返回成功标志，不根据旧快照推算或伪造写入后的剩余次数。
- `allowed`：`within_limit` 表示等待成功交付后计次；`already_counted` 表示同轮已计次，不重复写入。
- `rejected reason=limit_exceeded`：达到上限；`check_failed`：客户端未初始化或查询失败。
- `record_skipped reason=success_delivery_not_confirmed`：已通过查询且尚未计次，但本次未满足成功交付条件；
  同时记录业务状态及开始指令状态，可结合相邻指令发送日志判断失败、无产物、指令关闭或发送失败。
- `record_started`：每次写入的 `attempt` / `max_attempts`；`recorded`：API 已确认持久化或同轮记录已存在，
  不代表一定新增了数据库行。`record_failed` / `record_exhausted` 表示失败重试 / 重试耗尽。
- `api_response` 仅表示收到 HTTP 响应，不代表业务成功；应继续查看 `checked` / `recorded` 或失败日志。
  `api_failed` 记录网络异常类型与耗时；外层操作超时由 `check_failed` / `record_failed` 记录。

不输出原始 uid、完整请求或响应正文、底层异常消息；只记录标识摘要和上述状态字段。
计次策略、重试次数、错误返回和生成结果均保持不变。

## 验证范围

客户端生命周期、幂等重试、跨天及 WebSocket 调用链。只证明 Python 客户端遵守契约，
不证明尚未实现的真实 API、数据库唯一约束或读写一致性；这些必须在接入后单独联调。
